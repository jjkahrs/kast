Kast Chat Service

One chat service per realm (services/chat, C++20). It owns all chat that isn't proximity chat:

  • Whispers to a character by name, on any map of any world server of the realm. The sender gets an echo; a name with no chat connection gets "not online".
  • Fixed channels from CHAT_CHANNELS (default General,Trade,LFG), numbered /1, /2, /3 in that order. Every client is put in the first (General) on each connect and can join and leave the others; there are no player-made channels.
  • The zone channel: everyone online on the sender's current map.
  • Ignore: /ignore name hides that character's whispers, channel and zone lines until logout (memory only).
  • GM mutes: a GM or admin (the role in their JWT) mutes a character for some minutes. A muted character's whispers, channel and zone lines are dropped here, and its say, yell and emote on every world server (the mutes go to them over the link). Mutes are stored in MySQL (kast_chat) and survive restarts.

Proximity chat (say, yell, emote) stays on the world server, so it keeps working when the chat service is down.

How it fits together

game client --TLS 7777--> world server --TLS 7779 (internal link, shared secret)--> chat service
     |                         |  CharOnline / MapChanged / CharOffline  -->         ^
     |                         |  <-- MuteState                                        |
     +--------- TLS 7778, same access token (Hello, Auth) ------------------------------+
  1. The client logs in to the world server and enters the world. The world server answers EnterWorldOk, then ChatServer{host, port} (CHAT_PUBLIC_HOST / CHAT_PUBLIC_PORT).
  2. The world server tells the chat service CharOnline{account, character, name, map} over its internal link, then each map change and the logout.
  3. The client opens a second TLS connection to the chat service with the same access token. The chat service verifies it against the auth service's JWKS, binds the connection to the account's online character (waiting up to CHAT_BIND_TIMEOUT_MS for its CharOnline), answers AuthOk and puts it in General.
  4. If the chat service goes down, the client's chat connection closes, say/yell/emote keep working, and the client reconnects with backoff; once back, it is in General again and rejoins its other channels.

Several world servers can link to one chat service; each sends its own characters.

Layout

PathWhat
server/chat_router.* Who is online on which map, which client is which character, and where each request goes (whispers, channels, zone, ignore, mutes). No network or database: the self-check drives it directly
server/chat_server.* The network side: client connections (handshake, the hold until the character is online) and world links (secret, mutes on connect)
server/mute_store.* Mutes in MySQL, written on a worker thread
server/config.*, server/main.cpp Environment config and startup (migrations, mutes, TLS, JWKS)
migrations/ NNN_name.sql for kast_chat, applied in order at startup (schema_migrations)
tests/self_check.cpp chat_self_check (ctest)
../world/service_core.cmake What it shares with the world server, compiled from services/world: kast_protocol (frames and messages) and kast_service_core (TLS sessions, JWT/JWKS verification, sanitize_chat, WindowLimiter, mutes, env config and logging, MySQL and the migration runner)
