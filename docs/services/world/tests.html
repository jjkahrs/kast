Tests

ctest --preset debug, release and linux-release (the Docker build) run only the correctness tests. The performance tests carry LABELS perf and run with ctest --preset perf (Release) or perf-linux: log_bench, aoi_bench, activation_bench, map_threads_bench and world_timing_bench. A speed limit depends on what else the machine runs, so it never fails a build. world_timing_bench is world_self_check --timing: the self-check with its timing checks' speed limits on (replication idle tick, kast.query, the Lua bridge; Release only). Without --timing they print their numbers and check only behaviour.

  • Self-check (tests/self_check.cpp + tests/lua_checks.cpp, ctest world_self_check): assert-style checks of the pure logic with an injected clock, so nothing sleeps (except the send fan-out check: net::send_many to five sessions on unconnected sockets encodes the message once and leaves exactly proto::encode of it in each one's send buffer, also through the lag simulator, whose timers it waits a few ms for). The Lua checks write their scripts to a temp folder and drive a World with captured sends, saves and log lines. A batching check moves 3 players and a script NPC in view of 2 still players and asserts each of the 5 gets exactly one EntityMoves with every other mover's move and never its own, and that a lone player gets none (it fails if replication goes back to a message per mover). The codec checks round-trip EntityMoves empty, with two entries and full (kMaxEntries, which must fit one frame), and reject a cut entry, a count past the payload, bytes past the count and a NaN position. They cover the event bus (the engine's cases), kast.publish/subscribe/unsubscribe and the client sends: audiences, order, rejections and timing. They also cover state machines, from definitions to C++ / Lua parity, and Lua logging (kast.debug, fields tables, their errors, LOG_LEVEL). Log lines are written by a background thread, so the checks call log::flush() before reading what they captured.
  • AOI differential check (self_check.cpp, checkAoiDifferential): seeded random worlds (20 seeds × 400 ticks; players and NPCs on 3 maps, moves within a cell and across cells, logins and logouts, NPC create / destroy, transfers before and after the aoi pass, Lua-style moves after it, idle ticks) run through the old full recompute (kept in the test) and through aoi_system, which skips players with no touched cell near. After every tick each session's messages (encoded, in order), every Visible.ids / Visible.entered and every NPC's Viewers must be identical; it prints how often each event kind ran and fails if any ran 100 times or fewer. Leaving out any touch (for example the one for a move within a cell) fails it.
  • Instance checks (lua_checks.cpp, checkInstanceManifests, checkInstances, checkInstanceKeyErrors; Instances): the map.json fields and every refusal (field and file named), the exit checks in Maps::load; no copy at startup; same key one copy, another key or none a new one, each with its own Bat and Lua (init / shutdown, kast.map.instance()); instance = skipping the hook; a full copy refused (kast.transfer false, instance.full, no MapChange) and the C++ transfer too; relog into a live copy, a full one, a gone one and an old row; the empty timer with the injected clock (cancelled by re-entry, firing at 10 s, emptyTimeoutSec 0 at the next serial point); the Lua refusals (kast.world.post to an instance map, kast.create onto one, bad keys); 600 copies made and destroyed in a row (their entity ids recycled); instanceKey errors disabling only that system. world_self_check --instance-bench prints the median cost to make and destroy a copy with the sample lua/.
  • Parallel differential check (self_check.cpp, checkParallelDifferential; Threading): seeded random worlds (20 seeds × 400 ticks) on 4 maps, each run in two Worlds, one with MAP_THREADS=1 and one with 4, driven alike: logins (some next to a map's portal) and logouts, moves (a few speedhacks, so Corrections), says and yells, client events, C++ transfers and NPC creates / destroys between ticks, spawn-file NPCs that respawn, and a Lua system on its own seeded generator moving, creating (on its map and on others), destroying and transferring NPCs and players, setting an aoi component, posting to a map and to "all" (answered with a kast.broadcast), sending client events and changing a game machine, with MAX_NPCS 150 so the shares run out now and then. Map 5 is an instance map (maxPlayers 3, emptyTimeoutSec 1, a portal into it on every world map): the Lua system's instanceKey picks one of 3 keys or none, its kast.transfer passes instance =, the C++ transfers key copies too, logins come back saved in a live or long-gone copy, and instance.full is answered with a client event, so copies are made, filled, refused, rejoined and destroyed (hundreds of each). After every tick each session's messages (encoded, in order), the saves and the live contexts (map, instanceId, key, players, NPCs) must be byte-identical; it prints how often each kind ran and fails if any ran too rarely, or if the Lua system got disabled. world_self_check --parallel-stress N runs it over N seeds (the long race run). Two mutations were checked to fail it: entity ids from one pool behind a lock (a different session message at tick 17) and MAX_NPCS counted live across contexts (tick 136). checkConfig refuses MAP_THREADS 0, -1, -4, abc, 1.5, " 4" and 257.
  • Net thread handoff (self_check.cpp, checkNetHandoff): 8 real 127.0.0.1 TLS sessions accepted round-robin onto a 4-thread net::NetThreads, with the check's own thread as the game thread and the sessions' callbacks posting to it as GameServer's do. Every client writes 100 frames at once: each session's messages must reach the game thread in send order, and no callback may run on the game thread. One net::send_many from the game thread to all 8 must encode once (framesEncoded +1) and every client must receive exactly proto::encode of it. Then a client closes: the game thread keeps sending while the close races it, and after on_closed arrives a send, send_many and disconnect to that session must queue nothing (checked on its own net thread), and a queued send holding the last reference must run and then free the session. It prints one net threads: line. checkConfig refuses NET_THREADS 0, 65 and abc.
  • Parallel cost (ctest map_threads_bench, world_self_check --map-threads-bench): p50 and p95 World::tick ms over 300 ticks (after 50 to warm up) on the injected clock, the sample lua/ running, 4 maps of 4×4 tiles, each with 100 players moving 8 m/s and 100 patrolling spawn-file Guards, with MAP_THREADS=1 and 4. Prints the hardware thread count; fails if the 4-thread p95 is above 40% of the 1-thread p95. With fewer than 4 hardware threads, or in a Debug build (MSVC's checked STL and debug heap take process-wide locks: 4 threads measured at 140-230% of 1), it prints that the threshold was skipped instead; Release builds check it (ctest --preset perf or perf-linux).

  • Activation cost (ctest activation_bench, world_self_check --activation-bench): the median World::tick over 200 ticks (after 50 to warm up) on the injected clock, the sample lua/ running, 100 idle players on one tile of a 32×32 tile map, (a) alone and (b) with 10,000 patrolling spawn-file Guards on 100 tiles 9 or more tiles away.   • ThreadSanitizer (docker/tsan.override.yml, testing only): the Dockerfile's tsan stage builds kast_world and world_self_check with -fsanitize=thread as kast-world:tsan; the default image is unchanged. TSan needs a fixed address layout, so the image starts under setarch -R and the override runs it with seccomp:unconfined. docker compose -f docker-compose.yml -f docker/tsan.override.yml up -d --build world runs it; COMPOSE_FILE set to both files (;-separated on Windows) makes tests/integration.sh and tests/load.sh use it. Reports go to files in the tsan-reports volume, kept when the tests recreate world: docker compose run --rm --no-deps --entrypoint sh world -c 'cat /app/tsan/*' | grep -c "WARNING: ThreadSanitizer" must be 0. The self-check needs the source tree, so it runs in the build stage: docker build --target build-tsan -t kast-world:tsan-build ., then docker run --rm --security-opt seccomp=unconfined -w /src kast-world:tsan-build setarch x86_64 -R ./build/linux-release/world_self_check. Without the override, docker compose up -d --force-recreate world goes back to the default image.
  • Load (tests/load.sh):
    • Setup: recreates world (with the shell's MAP_THREADS, default 1, NET_THREADS, default 4, and MAX_CONNECTIONS, default COUNT + 100) so its totals cover only the test. It then runs COUNT bots in one process (8 io threads, 50 new connections per second) for DURATION s.
    • Across maps: MAPS=1,2,4,5 passes --maps to the bot: bot i heads for the i-th listed map (round robin, so COUNT spreads evenly). It enters on its saved map (START_MAP for a new character), walks at 9 m/s to the middle of the next portal on the shortest portal route there (read from --map-root's map.json and areas.json files), and once on its map wanders within the map's bounds, turning back 5 m before any portal area. tests/project/maps gives 4 flat maps for it: Start (1), Cave (2) and the test maps Plains (4) and Marsh (5), reached through Start's plains_gate and marsh_gate, about 320 m and 420 m west of the spawn point (Hills, 3, has terrain and a navmesh a wanderer would stray off). The gates are far from the spawn point, and at different distances, because a map's context starts on its first use and its Lua load takes one tick about 30 ms: gates next to the spawn would start every context in the login ramp's first 10 s window. The summary's on_target_map counts the bots that got there; every one must. Example: COUNT=400 MAPS=1,2,4,5 MAP_THREADS=4 bash tests/load.sh.
    • Across instance copies: an instance map in MAPS (the crypt, 6) spreads its bots over copies: every INSTANCE_SIZE of them (default the map's maxPlayers: 2) send the same instance key (the sample test_hooks.lua's client.test.instance_key) before walking to Start's crypt_gate, so each group gets its own copy; the summary's instance_keys counts the copies. Example: COUNT=200 MAPS=1,4,5,6 MAP_THREADS=4 bash tests/load.sh (25 copies).
    • Pass criteria:
      • Bot summary PASS: every bot entered the world (and, with MAPS, reached its map), with no errors, no unexpected disconnects and no Correction for honest movers. Without MAPS a wanderer that walks into the sample portal stops on the other map (map_changes_recv); the corrections for its moves still in flight are not counted.
      • Every 10 s window's tick p99 is under 25 ms, and so is the run total.
      • Zero failed save attempts.
      • Enter p99 under 500 ms: each bot times connect → EnterWorldOk (login, character list, create on a first run, enter); the summary has enter_ms_p50 and enter_ms_p99. The result also shows the saves lost on the graceful stop.
    • Net busy (information only): the result's net busy % worst window line has each net thread's highest busy_pct over the 10 s windows, and net busy % run total the net stats total line's (Operations).
