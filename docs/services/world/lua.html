Lua components and systems

Game developers define data components in Lua and write server-authoritative Lua systems that run on the 20 Hz tick and operate on player characters. The component file format is the engine's (Engine, Lua components), so a game project's components/ folder can be shared by the client and the server. The engine applies whatever the server replicates to the matching component on the local player and on remote clones (Engine, Online Services).

Layout

Path What
LUA_ROOT/components/**/*.lua Component definitions, scanned recursively, one type per file
LUA_ROOT/fsms/**/*.lua State machine definitions, scanned recursively, one machine per file
LUA_ROOT/items/**/*.lua Item definitions, scanned recursively, one item per file; the engine reads the same files (kast.items)
LUA_ROOT/npcs/**/*.lua NPC definitions, scanned recursively, one NPC type per file; server only (the engine never reads npcs/)
LUA_ROOT/systems/*.lua Systems, not recursive, run in alphabetical filename order
Any other folder Read only when a system asks: kast.definitions(folder). A dot-folder (.server/quests/) keeps game data out of a client build that shares the folder (the editor's Build leaves dot-folders out of game.pak)
  • LUA_ROOT: defaults to /app/lua. The image ships the sample from services/world/lua/ there, and compose bind-mounts ./lua over it.
  • Loading: files are loaded once at startup; there is no hot reload. After an edit, restart the server (docker compose restart world).
  • Errors refuse the start: an invalid component, state machine, item or NPC definition, an invalid system file, a GAME_STATE_MACHINES name with no valid definition, a spawn whose npc has no definition, or an error in a system's init stops the start. The server logs every error, not just the first, one Lua error line each. Each starts with the file path (and path:line for Lua errors); a startup failed: Lua line and exit status 1 follow.
  • No Lua is fine: a missing or empty LUA_ROOT means no custom components, state machines, NPC definitions or systems, with an info log. Spawn files then refuse the start: their npc names no definition.

Sharing with a game project: point the bind mount (or LUA_ROOT, when running on the host) at a folder whose components/ and fsms/ are the game project's. For example, change the volume to - ../../my-game:/app/lua:ro, which holds components/, fsms/, and the npcs/ and systems/ folders the client never reads. Client and server then read the same definition files.

Component definitions

Exactly the engine's format: return { name, displayName?, fields = {...} }.

  • Field types: float, int, bool, string, vec3, quat, enum, and array with of.
  • Field options: min, max, color, values, default.
  • Checks: the same strict key checks and error messages as the engine.

There are two more top-level keys. The engine accepts and checks both, but uses neither:

Key Values Default Meaning
persist true / false false Saved per character in MySQL (see Persistence below)
replicate "none" / "owner" / "aoi" "none" owner: sent to the owning player only. aoi: to the owner and every player who can see the character. none: never sent 
-- lua/components/health.lua (the sample)
return {
    name = "Health",
    persist = true,
    replicate = "aoi",
    fields = {
        { name = "current", type = "float", default = 100, min = 0 },
        { name = "max",     type = "float", default = 100, min = 1 },
        -- ...
    },
}
  • Invalid values: a bad persist or replicate is a definition error.
  • Reserved names: a definition may not be named Character, Npc, Transform or StateMachine (the built-ins), or after any server C++ component (Viewers, SessionLink, CharacterRef, MoveState, PendingMoves, PendingSay, ChatLimit, PendingClientEvents, ClientEventLimit, MoveLock, AoiCell, Visible, Moved, Dirty, SaveTimer, ReplicatedState, ScriptsLeft, PreservedComponents, ComponentData, StateMachineRuntime).
  • Duplicates: two files declaring the same name are both rejected, each error naming the other file, whatever the scan order.

Items

An item type is data: one file per item under LUA_ROOT/items/ (scanned recursively). The engine loads the game project's items/ with the same rules (Engine, kast.items), so a folder shared by client and server gives both the same names, stack sizes and qualities. NPC loot tables name items by id.

return {
    id = "bat_wing",                          -- unique across items/; a-z, 0-9 and _, at most 64 bytes
    name = "Bat Wing",                        -- shown to players; at most 255 bytes
    icon = "textures/icons/bat_wing.png",     -- project-relative image for clients; the server never opens it
    quality = "poor",                         -- poor, common, uncommon, rare or epic
    maxStack = 20,                            -- 1..1000
    sellPrice = 1,                            -- integer, 0..1000000000
    description = "A leathery wing.",         -- may be empty; at most 1024 bytes
}
  • Keys: exactly these seven, all required; any other key is an error.
  • Loading: once at startup, after fsms/ and before npcs/, in the definition sandbox. Every invalid file is one Lua error starting with its path (items/bat_wing.lua: "maxStack" must be an integer in [1, 1000]) and refuses the start. Two files with the same id are both rejected, each error naming the other file. A missing or empty items/ is fine.
  • In systems: kast.items is {[id] = {id =, name =, icon =, quality =, maxStack =, sellPrice =, description =}}, read-only all the way down (writing raises kast is read-only). What an item does is up to the systems; the starter-mmo sample's systems/inventory.lua keeps a bag of them.

Game data folders (kast.definitions)

A game's own data (quests, vendors, dialog...) can live in any folder under LUA_ROOT, one plain-data table per file, and a system reads it with kast.definitions(folder). The server gives the files no meaning: the system checks them.

local quests, paths = kast.definitions(".server/quests")
-- quests: {table, ...}, one per .lua file under LUA_ROOT/.server/quests (recursively), sorted by path
-- paths:  {".server/quests/bat_trouble.lua", ...}, LUA_ROOT-relative, for error messages
  • Folder: a relative, /-separated path without empty, . or .. parts and without \ or :, so it stays under LUA_ROOT; anything else raises kast.definitions: folder must be a relative path .... A missing folder returns two empty tables.
  • Files: each runs once in the definition sandbox and must return exactly one plain-data table (no functions or metatables). A file that fails raises kast.definitions: <path>: ... in the caller; called from init, that refuses the start like any init error.
  • Read once: the first call per folder reads the files; later calls (any system) return fresh copies of the same data, so a system may change what it gets. Call it from init: the files are not read again until restart.
  • Server-only data: the editor's Build leaves dot-folders out of game.pak, so a folder such as .server/quests/ in a project the client and server share never reaches players. The starter-mmo sample keeps its quests there (systems/quests.lua).

Systems

A system file returns a table; only update is required:

return {
    init = function() end,         -- at startup, after the file loaded; an error here refuses the start
    update = function(dt) end,     -- every tick; dt = 1 / TICK_HZ seconds
    shutdown = function() end,     -- graceful shutdown, before the final saves
    onEnter = function(e) end,     -- a character spawned; its persisted components are already restored (never an NPC)
    onLeave = function(e) end,     -- a character is leaving; changes made here are saved (never an NPC)
    validateCharacter = function(name, options) return true end, -- may this character be created? (see below)
}
  • One state, isolated files: the server has one Lua state, and each system file gets its own environment, so globals never leak between files.
  • Sandbox: the same as the engine's. Only base, table, string and math are open, with no io, os, ffi, debug, jit, package, require, loadfile, dofile, load or loadstring. Definition files are sandboxed too.
  • Runaway scripts: a callback that runs longer than 2 s raises an error, so an infinite loop disables its system instead of hanging the server.
  • Runtime errors: an error in any callback is logged as Lua system disabled, with the system, the callback and path:line. That system is then disabled until restart; the server and the other systems keep running.

The kast.* API has the engine's semantics and error messages, so a script behaves the same on client and server:

Function What
kast.query(names...) Iterator over entity ids with every listed component, in ascending id order. Captured when called: entities gone later in the loop are skipped
kast.items The item definitions by id, read-only
kast.definitions(folder) The plain-data tables returned by every .lua file under LUA_ROOT/folder, and their paths
kast.npcDef(name) A fresh copy of the NPC definition name: {name, template, loot} (loot nil without one); nil for an unknown name. A non-string name raises
kast.get(e, name) A fresh table of the component's fields; arrays are 1-based sequences, vec3/quat are {x=, y=, z=[, w=]}
kast.set(e, name, fields) Partial: listed fields change, the others keep their values. All-or-nothing: an unknown field, a wrong type, an out-of-range value or an unknown enum value raises an error and leaves the component unchanged
kast.has(e, name) / kast.add(e, name) / kast.remove(e, name) add uses the field defaults and does nothing if the component is present; remove does nothing if it is absent
kast.create(name, opts) Creates an NPC and returns its entity id; opts = {npc = string \| template = string, components = {...}?, map = id?, position = {x, y, z}?, heading = number?} (see NPCs)
kast.transfer(e, map, position [, heading]) Moves player or NPC e to position ({x, y, z}) on map map; heading defaults to the current one. Returns true, or false if this process does not own the destination (see Maps)
kast.destroy(e) Removes NPC e; the players who see it get Despawn
kast.setMovable(e, movable) false: the server refuses every Move from player e (one Correction back to where it stands per tick) until set true again. Not saved: a character logs in movable. Raises for an NPC (kast.setMovable: entity N is an NPC; only players send moves) and for a non-boolean
kast.debug/log/warn/error(msg [, fields]) A server log line <system path>: <msg> at debug, info, warn or error (LOG_LEVEL filters them; kast.debug shows only with LOG_LEVEL=debug). fields is a table of plain data, as an event payload, and becomes JSON fields after msg: kast.log("hit", {player = 7, zone = "x"}) logs {"ts":…,"level":"info","msg":"systems/a.lua: hit","player":7,"zone":"x"}; nested tables become nested JSON. Raises (at the script's file:line, naming the function, e.g. kast.log: fields must be a table, got 5) when fields is not a table, is a list, holds a function, userdata or thread, contains itself, or uses the reserved keys ts, level or msg. Never log tokens, passwords or chat text
kast.publish(name [, payload]) Queues an event on the server's event bus for the next drain (see Events)
kast.subscribe(name, fn) Calls fn(payload) for every later name event; returns a handle
kast.unsubscribe(handle) Removes the calling system's subscription; another system's or a stale handle does nothing
kast.sendTo(e, name [, payload]) Sends the event to character e's client only (an NPC has none: nothing is sent)
kast.sendNearby(e, name [, payload]) Sends the event to e's client and every client that currently sees e (the replicate = "aoi" audience)
kast.broadcast(name [, payload]) Sends the event to every player in the world, on every map
kast.fsm.state/change/canChange/states(target [, state]) Game and character state machines (see State machines)
kast.map.area(e) / kast.map.areaAt(map, x, y, z) The area e or a point is in: {id, name, flags, music} or nil (see Areas)
kast.map.spawn(map) The map's spawn point (map.json "spawn"): {position = {x, y, z}, heading}. Raises on an unloaded map
kast.map.ground(map, x, z) The ground's height at a point on loaded map map, or nil off its tiles (see Ground). Raises on an unloaded map
kast.map.path(map, from, to) The navmesh path between two {x, y, z} points: a list of {x, y, z}, or nil (see Navmesh). Raises on an unloaded map or a bad point
  • Entities: an entity is a player character's or an NPC's server wire id, the integer clients see as entityId. kast.query("Character") finds the players, kast.query("Npc") the NPCs, and kast.query() both.
  • kast is read-only: assigning to it raises an error.
  • Read-only built-ins: every character has Character and Transform, every NPC Npc and Transform, and an NPC from a spawn file also Spawn. get, has and query work on them; set and add raise "<name>" is read-only on the server, and remove raises "<name>" cannot be removed. The one exception is set on an NPC's Transform (see NPCs).
  • Writable built-in: StateMachine (machine, initialState, both strings) works with every function, like a Lua component that is never persisted or replicated (see State machines).
Name Fields
Character charId, name, options (the creation options, {key = value, ...}, empty for none; players only)
Npc name, template, npc (its NPC definition, "" if made with template; NPCs only)
Spawn id, pos = {x, y, z}, heading (the spawn file's values; y is not clamped to the ground), and with a path path = {{x, y, z}, ...}, wait (seconds), loop (NPCs from a spawn file only; see NPC spawns)
Transform position = {x, y, z}, heading (radians), map (id, read-only). A player moves only by the validated client movement, an NPC only by kast.set; either changes map only by kast.transfer
StateMachine machine, initialState (writable; added by kast.add, an NPC definition or kast.create's components)

Character creation

A client may create a character with options, string pairs the game defines (kast.world.createCharacter(name, {class = "mage"})). The engine and the protocol only carry them. The server checks, in this order:

  1. C++ limits: at most 8 options, keys of 1–16 characters of [a-z_], values of at most 32 printable ASCII characters. Anything else is CharError{options_invalid}, and no Lua runs.
  2. The Lua hook: every enabled system that returns a validateCharacter function is called with the name and a fresh table of the options. Each must return exactly true; anything else (false, nil, any other value) refuses the character with options_invalid. An error refuses it too, and disables that system like an error in any callback.
  3. No hook: when no system defines validateCharacter (the default services/world/lua), empty options create the character as before and any option is refused with options_invalid.

Then the usual rules (name taken, character limit) apply. Accepted options are saved with the character (the options column, migration 004_character_options.sql) and return in every character list. In the world, kast.get(e, "Character").options holds them, typically read in onEnter to set up a component. A character created before migration 004 has empty options.

-- samples/starter-mmo/systems/classes.lua (shortened)
local CLASSES = {warrior = {maxHealth = 140}, mage = {maxHealth = 80}, priest = {maxHealth = 90}, rogue = {maxHealth = 110}}
return {
    validateCharacter = function(name, options)
        for key in pairs(options) do
            if key ~= "class" then return false end
        end
        return CLASSES[options.class] ~= nil
    end,
    onEnter = function(e)
        if not kast.has(e, "Class") then -- a persisted component: set once, from the creation options
            local wanted = kast.get(e, "Character").options.class
            kast.add(e, "Class")
            kast.set(e, "Class", {id = CLASSES[wanted] and wanted or "warrior"})
        end
    end,
    update = function(dt) end,
}

The hook runs on the server's game thread while the request is answered, so keep it to checks on its arguments.

Tick order

Each tick runs, in this order:

  1. movement
  2. areas: area.leave / area.enter for players that moved, and portal transfers (Areas)
  3. AOI (Spawn / Despawn)
  4. chat
  5. client events in: each character's ClientEvents published on the bus as client.<name> (Client events)
  6. spawner: the NPC spawns that are due
  7. Lua update, every system in filename order
  8. event drain: the events queued since the last drain go to their subscribers
  9. replication (EntityMove)
  10. component replication
  11. events to clients: ServerEvent for every kast.sendTo / sendNearby / broadcast since the last flush
  12. save
  13. end of tick

Lua sees this tick's validated positions. Its changes are replicated and become eligible for saving in the same tick. An NPC that Lua creates, or moves into or out of a player's view, gets its Spawn / Despawn at the next tick's step 3.

Lifecycle hooks run at these points:

Event Hooks
EnterWorld Spawn, restore the persisted components, then onEnter
Logout, disconnect or duplicate-login kick onLeave and its client events, then the save and the despawn
Graceful shutdown onLeave for every character, then every system's shutdown, then their client events, then the saves and despawns. Undelivered bus events are dropped

Client events

A client sends an event to the server's Lua with the engine's kast.world.send(name, data) (Engine, Online Services; wire format in protocol). Systems receive it on the bus as client.<name>:

kast.subscribe("client.combat.power", function(e)
    -- e.entity: the sender's character entity id; e.data: the client's JSON object as a table
    local target = e.data.target
    if type(target) ~= "number" or not kast.has(target, "Npc") then return end
    -- ...
end)
  • Payload: {entity = <sender's character entity id>, data = <the JSON object as a table>}. entity is set by the server and always the sender.
  • Untrusted: data is whatever the client sent. Check every field's type and every claim (range, cooldown, ownership) before acting on it (Security, Client events).
  • Timing: published after chat (tick order step 5) and delivered by the event drain right after that tick's Lua update, in arrival order.
  • Limits: name 1–32 characters of a-z0-9._, at most 1 KB of JSON, 10 per second per character; the rest are dropped (protocol).

Persistence

  • Storage: components with persist = true are stored in characters.components, a JSON column added by migrations/002_character_components.sql. It holds {"<Name>": {...}, ...} in the replication encoding.
  • When they are saved: with the position, through the existing save flow on the DB worker. That means on logout/disconnect and on graceful shutdown. Every kast.set / add / remove that changes a persisted component marks the character dirty, so the SAVE_INTERVAL_MS save picks it up. The tick never waits on MySQL.
  • Loading (drift rules, as in the engine): a missing field gets its default, an unknown field is dropped, and a wrong-typed or out-of-range value is reset to its default. Each fix logs a persisted component fixed on load warning naming the character and field.
  • No data loss: column entries with no current definition, or whose definition is no longer persist, are kept verbatim and written back unchanged on every save. A column that isn't a JSON object is never overwritten (and nothing is restored from it).

Replication

ComponentUpdate and ComponentRemove are described in protocol.

  • What is sent: after the Lua systems run, every owner / aoi component that was added, changed or removed since it was last sent. The diff is per component against the last sent JSON, so unchanged components are never resent.
  • Full sets: the owner gets its full set on the first tick in the world. A viewer gets an entity's full aoi set when the entity comes into view, right after its Spawn.
  • NPCs: the same rules without an owner: aoi components go to the players who see the NPC, owner ones to nobody.
  • Ordering: data never precedes Spawn or follows Despawn.
  • Client writes: there are none. A client that sends a component message is disconnected with unexpected_message. Clients ask for changes with client events, which a system checks and applies.

Sample

The lua/ folder holds the sample:

File What
components/health.lua Health: persist, replicate = "aoi", every field type. The same file as tests/project/components/health.lua
components/wallet.lua Wallet { gold }: persist, replicate = "owner"
fsms/locomotion.lua Character machine idle / moving, each enterable only from the other. Every enter sends the owner fsm.state {machine, from, to} (kast.sendTo)
fsms/zone_cycle.lua Game machine day / night (listed in GAME_STATE_MACHINES). enter only logs
fsms/patrol.lua NPC machine walking / waiting, each enterable only from the other. No callbacks: it only records the phase
npcs/guard.lua, npcs/sentry.lua NPC definitions "Guard" and "Sentry" (template Guard): Health data and StateMachine with patrol
npcs/bat.lua NPC definition "Bat" (template Guard): Health data, no machine
systems/locomotion.lua onEnter adds StateMachine with locomotion, which enters idle, then tries idle again: denied by allowedFrom, a warning and no event. update switches to moving when the character's Transform changes and back to idle after 1 s standing still. It flips zone_cycle every 5 minutes if it is listed. It sends only on transitions, never per tick
systems/events.lua On login, sends the player welcome (sendTo) and publishes player.entered on the bus. Its subscriber runs on the next tick, after the newcomer's Spawn, and sends player.arrived to the newcomer and everyone who sees it (sendNearby). On logout, sends every player player.left (broadcast) before the Despawn. It sends only on login and logout, never per tick. It also subscribes to area.enter / area.leave and logs each (area.enter entity 5 map 1 area goldshire (Goldshire) flags {noMount=false, pvp=true})
systems/npcs.lua Patrols every NPC whose Spawn has a path (its definition gives it the patrol machine): it walks it at 3 m/s to each point in turn, facing where it goes, and waits the path's wait at each (loop, or back along the path). While walking it costs one EntityMove per tick per viewer. No NPCs or waypoints of its own: the sample maps' spawn files place the "Guard" (npc Guard, tests/project/maps/start/.server/spawns/4_4.json: respawn 5 s, a 20 m square around the spawn point, 2 s waits), the "Sentry" on the hills and a still "Bat" (never respawns) at map 2's spawn point, the far side of the sample portal
systems/test_hooks.lua Test only. Scenario 18: a character whose name starts with Respawntest destroys the Guard (spawn guard_1) when it enters. Scenarios 21 and 22: every client.test.echo goes back to its sender as test.echo {n, entity}. Remove it from a real game
systems/regen.lua onEnter adds Health and Wallet if absent and pays 1 gold per login. Once a second per character, each on its own phase, update regenerates Health.current toward max (+2) if the character stood still, or drains it by 0.5 per metre moved (Transform deltas). It keeps whole points and writes only on a change, so a character costs at most one ComponentUpdate a second per viewer

Keep replicated components quiet. Each change goes out in full to the owner and everyone in view. A component written every tick costs one message per tick per viewer, and in a crowd that is N² messages. An earlier sample that updated Health every tick made the 500-bot load test drop 378 clients on the 1 MiB send-buffer cap while they crowded the spawn point. Write replicated values at the rate clients need, and only when they change.
