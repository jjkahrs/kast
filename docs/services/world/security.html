Security behaviour

TLS

  • Protocol: TLS 1.2 or later only.
  • Production: set TLS_CERT_FILE and TLS_KEY_FILE.
  • Dev certificate: without them, the server generates a self-signed dev cert once and logs a warning (the same idea as auth's dev signing key). TLS_DEV_CERT_DIR is gitignored.
  • Bot verification: the bot checks the server certificate and host name against the file passed with --ca (/certs/server.crt in compose).
  • No downgrade: a client that never completes TLS is closed when the handshake deadline expires. Plain TCP never gets a game message.

Token verification

The server follows the "Verifying access tokens from the World Server" section of the Auth Server docs:

  • Algorithm: alg must be RS256, so none and HS* are rejected. HS256 signed with the public key (key confusion) is rejected too.
  • Key selection:
    • The key is chosen by the kid header from the cached JWKS.
    • The JWKS is refreshed after 300 s.
    • An unknown kid refetches the JWKS once, at most every JWKS_MIN_REFETCH_SECONDS, so random kids can't hammer auth.
  • Claims:
    • iss and aud must match the config.
    • exp is required, with JWT_CLOCK_SKEW_SECONDS of leeway.
    • sub must be a decimal account id.
    • role must be player, gm or admin.
  • Auth unreachable: if the JWKS can't be fetched, the client gets service_unavailable.
  • Off the game thread: verification and the JWKS fetch run on their own thread, never on the game thread.
  • Logging: tokens are never logged, and neither are passwords. Chat text is never logged at info or above; at debug level only its byte length is.

Ban gap

  • When the token is checked: only at the handshake. A session then lasts until disconnect.
  • Effect: a player banned in auth keeps playing until they disconnect. They can't log in again once their access token expires, at most 15 minutes after it was issued, because auth revokes the refresh tokens immediately.
  • Closing the gap: this needs a ban/revocation endpoint in auth that the world polls or subscribes to. Neither exists yet.
  • Role changes: a role change also only applies at the next login.

Abuse limits

All of these are configurable; see the protocol for the exact rules.

  • Frames: maximum frame size, handshake deadline and idle timeout.
  • Messages: the per-connection message rate, with disconnect on sustained excess, and one character request in flight at a time.
  • Movement: bounds, speed and the ground (no flying), with Correction. Rejected moves are never replicated.
  • Chat: size limit, UTF-8 validation, control-character stripping and the 5 per 10 s rate limit, for say, yell and emote alike. A yell's reach is capped by CHAT_YELL_RADIUS; a character the chat service muted is dropped with a notice (Chat link).
  • Client events: name, size and JSON-object checks, and 10 per second per character (not configurable; see Client events).
  • Connections: a connection limit and a send-buffer cap for clients that stop reading.
  • Malformed input: an unknown opcode, a bad length or a decode failure disconnects the client with a reason code.

Chat link

The world server is the client end of the chat service's internal link (CHAT_LINK_HOST):

  • TLS, verified: the chat service's certificate must chain to CHAT_LINK_CA_FILE (default: this server's own certificate, which the dev stack shares) and name CHAT_LINK_HOST.
  • Shared secret: LinkHello carries CHAT_LINK_SECRET (16+ characters), never logged. A wrong secret is refused with Disconnect{invalid_token}, logged as chat link: refused by the chat service, and retried with backoff.
  • What crosses it: account id, character id, name and map of each character in the world, and the mutes back. No chat text, no tokens.
  • Mutes: the chat service decides them (GM / admin role from their JWT); the world only applies them to say, yell and emote. A link (re)connect replaces the whole list.
  • Failure: the world runs as before without the link: proximity chat keeps working, mutes already received stay until they end.

Admin port

The admin service asks each world server who is online and kicks sessions through its admin port (WORLD_ADMIN_*, configuration):

  • Off unless configured: without WORLD_ADMIN_SECRET nothing listens, and the start logs admin port off: WORLD_ADMIN_SECRET is not set.
  • Internal only: it binds WORLD_ADMIN_HOST, 127.0.0.1 by default. The compose stack binds 0.0.0.0 inside the container and does not publish the port, so only containers on the compose network reach it. Never expose it publicly.
  • TLS: the server's own certificate and TLS context, as for game clients. The dev certificate names localhost, world, chat and 127.0.0.1; the admin service trusts it as a CA file.
  • Shared secret: the first message must be LinkHello carrying WORLD_ADMIN_SECRET (16+ characters). It is compared in constant time (CRYPTO_memcmp, after a length check). A wrong secret is logged as admin port refused: wrong secret (session and remote address, never the secret) and the connection is closed with Disconnect{invalid_token}. Anything else before the hello: Disconnect{unexpected_message}.
  • Limits: at most 32 admin connections at once (more get server_full), and the game clients' frame size, handshake deadline, idle timeout and message rate.
  • Kicks: logged with the account, character, reason and admin address. A kicked character leaves the world exactly as on a duplicate login, so it is saved; the client gets Disconnect{kicked}. The reason text stays in the world's log.
  • Thread safety: the listener runs on the io thread with the game loop, so the online list and kicks never race the tick.

Client events

ClientEvent (kast.world.send on the client) is the only way a client talks to the server's Lua systems. The rules are in the protocol.

  • Validation: the server re-checks every event: a name of 1–32 characters of a-z0-9._, at most 1 KB of JSON, and JSON that parses to an object. Anything else is a malformed frame: Disconnect{malformed}, logged as client event rejected with the session and byte count.
  • Rate limit: 10 per second per character. Excess events are dropped silently and counted; the count is logged as client events dropped {char, count} when the character leaves. The per-connection message rate applies too.
  • Handlers must validate data: only entity (the sender) is set by the server; data is whatever the client sent. The client asks, the server decides. The starter-mmo sample's systems/combat.lua checks, on the server, that target is a number naming an NPC with Health, that the target and the attacker are alive, that the cooldown has passed and that the target is on the attacker's map within range. The damage is the server's own constant: the client never decides it. A refused attack only sends the attacker combat.rejected {reason}.
  • Locked movement: kast.setMovable(e, false) (a MoveLock on the character) makes the movement step refuse every Move from that player with a Correction back to where it stands. The sample uses it for dead players, so a modified client can't walk while dead. It is not saved: the sample's combat.lua kills a character that logged out dead again on login.

TRUST_PROXY (test only)

  • What it does: the test compose sets TRUST_PROXY=true on auth. Every bot sends its own X-Forwarded-For address, so auth's per-IP limits (register 5/h, login 20/min) apply per bot. That lets one harness register, verify and log in 500+ accounts.
  • Never in production: don't set it on an auth service that clients can reach without a trusted proxy in front of it. Anyone could then forge their IP and bypass the limits.
  • Auth's key in scenario 8: the test bot also mounts auth's key volume read-only and runs as root for that one scenario. It uses the key to mint an expired but correctly signed token. This is test-only too.
