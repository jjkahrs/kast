Maps

The world is a set of maps (continents, dungeons), all run by this one process. A map is seamless inside; maps are joined only by transfers. Players and NPCs on different maps never see each other, even at the same x/z.

<MAP_ROOT>/<folder>/map.json        one folder per map; dot-folders (.server/) are skipped
<MAP_ROOT>/<folder>/areas.json      optional: the map's named areas (see Areas)
<MAP_ROOT>/<folder>/heights/<tx>_<tz>.r16|.png   optional: tile heightmaps (docs/engine/terrain.html; see Ground)
<MAP_ROOT>/<folder>/.server/spawns/<tx>_<tz>.json   optional, server only: the NPCs a tile places (see NPC spawns)
<MAP_ROOT>/<folder>/.server/nav/<tx>_<tz>.navtile   optional, server only: the tile's baked navmesh (see Navmesh)

{ "version": 1, "id": 1, "name": "Eastlands",
  "tiles": [[0, 0, 7, 7]],
  "heightRange": [-100, 500],
  "spawn": {"pos": [1024, 0, 1024], "heading": 0},
  "material": "materials/terrain_grass.mat",
  "nav": {"agentRadius": 0.4, "agentHeight": 1.8, "maxClimb": 0.5, "maxSlopeDeg": 45, "cellSize": 0.5} }
  • Tiles: a map is made of 256 m tiles; tile (tx, tz) = (floor(x / 256), floor(z / 256)), so x = 256 is tile 1. The map's origin is the corner of tile (0, 0). tiles lists inclusive rectangles [x0, z0, x1, z1]; the map is their union, and negative tiles are fine.
  • Identity: id (0-65535) is what the database, the wire and Lua use. It must be unique across maps; the folder name only locates the files. version must be 1.
  • Required: version, id, tiles and spawn.pos (on a declared tile). name, spawn.heading, heightRange, material and nav are optional. The game client's terrain uses heightRange, material and nav.maxSlopeDeg (Engine, Terrain); the server uses heightRange and the heightmaps for the ground. map/heights.h (heightmap decoding and the shared ground triangles) is part of kast_map, so the server build needs vcpkg's stb.
  • Startup: every map is loaded and logged (maps loaded). Any bad manifest (with the file and the problem, such as maps/cave/map.json: tiles[0]: x0 <= x1 and z0 <= z1 required), a duplicate id, no maps, a missing START_MAP, or a spawn y outside MIN_Y/MAX_Y refuses the start.
  • Bounds: a move onto a tile the map does not declare is rejected with Correction.
  • Characters: characters.map_id (migrations/003_character_map.sql) is saved with the position. On enter, a map that is no longer loaded, or a position no longer on its map, puts the character at START_MAP's spawn (logged). Rows from before the migration have map_id 0, read as START_MAP with their position kept.
  • Transfers: World::transfer(e, {map, pos, heading}) (and kast.transfer from Lua) is the only way to change map, for players and NPCs alike, and also teleports within a map. It moves the entity at once, resets a player's move budget and sends it MapChange, then Despawn for its old neighbours, who get its Despawn. The next interest pass sends the Spawns at the destination: in the same tick for a portal, the next tick for kast.transfer. So MapChange always reaches the client first (protocol).
  • Ownership: a transfer to a tile this process does not own is refused and logged. Every loaded tile is owned for now; the check is the seam for running maps in several processes later.

Ground

The server has no physics engine; it knows the ground from the same heightmaps the client stands on.

  • Loading: at startup, each owned tile's heights/<tx>_<tz>.r16 (tried first) or .png is decoded with kast_map's decode_heights. A tile without a file is flat at the map's heightMin (0 without heightRange). A file that fails to decode refuses the start (maps/hills/heights/0_0.png: png: 8-bit with 1 channel(s), need 16-bit grayscale).
  • Height: Maps::ground(map, x, z) is kast_map's ground_at: the triangle under the point, the same triangles as the client's Jolt heightfield, so client and server agree to within float rounding. Off the map's tiles it is empty.
  • Player moves: after the speed check, against the ground under the new position:
    • more than MOVE_GROUND_TOLERANCE (0.5 m) below it: accepted and lifted onto it;
    • more than MOVE_MAX_AIR (6 m) above it and not lower than the last position: rejected (Correction), so no flying or hovering;
    • lower than the last position: accepted, however high (falling).
  • Placement: NPCs always stand on the ground (kast.create, spawn files and kast.set of Transform ignore y). Transfers and portals put players and NPCs on the ground at the destination. A character saved under the ground (the heights changed since) enters on it.
  • Lua: kast.map.ground(map, x, z) is the height there, or nil off the map.

Navmesh

The ground says how high a player is, not whether they could have walked there. A map can carry a baked navmesh (Recast/Detour) of where its agents can walk; the server checks player moves against it and NPCs path on it.

  • Baking: kast_mapbake lints a map and bakes its navtiles: see the Map Bake docs.

  • Navtile format: a 12-byte little-endian header, {'KNAV', u32 version (1), u32 Detour DT_NAVMESH_VERSION (7)}, then the Detour tile from dtCreateNavMeshData for tile (tx, tz) (map/navtile.h).

  • Loading: at startup, each owned tile's navtile goes into one dtNavMesh per map (server/world/nav.cpp, the only file that includes Detour), sized for the map's declared tiles. A bad magic, an unknown navtile or Detour version, a tile baked for another tile, or too many polygons refuses the start with the file and the reason (maps/hills/.server/nav/0_0.navtile: navtile version 99, this server reads 1 (rebake with kast_mapbake)). A map without navtiles has no navmesh and keeps the Ground rules only.
  • Player moves: with MOVE_NAV_CHECK=1 (default), on a map with a navmesh, a move must end within 0.5 m across (the bake's agentRadius shrink at walkable edges) and MOVE_MAX_AIR up or down of a navmesh polygon. Otherwise the verdict is off_mesh and the client gets Correction at once, spending no move budget: walking up a cliff face or onto a slope steeper than maxSlopeDeg is snapped back. No grace period, so a player cannot drop off a cliff face either.
  • NPC paths: kast.map.path(map, from, to) ({x, y, z} tables) is the straight path along the navmesh: a list of {x, y, z} points from from snapped onto the mesh to to snapped onto it, with the corners between. It is nil when the map has no navmesh, either end is more than 2 m across (or 4 m up or down) from it, or to cannot be reached. The sample systems/npcs.lua walks these corners between a patrol's points, so the hills' Sentry goes round the mesa its route crosses.
  • Limits: Detour's poly refs are 32-bit here: tile bits + polygon bits <= 22, so a map of 1024 tiles allows 4096 polygons per tile (more tiles, fewer polygons). A navtile over the limit refuses the start; DT_POLYREF64 (Detour rebuilt) lifts it. No dynamic obstacles, off-mesh links (jumps, ladders) or static props in the bake, and the client does no pathing.
  • Sample: tests/project/maps/hills has a mesa (x 170-200, z 316-346, 25 m flat top, 81 degree walls) and the Sentry (.server/spawns/0_1.json) patrolling from (150, 331) to (215, 331), straight through it. Its baked navtiles are in .server/nav/; ctest mapbake_cli fails if they no longer match a fresh bake.
