Kast World Protocol

Protocol version: 9 (kProtocolVersion in protocol/messages.h, sent in Hello). A client on any other version gets protocol_mismatch.

Version Changes
9 Batched moves: EntityMove is replaced by EntityMoves (same opcode 0x0122), every move a viewer sees in a tick in one message. See Movement
8 Chat: Say and ChatMsg start with u8 kind (say, yell, emote); new ChatServer (0x012A) after EnterWorldOk; ChatNotice (0x0132) for a muted say; the chat service's messages (0x0030–0x0034, 0x0130–0x0132) and its internal link (0x0200–0x0205); new code no_character (26). See Proximity chat and Chat service protocol
7 Requests: ClientEvent gains u32 requestId; new Reply (0x0129)
6 Client prediction: Move gains u32 seq, u32 epoch; Correction gains u32 ackSeq, u32 epoch; MapChange gains u32 epoch
5 Zone objects: new Interact (0x0023). See Interact
4 Character creation options: CharCreate and CharInfo gain an options map; new code options_invalid (25). See Characters
3 Maps: EnterWorldOk gains u16 map after entityId; new MapChange (0x0128). See Maps
2 Spawn gains kind and template (NPCs)
1 First version

The encoder and decoder live in protocol/, a static library with no Asio, database or ECS dependency, so a game client can reuse it.

Transport

  • Connection: TLS (1.2 or later) over TCP. Default port 7777.
  • Dev certificate: with no certificate configured, the server generates a self-signed one with SANs localhost, world and 127.0.0.1. Clients trust it by loading that file as their CA.
  • Byte order: every integer is little-endian.
  • Floats: f32 is IEEE-754, written as its u32 bits. NaN and infinity are malformed.

Frame

+----------------+----------------+----------------------+
| u16 length     | u16 opcode     | payload (length B)   |
+----------------+----------------+----------------------+
  • length: the number of payload bytes, not counting the 4-byte header.
  • Size limit: a frame whose length is over MAX_FRAME_BYTES (default 4096) gets frame_too_large. The server checks this from the header, before reading the payload.
  • Exact payload: the payload must decode to exactly length bytes. Short fields, a string that runs past the end, trailing bytes, or a bad enum value all mean malformed.

Field types

Type Encoding
u8 / u16 / u32 / u64 Unsigned, little-endian
f32 IEEE-754 single precision, as u32 bits; must be finite
str u16 byte length + that many bytes (UTF-8 where noted)
vec3 f32 x, f32 y, f32 z. x/z is the ground plane; y is height

Handshake

client                                 server
  |---- TCP connect ----------------------->|   handshake deadline starts (HANDSHAKE_TIMEOUT_MS, 10 s)
  |<=== TLS handshake =====================>|
  |---- Hello{protocolVersion} ------------>|   mismatch -> Disconnect{protocol_mismatch}
  |---- Auth{accessToken} ----------------->|   JWT checked against auth's JWKS (security.html)
  |<--- AuthOk{accountId, role} ------------|   or Disconnect{invalid_token | token_expired | service_unavailable}
  |                                         |   deadline cleared
  |---- CharListReq / CharCreate / ... ---->|   lobby: character requests
  |<--- CharList / CharCreated / CharError -|
  |---- EnterWorld{charId} ---------------->|
  |<--- EnterWorldOk{entityId, map, ...} ---|   in world
  |---- Move / Say / ClientEvent ---------->|
  |<--- Spawn / Despawn / EntityMoves / ...|
  • Deadline: the whole handshake must finish within the deadline: TLS, Hello and Auth. Otherwise the server sends Disconnect{handshake_timeout}. A client that never starts TLS is simply closed, because there is no secure channel to send a reason on.
  • Message order:
    • Before AuthOk, only Hello and then Auth are accepted. Any other message gets Disconnect{unexpected_message}, and so does any message sent while the token is being verified.
    • In the lobby, Move, Say and ClientEvent are ignored.
    • In the world, a character request is answered with CharError{already_in_world}.
  • Token lifetime: the token is checked only at the handshake. The session then lasts until disconnect (see Security, Ban gap).
  • Duplicate login: a second login for an account that is already online kicks the old session with Disconnect{logged_in_elsewhere} and saves its character first.

Heartbeat

  • Server pings: the server sends Ping{nonce} every PING_INTERVAL_MS (default 20 s). The client must answer Pong{nonce}.
  • Client pings: a client may also send Ping, and the server answers Pong.
  • Idle timeout: a connection that sends nothing for IDLE_TIMEOUT_MS (default 60 s) gets Disconnect{idle_timeout}.

Abuse limits

  • Message rate: each connection is rate limited to MSG_RATE_PER_SEC messages per second (default 60), with bursts up to MSG_BURST (default 120).
    • Messages over the limit are dropped.
    • A sender that stays over the limit for MSG_RATE_GRACE_MS (default 2 s) without recovering gets Disconnect{rate_limited}.
  • Character requests: one at a time per client. A request sent while another is in flight gets CharError{rate_limited}.
  • Send buffer: a client that stops reading and lets more than MAX_SEND_BUFFER_BYTES pile up is dropped without a reason.
  • Connection limit: a connection beyond MAX_CONNECTIONS completes TLS, then gets Disconnect{server_full}.

Messages

C = client to server, S = server to client, L = the internal link between a world server and the chat service, A = the world server's admin port (LinkHello / LinkOk open it too). "(chat)": a message of the chat service's own connection, never sent to or by the world server. "Payload" lists fields in wire order.

Characters

  • Name rules: CharCreate names are 3–16 ASCII letters (name_invalid otherwise).
  • Creation options: string pairs the game defines (a class, a look); the protocol and the engine only carry them. The server takes at most 8, each key 1–16 characters of [a-z_] and each value at most 32 printable ASCII characters (0x20–0x7E); anything else is options_invalid, before any Lua runs. Then the server Lua's validateCharacter decides (Lua: character creation); without one, only empty options pass. Accepted options are saved with the character (column options, migration 004) and come back in every CharInfo.
  • Uniqueness: names are unique per realm, case-insensitively (name_taken). A deleted character's name stays reserved.
  • Character limit: at most MAX_CHARS_PER_ACCOUNT (default 10) live characters per account per realm (char_limit).
  • Spawn point: new characters start on map START_MAP (default 1) at its map.json spawn.
  • Ownership: CharDelete (a soft delete) and EnterWorld only work on the caller's own live characters. Anything else gets not_found, whether the character doesn't exist, belongs to another account or is deleted.
  • Database down: every character request answers CharError{service_unavailable} while the database is down.

Movement

  • Sending moves: the client sends Move with its new position. The server validates it on the next tick (20 Hz).
  • Bounds:
    • x/z must be on a tile the player's map declares (see Maps); x = 256 is already tile 1.
    • y does not count toward speed. It is checked against the ground under the new x/z (Maps, Ground): more than MOVE_GROUND_TOLERANCE (0.5 m) below it is lifted onto it, and a move ending more than MOVE_MAX_AIR (6 m) above it is rejected unless it descends (falling is always allowed). Then y is clamped to [MIN_Y, MAX_Y].
  • Speed:
    • Budget: distance on the x/z plane is paid from a budget. It refills at MAX_SPEED + SPEED_TOLERANCE m/s (default 10 + 1) of server time and is capped at MOVE_BURST_SECONDS (default 1 s) of travel.
    • Effect: packet timing jitter is absorbed, but sustained speed can never exceed the limit.
    • Client clock: clientTimeMs is informational. The server only trusts its own clock.
  • Rejected moves: the move is dropped, the client gets one Correction per tick with its last valid position, and observers see nothing.
  • Accepted moves: go to observers in range, never back to the mover. Each tick a player gets one EntityMoves with every move it sees (players' and NPCs'), at the point in the tick where they are sent, or none if nothing it sees moved. A list longer than kMaxEntries goes as several in a row. This saves a message, an encode and a frame header per move, but the bytes are still 20 per move per viewer: O(movers × viewers) a tick. Quantized or delta-encoded entries, or a lower rate for far viewers, are the next step if bandwidth matters.

Interest management

  • Grid: a uniform grid with AOI_CELL_SIZE m cells (default 64). A player sees every other player and every NPC on the same map within AOI_VIEW_RADIUS m (default 128) on the x/z plane. Entities on other maps are never seen, whatever their x/z.
  • Updates: each tick, a player gets Spawn for anyone who came into range and Despawn for anyone who left, logged out or (an NPC) was destroyed.
  • Skip rule (server cost only): the grid remembers every cell touched since the last pass (a move in or between cells, a spawn, despawn, NPC create / destroy or transfer, including Lua NPC moves after the pass). A player whose view window covers no touched cell, its own included, keeps its view without a recompute; what clients get is exactly what a full recompute would send.
  • NPCs: server-side entities that Lua systems create, move and destroy (Lua components and systems). Their Spawn has kind 1 and the template the system chose; a client shows them however it likes (the engine clones the scene entity of that name). Their moves arrive in EntityMoves, like a player's. NPCs see nothing themselves.
  • Entity ids: entityId is valid only while the entity exists. A later entity may reuse its slot with a different id.

Maps

  • Model: the world is a set of maps (continents, dungeons), each made of 256 m tiles. Tile (tx, tz) holds x/z in [256 tx, 256 (tx + 1)); the map's origin is the corner of tile (0, 0). Coordinates: y up, metres, heading = atan2(dx, dz) (0 faces +z). A map is identified by its u16 id (map.json id, Maps).
  • Entering: EnterWorldOk.map is the map the character is on. Load it before showing the world.
  • MapChange: the server moved you (a portal, a script). Drop every remote entity you know, load map if it differs, and place yourself at pos / heading. It is sent at once, so it always arrives before the Despawns of your old neighbours and the Spawns of your new ones (both on the next tick). A Move you sent before it arrived is checked from the new position with an empty speed budget, so it gets Correction.
  • Others: a player who changes map is a plain Despawn to its old neighbours and a Spawn to its new ones.
  • Instances: every copy of an instance map has the map's id, so entering one is a MapChange to that id like any map change; the wire does not name the copy. A move from one copy to another of the same map (only through kast.transfer with another instance key) is a MapChange with the same map id: the client keeps the map loaded and places itself again, and the Despawns and Spawns swap the old copy's entities for the new one's. A transfer refused because the copy is full sends nothing.

Proximity chat (say, yell, emote)

The world server owns proximity chat; whispers, channels and the zone channel are the chat service's.

  • Delivery: Say{kind, text} goes to the sender and back as ChatMsg{kind, fromName, text}: say to everyone in view (the AOI audience), yell to every player on the same map within CHAT_YELL_RADIUS (default 300 m, x/z; it may reach past the view radius), emote to the say audience, shown as "Name text" (/me waves: "Alice waves").
  • Muted characters: while the chat service has the character muted (its MuteStates over the link), a say, yell or emote is dropped and the sender gets ChatNotice{muted, "", minutes left}. With the link down, the last mutes it sent stay in force until they end.
  • Where chat is: right after EnterWorldOk the server sends ChatServer{host, port} (when CHAT_PUBLIC_HOST is set); the client opens a second TLS connection there with the same access token. See Chat service protocol.
  • Size: the text must be valid UTF-8 and at most CHAT_MAX_BYTES (default 256) bytes.
  • Control characters: C0, DEL and C1 are stripped.
  • Rate limit: CHAT_RATE_COUNT per CHAT_RATE_WINDOW_MS (default 5 per 10 s). Rejected messages count toward it.
  • Rejected messages (invalid, too long or over the rate) are dropped silently. The chat service applies the same rules (the same code, sanitize_chat and WindowLimiter) and answers with a ChatNotice instead.

Client events

A client sends a named event to the server's Lua systems as ClientEvent (the engine's kast.world.send(name, data), Online services). It is client-to-server only and the reverse of Server events.

  • name: 1–32 characters of a-z, 0-9, . and _ (kClientEventNameMax, proto::valid_client_event_name), e.g. combat.power.
  • json: the payload as JSON, at most 1024 bytes (kClientEventJsonMax). It must parse to an object.
  • Validation: the server re-checks everything. A bad name, more than 1 KB, text that isn't JSON or JSON that isn't an object gets Disconnect{malformed}, like any other malformed frame.
  • Phase: only accepted in the world. In the lobby it is ignored, like a stale Move or Say.
  • Rate limit: 10 per 1 s window per character (WorldRules clientEventRateCount / clientEventRateWindow, not configurable). Events over the limit are dropped silently and counted; the count is logged as "client events dropped" {char, count} when the character leaves. This is on top of the connection's message rate.
  • Delivery: on the next tick, after chat and before the spawner and the Lua update, each event is published on the Lua bus as client.<name> with the payload {entity = <sender's character entity id>, data = <the object as a table>}, in arrival order. The bus drain right after that tick's Lua update delivers it (Lua, Client events).
  • Trust: data comes from the client. Handlers must check every field (Security, Client events).

Interact

A client activates an interactable zone object (a shrine, a lever) with Interact{u32 objectId}: the object's id from the map's objects/<tx>_<tz>.json (the engine's kast.interact(id), Engine, Terrain). Client-to-server only.

  • Check: on the next tick, the id must be an interactable of the player's current map (its .server/interactables entry, Maps, Objects) and the player within its range of the shape's edge, measured on the ground plane.
  • Accepted: the object's event is published on the server bus as {entity, map, object, data} (Events, Interactables).
  • Rejected (unknown id, another map's object, out of range): dropped silently, logged at debug level as interact rejected. There is no reply message; the game's Lua answers an accepted one if it wants to (with Server events).
  • Phase and limits: only accepted in the world (in the lobby it is ignored, like a stale Move), and counted by the connection's message rate.

Lua components

Game-defined Lua components (Lua components and systems) reach clients as these two messages. They are server-authoritative: there is no client-to-server component message, and a client that sends one gets Disconnect{unexpected_message}.

  • ComponentUpdate: the component's full value as a JSON object, in the engine's scene-file encoding:
    • fields in definition order, floats as the shortest decimal that reads back as the same f32, ints as integers;
    • vec3 / quat as arrays [x, y, z] / [x, y, z, w], enums by name, arrays as JSON arrays.
  • ComponentRemove: the entity no longer has the component.
  • Who gets them, by the definition's replicate key:
    • "owner": only the owning player's session. An NPC has no owner, so nobody.
    • "aoi": the owner and every session that currently sees the entity.
    • "none" (the default): never sent.
  • When: at most once per component per tick (20 Hz), after the Lua systems ran, and only if the value differs from what was last sent. Unchanged components are never resent.
    • The owner gets every replicated component it has on the first tick after EnterWorldOk.
    • A viewer gets every "aoi" component of an entity on the tick that entity comes into view, after its Spawn. That full set replaces the tick's changes for that viewer.
  • Ordering: for any entity, ComponentUpdate / ComponentRemove come after its Spawn (or the owner's EnterWorldOk) and never after its Despawn.
  • Size: a component whose frame would pass the u16 length limit (65535-byte payload) is not sent. The server logs an error once, until the value fits again.
  • Bandwidth: each change is sent in full. A component that changes every tick (e.g. regenerating health) costs one message per tick for each recipient.

Server events

A server Lua system sends a named event to clients with kast.sendTo, kast.sendNearby or kast.broadcast (Lua components and systems, Events). Each recipient gets one ServerEvent. It is server-to-client only: a client that sends one gets Disconnect{unexpected_message}.

  • name: the non-empty name the system chose, e.g. player.left. The engine publishes it as server.<name>.
  • json: the payload as compact JSON: any plain-data value (null when the system sent none). Bytes in Lua strings that aren't UTF-8 are replaced with U+FFFD.
  • Who gets it:
    • sendTo(e, ...): the session of character e. An NPC has no session: nobody.
    • sendNearby(e, ...): e's session and every session that currently sees e (the "aoi" audience). For an NPC, the sessions that see it.
    • broadcast(...): every player in the zone.
    • The audience is taken when the event is sent, not when the system queued it. A character no longer in the world gets nothing, and neither does anyone around it.
  • When: once per tick, after ComponentUpdate / ComponentRemove, in the order the systems queued them. So a client already has the Spawn and the latest component values of any entity the event refers to. Events queued in onLeave go out at the despawn, before that character's Despawn; events queued in onEnter go out on the next tick.
  • Ordering: no ServerEvent about or to an entity comes before its Spawn (or the owner's EnterWorldOk) or after its Despawn.
  • Size: the frame must fit the u16 length limit: 4 + name + json bytes at most 65535. A bigger event is rejected by the Lua call with an error; nothing is sent.
  • Bandwidth: each event is one message per recipient. broadcast reaches every player, so one call costs N messages in a zone of N players, and a call per player costs N².

Admin port

An internal TLS listener for the admin service (WORLD_ADMIN_HOST:WORLD_ADMIN_PORT, default 127.0.0.1:7780), on only when WORLD_ADMIN_SECRET is set (configuration, security). Same TLS context and certificate as the game port, same frames and field types; messages marked A in the table.

admin tool                               world server
  |---- TCP connect + TLS ------------------>|   handshake deadline (HANDSHAKE_TIMEOUT_MS)
  |---- LinkHello{protocolVersion, secret} ->|   wrong version -> Disconnect{protocol_mismatch}
  |                                          |   wrong secret  -> logged, Disconnect{invalid_token}
  |<--- LinkOk -------------------------------|   deadline cleared
  |---- AdminOnlineReq ---------------------->|
  |<--- AdminOnline{more=1, ...} -------------|   chunks of up to 1000 entries
  |<--- AdminOnline{more=0, ...} -------------|   last (or only, possibly empty) chunk
  |---- AdminKick{accountId | charId, reason}>|
  |<--- AdminKicked{kicked} ------------------|
  |---- AdminInstancesReq ------------------->|
  |<--- AdminInstances{more=1, ...} ----------|   chunks of up to 100 entries
  |<--- AdminInstances{more=0, ...} ----------|   last (or only) chunk
  • Hello: the first message must be LinkHello (the chat link's hello, 0x0200) with protocolVersion = the admin port's own version (kAdminProtocolVersion, 10; it was the game's 9 before the instance list) and secret = WORLD_ADMIN_SECRET. The game protocol and the chat link stay on kProtocolVersion (9). Anything else first gets Disconnect{unexpected_message}.
  • Requests: after LinkOk, any number of AdminOnlineReq, AdminKick and AdminInstancesReq, answered in order on the same connection. Any other message gets Disconnect{unexpected_message}; a bad payload Disconnect{malformed}.
  • Online list: every authenticated session. One in the lobby has charId 0, an empty name and map 0. connectedAtMs is when the TCP connection was accepted (Unix ms).
  • Kick: exactly one of accountId / charId is non-zero (both or neither: malformed). By account: every session of that account, lobby or world. By character: the session that has it in the world. Each one leaves the world as on a duplicate login (its save is queued), then gets Disconnect{kicked}. kicked counts them; 0 when nobody matched. The reason is logged, not sent to the player.
  • Instances: every live map context, in map then instance order: each world map's (instance 0, key empty) and every instance copy (its process-unique instanceId and its key, empty for a keyless copy). players and npcs are what it holds now, createdAtMs when it started (Unix ms), emptySinceMs when an empty copy's timer started (0: it has players, or a world map).
  • Heartbeat and limits: as for game clients: the server pings every PING_INTERVAL_MS and closes a connection idle for IDLE_TIMEOUT_MS; at most 32 admin connections (then server_full). One connection per request is fine.
