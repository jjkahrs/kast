Events

Each map context has its own event bus, with the engine's API and rules (Engine, Events), and so does the realm context. Systems use their map's to talk to each other, and server C++ can publish and subscribe through World::bus(map) (World::bus(): START_MAP's) and World::realm_bus(). Events never reach clients on their own: only the three send functions put anything on the network.

  • Between maps: kast.publish reaches only its own map's subscribers. kast.world.post(target, event, data) (Lua) reaches another map's bus, the realm's ("realm") or every running context's ("all"): it is published there at the end of the tick and delivered at the next tick's drain, in post order, with the payload {from = <map id or "realm">, data}. The game machines' fsm.changed and a portal's area.leave / area.enter go on the buses of the maps concerned (Map contexts).
  • Delivery: kast.publish only queues. The queue is drained once per tick, right after every system's update (step 6 below). Events are delivered in publish order, and each event's subscribers run in subscription order, C++ and Lua alike. Events published during the drain (by a subscriber), or from init, onEnter or onLeave, wait for the next tick's drain. A graceful shutdown drops the queue.
  • Payloads: plain data. That is nil, booleans, finite numbers, strings, and tables whose keys are exactly 1..n (arrays) or all strings (objects), nested at most 32 deep. Functions, userdata, threads, cycles, mixed keys, NaN and infinities raise an error at the call (kast.publish: payload.x must be a finite number), and nothing is queued. Every subscriber gets its own copy.
  • Names: non-empty strings. Anything else raises <function>: event name must be a non-empty string, got <value>.
  • Subscriptions belong to the calling system. When that system is disabled by any error, all of its subscriptions are removed. A failing subscriber is logged as Lua system disabled (callback event '<name>', with path:line), and the event's other subscribers still run.
  • Client events: kast.sendTo, kast.sendNearby and kast.broadcast take the same names and payloads. Each recipient gets a ServerEvent (protocol), and the engine publishes it on the client's bus as server.<name>.
    • When: sends are queued and go out in call order after component replication (step 8), so a client already has the Spawn and the latest component values. Sends from onLeave go out at the despawn, before that character's Despawn; sends from onEnter go out on the next tick.
    • Targets: a bad id (not a whole number from 0 to 2^32-1) raises kast.sendTo: invalid entity id <value>. A valid id whose character or NPC is not in the world when the events go out (it left meanwhile) sends nothing, and so does one on another map: kast.sendTo, sendNearby and reply reach the sender's map only. kast.broadcast reaches every map: its own map's players in call order, the other maps' at the end of the tick.
    • Size: an event whose frame would pass 65535 bytes raises kast.sendTo: event "<name>" is too large to send at the call.

Interactables

An interactable zone object (Maps, Objects) names the event its activation publishes. When a player's Interact (protocol) passes the server's checks (an interactable of the player's map, the player within its range), the server publishes that event on this bus, from C++, in the tick after the message arrived; the drain after that tick's Lua update delivers it:

-- maps/meadow/.server/interactables/0_0.json: {"id": 1, "event": "shrine.activated", "data": {"message": "..."}, ...}
kast.subscribe("shrine.activated", function(e)
    -- e.entity: the player's character; e.map: its map id; e.object: the interactable's id;
    -- e.data: the entry's "data" object, or nil if it has none
    kast.sendTo(e.entity, "shrine.blessing", {text = e.data and e.data.message or "The shrine hums."})
end)
  • One event per object, named in its file, so a game can give each shrine, lever or chest its own subscriber, or share one name and tell them apart by e.object.
  • Trust: everything in the payload comes from the server: the map files and the player's checked position. The client only chose the id.
  • State is the game's: the server keeps none (no cooldowns, no enabled flag, no "opened" door). A subscriber that wants a cooldown keeps it in Lua; nothing is replicated unless the subscriber sends it.
  • Rejections publish nothing and send nothing; they are logged at debug level (interact rejected).
  • Samples: samples/starter-mmo/systems/shrines.lua (the Meadow Shrine restores Health and answers shrine.blessing) and services/world/lua/systems/test_hooks.lua (the hills' Test Shrine answers test.shrine, for integration scenario 25).

Client events cost bandwidth. Each send is one message per recipient, and nothing rate-limits them: only the existing 1 MiB per-session send-buffer cap stops a flood, by disconnecting the client. broadcast reaches every player, so one call per player costs N² messages in a zone of N. sendNearby in a crowd costs about the same. Send on game events (a login, a kill, a quest step), never every tick.
