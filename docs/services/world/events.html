Events

The server has one event bus with the engine's API and rules (Engine, Events). Systems use it to talk to each other, and server C++ can publish and subscribe through World::bus(). Events never reach clients on their own: only the three send functions put anything on the network.

  • Delivery: kast.publish only queues. The queue is drained once per tick, right after every system's update (step 6 below). Events are delivered in publish order, and each event's subscribers run in subscription order, C++ and Lua alike. Events published during the drain (by a subscriber), or from init, onEnter or onLeave, wait for the next tick's drain. A graceful shutdown drops the queue.
  • Payloads: plain data. That is nil, booleans, finite numbers, strings, and tables whose keys are exactly 1..n (arrays) or all strings (objects), nested at most 32 deep. Functions, userdata, threads, cycles, mixed keys, NaN and infinities raise an error at the call (kast.publish: payload.x must be a finite number), and nothing is queued. Every subscriber gets its own copy.
  • Names: non-empty strings. Anything else raises <function>: event name must be a non-empty string, got <value>.
  • Subscriptions belong to the calling system. When that system is disabled by any error, all of its subscriptions are removed. A failing subscriber is logged as Lua system disabled (callback event '<name>', with path:line), and the event's other subscribers still run.
  • Client events: kast.sendTo, kast.sendNearby and kast.broadcast take the same names and payloads. Each recipient gets a ServerEvent (protocol), and the engine publishes it on the client's bus as server.<name>.
    • When: sends are queued and go out in call order after component replication (step 8), so a client already has the Spawn and the latest component values. Sends from onLeave go out at the despawn, before that character's Despawn; sends from onEnter go out on the next tick.
    • Targets: a bad id (not a whole number from 0 to 2^32-1) raises kast.sendTo: invalid entity id <value>. A valid id whose character or NPC is not in the world when the events go out (it left meanwhile) sends nothing.
    • Size: an event whose frame would pass 65535 bytes raises kast.sendTo: event "<name>" is too large to send at the call.

Client events cost bandwidth. Each send is one message per recipient, and nothing rate-limits them: only the existing 1 MiB per-session send-buffer cap stops a flood, by disconnecting the client. broadcast reaches every player, so one call per player costs N² messages in a zone of N. sendNearby in a crowd costs about the same. Send on game events (a login, a kill, a quest step), never every tick.
