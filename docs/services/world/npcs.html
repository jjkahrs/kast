NPCs

A system creates server-authoritative NPCs with kast.create, moves them by setting their Transform, and removes them with kast.destroy. Clients see them through the usual interest management: a player in range gets Spawn with kind npc and the NPC's template (protocol), then EntityMove as it moves, and Despawn when it leaves the view or is destroyed. The engine shows each one as a clone of the scene entity named after its template (Engine, Replication).

local guard = kast.create("Guard", {npc = "Guard", position = {x = 1034, y = 0, z = 1024}, heading = 0})
local boss = kast.create("Gate Boss", {npc = "Guard", components = {Health = {max = 500, current = 500}}})
local prop = kast.create("Crate", {template = "Crate"})            -- no definition, no components
kast.set(guard, "Transform", {position = {x = 1035, y = 0, z = 1024}}) -- one EntityMove to every player who sees it
kast.destroy(guard)                                                 -- Despawn to every player who sees it
  • kast.create(name, opts): name (the Npc.name clients see) must be a non-empty string of at most 255 bytes. opts needs exactly one of npc (an NPC definition's name: its template and components) and template (non-empty, at most 255 bytes; no components); both or neither raises (kast.create: opts needs exactly one of npc (an npcs/ definition) and template), as does an unknown npc. components has a definition's components shape and is merged per field over the definition's data (or over the field defaults with template), with the same checks (kast.create: "Health": "current" must be >= 0). map defaults to START_MAP and must be a loaded map's id. position ({x, y, z}, finite numbers) defaults to that map's spawn point and heading (radians) to 0. A position off the map is clamped to the nearest point on a declared tile, and y is the ground there (no flying NPCs). Any other key in opts, a bad value, or MAX_NPCS NPCs already in the world raises an error at the call and creates nothing. It works from init on; the components are there when it returns (a StateMachine has entered its initial state), and players in range get the Spawn on the next tick, followed by its aoi components.
  • kast.destroy(e): a player id (kast.destroy: entity 7 is a player; only NPCs can be destroyed), a stale id or an invalid id raises an error. A destroyed NPC's id is stale at once: kast.* on it raises invalid entity id.
  • Moving: kast.set(npc, "Transform", {position = {x, y, z}, heading = h}) is partial and all-or-nothing like any set, and clamps onto the NPC's map like create. map cannot be set ("Transform": "map" is read-only; use kast.transfer). Script moves are trusted: there is no speed check. A move goes out as EntityMove in the same tick, like an accepted player move. A move into or out of a player's view gives Spawn / Despawn on the next tick.
  • Components and machines: kast.add/set/get/has/remove, and StateMachine with kast.fsm.*, work on NPCs as on characters, whether the components came from a definition or a system. An aoi component reaches the players who see the NPC, an owner one nobody, and persist is ignored.
  • Events: kast.sendTo(npc, ...) sends nothing (no error); kast.sendNearby(npc, ...) reaches the players who see it. onEnter and onLeave never run for NPCs.
  • Ephemeral: NPCs are never saved and need no database. A restart starts without them: the spawn files and the systems' init create them again. A graceful shutdown removes them silently, after the players.

NPCs cost bandwidth like players. Each move is one EntityMove per tick to each player in view, so a crowd of walking NPCs around a crowd of players costs NPCs x players messages a tick. Move NPCs at the rate clients need and let the engine interpolate.

NPC definitions

An NPC type is data: one file per type under LUA_ROOT/npcs/ (scanned recursively), listing the Lua components every NPC of that type starts with. Spawn files (npc) and kast.create (opts.npc) make NPCs from them.

return {
    name = "Guard",          -- the NPC's Npc.name and Npc.npc
    template = "Guard",      -- the scene entity clients clone
    components = {           -- optional; omitted: none
        Health = { current = 50, max = 50 },   -- partial: unlisted fields take their defaults; {} is all defaults
        StateMachine = { machine = "patrol" }, -- enters "patrol"'s initial state when the NPC is created
    },
    loot = {                 -- optional: what a system may roll when it dies (see below)
        gold = { min = 5, max = 15 },
        items = { { item = "linen_cloth", chance = 0.6, min = 1, max = 2 } },
    },
}
  • Keys: name (unique across npcs/) and template are required, non-empty strings of at most 255 bytes; components and loot are optional. Any other key is an error.
  • Loot: gold = {min, max} (integers, 0 <= min <= max <= 1000000) and items, a sequence of {item, chance, min, max}: item an item definition's id, chance in (0, 1], 1 <= min <= max <= 1000000. Both parts are optional; other keys are errors. The server only checks and keeps it: systems read it with kast.npcDef(name).loot and decide when and how to roll it (the starter-mmo sample rolls it once at death, math.random, for the player who hit the NPC first).
  • Components: any Lua component, and the writable built-in StateMachine, whose machine must name a valid state machine. The read-only built-ins (Npc, Transform, Spawn, Character) and unknown names are errors. Field values are checked like kast.set (unknown field, wrong type, min/max, enum values, array elements).
  • Loading: once at startup, after fsms/ and items/ and before the systems' init, in the definition sandbox. Every invalid file is one Lua error starting with its path (npcs/guard.lua: "Health": unknown field "hp") and refuses the start. Two files with the same name are both rejected, each error naming the other file. A missing or empty npcs/ is fine.
  • When: an NPC gets its components when it is created, so the first Spawn a player gets is followed by its aoi components in the usual AOI-enter full set. A respawned NPC starts with fresh definition data. persist is ignored and owner components reach nobody, as for every NPC.
  • Friendly NPCs: the server has no hostile / friendly flag; what an NPC is depends on its components and the systems. The starter-mmo sample's convention: an NPC without Health is friendly. Its systems/combat.lua refuses any power aimed at an NPC without Health (target) and Frost Nova queries Npc + Health, so such an NPC never fights, is never hurt and never dies; with no loot it drops nothing. Clients see the same thing (no Health replicated) and don't target it (scripts/combat.lua). Its quest giver, npcs/elder.lua, is just {name = "Elder", template = "Elder"}, placed by the Meadow's spawn file without a path; systems/quests.lua makes it a quest giver because quests name it as their giver.

NPC spawns

A map's NPCs are data: one file per tile, <MAP_ROOT>/<folder>/.server/spawns/<tx>_<tz>.json. The dot-folder keeps it server only (the editor's Build leaves dot-folders out of game.pak).

{ "version": 2,
  "paths": {"gate_patrol": {"loop": true, "wait": 2,
            "points": [[1034, 0, 1034], [1034, 0, 1014], [1014, 0, 1014], [1014, 0, 1034]]}},
  "spawns": [
    {"id": "guard_1", "npc": "Guard", "pos": [1024, 0, 1024], "heading": 0, "respawnSec": 30, "path": "gate_patrol"}
  ]}
  • Version: version must be 2. A version 1 file (name / template per spawn) is rejected: replace both with npc.
  • Spawn: id (non-empty, unique on the map), npc (an NPC definition's name, at most 255 bytes: the NPC's name, template and components), pos and respawnSec are required; heading (radians) defaults to 0, path is optional. Any other key is an error. pos must lie inside the file's tile; its y is replaced by the ground there, like kast.create.
  • Respawn: respawnSec (0 to 31536000, a year) is how long after an NPC is destroyed (kast.destroy) the spawn places a new one, at pos again, as a new entity id, with fresh definition data. -1 never respawns.
  • Paths: named in the file's paths and used by its spawns. points (at least one [x, y, z]) is the route, wait (seconds, default 0) the pause at each point, and loop (default true) goes from the last point back to the first; false walks back along the route. The server does not move NPCs: a Lua system reads the path from the read-only Spawn component (kast.query("Spawn"), kast.get(e, "Spawn")). The sample systems/npcs.lua walks every NPC that has one, along kast.map.path between its points on a map with a navmesh. Spawn also holds the file's pos ({x, y, z}, y as written, not clamped to the ground) and heading, so a system can send an NPC home (the starter-mmo sample's systems/combat.lua walks a leashed NPC back to it and heals it there).
  • Loading: at startup, the spawn files of every tile this process owns (every tile, for now). A file name that is not <tx>_<tz>.json, a tile not on the map, an invalid file (each problem named, such as maps/start/.server/spawns/4_4.json: spawn "guard_1": "pos" is outside tile 4_4), an unknown path or an id used twice on a map refuses the start, and so does an npc with no definition, once LUA_ROOT is loaded (maps/start/.server/spawns/4_4.json: spawn "guard_1": unknown npc "Gaurd" (no definition in npcs/)). map::parse_spawns (the kast_map library) checks one file's shape without the server or Lua.
  • Spawning: every spawn is placed on the first tick, and each tick the spawner places the ones due, before the Lua update, so systems see them that tick; players get the Spawn on the next. They count toward MAX_NPCS: at the cap the due spawns wait (one warning, spawns deferred: MAX_NPCS reached) and go in once there is room. Every spawn is always active, near players or not.
