State machines

Server Lua and server C++ can drive finite state machines with the engine's definition files and rules (Engine, State machines). That section is the spec for the file format, validation and its messages, ctx, the transition rules, and the kast.fsm API. A game project's fsms/ folder can be shared with the server like components/. The port lives in server/lua/state_machines.* and server/lua/lua_state_machines.*.

  • Definitions: LUA_ROOT/fsms/**/*.lua, one machine per file, loaded once at startup before the systems' init. Each file runs in its own sandboxed environment with the full read-only kast API. kast.log from a callback is prefixed with the definition path (fsms/door.lua: ...). A missing fsms/ folder means no machines.
  • Game machines: GAME_STATE_MACHINES lists them by name. After every system's init, each enters its initial state: enter runs with ctx.from = nil, and no fsm.changed is published. A machine that kast.fsm.* touches during an init enters right then, once. Game machines run for the server's lifetime; shutdown runs no exit.
  • Character and NPC machines: use the writable built-in StateMachine (machine, initialState) through kast.add, kast.set, kast.get, kast.has, kast.remove and kast.query.
    • kast.add alone leaves machine empty: there is no machine yet, and kast.fsm.* on that character raises.
    • Setting machine enters that machine's initial state at once. That is initialState if it names a state, otherwise the definition's initial, with a warning. from is nil and no event is published.
    • Changing machine enters the new machine's initial state, with no exit of the old one. Changing only initialState does nothing. A machine with no valid definition is logged once.
    • Removal, logout and graceful shutdown just drop the machine, with no exit.
    • The typical use is a system's onEnter adding and setting it (see the sample).
  • Not persisted, not replicated: StateMachine and the current state never reach MySQL (the components column) or clients. A character starts its machine again from the initial state on every login. To tell clients about a transition, send it from enter (kast.sendTo / sendNearby).
  • Events: fsm.changed {machine, entity, from, to} goes on the server's event bus, with entity null for game machines and the publisher set to the definition path. It is delivered at the normal drain (see Events), so a transition made in update reaches subscribers in the same tick.
  • Callback errors: an error in enter or exit is logged as State machine fsms/door.lua: enter "open" failed: fsms/door.lua:5: ... with a traceback. The transition still commits and the machine stays usable; no system is disabled. A callback runs under the 2 s script budget of whatever entered Lua. When a system's kast.fsm.change triggers a runaway callback, the callback is stopped and logged, and then that system is disabled too, because they share one budget (as in the engine).
  • Misuse: every bad kast.fsm.* argument raises at the calling line, which a system callback treats like any other error (the system is disabled). An unknown state name passed to change is a denial (false and a warning).
  • Startup: a rejected fsms/ file or a GAME_STATE_MACHINES name with no valid definition refuses the start, like any other Lua error (one Lua error line each, startup failed: Lua, exit status 1). That also applies when LUA_ROOT is missing and GAME_STATE_MACHINES is set.
  • C++: World::fsm() (lua::StateMachines, also Runtime::fsm()) gives state, change, canChange and states for a game machine name or a character or NPC wire id. It applies the same rules, events and logging as kast.fsm, and a bad target throws std::invalid_argument.
  • Not on the server: hot reload, scenes and kast.loadScene, the editor's panels.
lua::StateMachines& fsm = world.fsm();
std::string phase = fsm.state("zone_cycle");          // a game machine by name
bool moved = fsm.change(lua::EntityId{7}, "moving");  // a character's machine by wire id
