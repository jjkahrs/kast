Security behaviour

Sessions (backend-for-frontend)

  • Sign-in goes through auth's /v1/auth/login. The access and refresh tokens are kept only in the kast_admin_access / kast_admin_refresh cookies: HttpOnly, SameSite=Strict, Path=/api, and Secure unless COOKIE_SECURE=false. The SPA's JavaScript never sees a token.
  • Access tokens are verified locally against auth's JWKS (issuer, audience, expiry). The role comes from the token. An expired access token is refreshed through auth once per refresh token, even under parallel requests (auth treats a reused refresh token as theft).
  • Players are refused at sign-in (403) and the session auth just created for them is logged out.
  • Logout calls auth's logout and clears the cookies.

CSRF

Double-submit token: kast_admin_csrf (readable by JavaScript, SameSite=Strict, Path=/) is handed out on the first /api request and replaced at sign-in. Every non-GET request must send the same value in X-CSRF-Token, or it gets 403 csrf_invalid.

Online guard and force

Before any character write, the admin service asks the character's realm whether the account is online. Online → 409 character_online, and the UI offers a Kick. If the realm has no admin endpoint, refuses the connection or times out (WORLD_ADMIN_TIMEOUT_MS) → 503 realm_unreachable. Admins may send force: true to write anyway; the audit row records forced=true. GMs cannot force (403).

World admin port

  • TLS to each world server's admin port, verified against WORLD_ADMIN_CA_FILE. The first message carries WORLD_ADMIN_SECRET, which the world compares in constant time. One connection per request.
  • The secret lives only in the environment: never stored, logged or returned.
  • Realm admin hosts and ports are admin-only data. GMs never receive them: their requests use the server-side copy in kast_admin.realm_endpoints (see Setup).
  • Never publish the world admin port or the admin app to the internet. Compose keeps 7780 on the compose network and binds 3200 to 127.0.0.1.

Least privilege

  • The admin service never connects to kast_auth. Account and realm changes go through auth's API with the caller's token, so auth enforces its own rules (for example GMs only on player accounts, no self-ban).
  • Its world MySQL user has SELECT, UPDATE on kast_world.characters only: characters are soft-deleted, never removed.
  • Its admin MySQL user owns kast_admin only.

Audit log

Every mutating request writes exactly one admin_audit row before the response: actor id, email and role, action (for example character.rename, account.ban, realm.kick), target, before/after JSON, forced, and result (ok or the error code, including role refusals). Passwords are never recorded. Timestamps are UTC, written by the app.

HTTP hardening

helmet defaults (CSP default-src 'self', no MIME sniffing, no framing), Cache-Control: no-store on /api, a 100 KB JSON body limit, zod validation of every input, and generic 500s that never leak internals.
