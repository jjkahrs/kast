LOD and occlusion

Three automatic steps cut what large scenes submit, on top of frustum culling and instancing: mesh LOD (a model draws a coarser copy of itself when it is small on screen), terrain LOD (far terrain chunks draw every 2nd, 4th or 8th sample) and Hi-Z occlusion culling (the camera pass skips what an earlier frame's depth shows is hidden). All three work in the editor's Scene and Game views, the built game and the Scene view's open zone, and each can be turned off with a flag to compare output and speed.

Mesh LOD

At import: the LOD chain

The editor's importer (editor/model_importer.cpp) gives every mesh of a model a chain of levels. LOD0 is the mesh as authored. By default there are 4 levels, LOD1, LOD2 and LOD3 aiming at 50%, 25% and 12.5% of LOD0's triangles. They are made with meshoptimizer:

  • meshopt_simplifyWithAttributes with the mesh borders locked and normals (weight 0.5) and UVs (weight 1) as attributes, so UV seams and hard edges stay where they are.
  • Simplification stops at an error of kLodMaxError = 10% of the mesh's extent even if the target count is not reached, so a tiny closed mesh (a 12-triangle cube) keeps its shape instead of collapsing.
  • If a level still ends more than 10% over its target (seen on dense skinned characters), it is made again with meshopt_simplifySloppy (borders locked) and that result is kept if it is smaller. Sloppy levels ignore UV seams: textures can smear a little on far levels.
  • Levels are index-only: each level is a new index list over LOD0's vertices. Lightmap UVs, skin weights and vertex colours stay valid at every level, and skinned meshes keep their bones.

The starter MMO's skinned female-128-anim.glb (14244 triangles) gets 7083 / 3478 / 1657, within 10% of the targets.

Authored levels: _LODn

A model that already has levels uses them instead of generated ones. Name the nodes (or meshes) Unity-style: Rock_LOD0, Rock_LOD1, Rock_LOD2 ... (case-insensitive; the node name is tried first, then the mesh name). For each group, each level's parts are merged into the LOD0 mesh with the same material: their vertices are appended to LOD0's vertex buffer (transformed into LOD0's node space; for skinned meshes the joints are remapped) and their triangles become that level. Non-LOD0 parts are not drawn as meshes of their own, so nothing renders twice. A level without a part for some LOD0 mesh draws nothing for that mesh. A level part whose material LOD0 doesn't use is dropped with a warning, and a _LOD1 part with no _LOD0 group renders as an ordinary mesh with a warning.

Import settings: <model>.import.json

A model's LOD settings live in a sidecar next to it, written by the Model Preview's LOD section (or by hand). Without one the defaults apply.

{"version": 1, "lod": {"auto": true, "ratios": [1, 0.5, 0.25, 0.125],
                       "thresholds": [0.5, 0.25, 0.1, 0.03], "cullBelowLast": false}}
  • auto: generate levels (false: LOD0 only, unless the file has authored levels).
  • ratios: one per level (1 to 8 levels), LOD0's always 1: the target fraction of LOD0's triangles.
  • thresholds: per level, the screen height from which it is used (defaults 50%, 25%, 10%, 3%).
  • cullBelowLast: below the last threshold the model is not drawn at all (else it keeps its last level).

The sidecar is part of the model's import cache key, so editing it imports the model again (within a frame). It is not shipped: Build bakes the settings into the cooked .kmodel (.kmodel version 3), so the built game, which has no importer, has the same levels and thresholds. A malformed sidecar logs a warning and the defaults are used.

At run time: picking a level

  • The screen height of a ModelRenderer is the largest extent of its world bounds (bind pose) over the height the camera sees at the distance of the bounds' centre: extent * proj[5] / (2 * distance) (orthographic: extent * proj[5] / 2). It depends on distance only, so turning the camera never changes a level (engine/lod.h lodScreenHeight).
  • The level is the first whose threshold the screen height reaches (selectLod). Below the last threshold it is the last level, or nothing with cull-below.
  • Hysteresis: a level is kept until the screen height leaves its range by kLodHysteresis = 10% of the boundary it crossed, so a model parked at a threshold doesn't flicker (with the camera parked at a boundary for 150 frames, no change was logged). Switching is an instant pop; there is no crossfade.
  • One level per entity, from the main camera's view. The shadow passes (cascades, point, spot and area light shadows) draw the same level. Each level has its own index buffer and the level is part of the instancing batch key, so each level batches separately.
  • Bias multiplies the screen height: above 1 keeps detail further away. The global bias (Renderer::setLodBias, --lod-bias) and an entity's LODGroup bias multiply.
  • Always LOD0: physics colliders, the lightmap, VoxelGI, SDFGI and reflection probe bakers.
  • Lightmapped meshes at LOD1+ keep sampling their lightmap: if the bake kept the mesh's own vertices, the model's level is drawn over them; otherwise (an unwrapped copy) the level is made at run time from LOD0's unwrapped triangles with meshopt_simplify to the same triangle count, keeping chart seams, and cached.

LODGroup component

Optional, on an entity with a ModelRenderer (Add Component > LOD Group). It overrides the model's thresholds and cull-below for that entity:

A level past the model's last draws its last. The Inspector shows the level the Scene view drew it at (LOD Group Inspector).

Terrain LOD

  • Each 256 m terrain tile (257 x 257 samples, one vertex buffer) is split into 8 x 8 chunks of 32 x 32 quads, numbered in Morton order (terrainChunkCell).
  • Each chunk draws with an index stride of 1, 2, 4 or 8 samples. The index buffers are shared by every tile: one per stride, with and without skirts, each holding every chunk.
  • The renderer takes the coarsest stride that meets both: the chunk's largest height error at that stride covers at most kTerrainMaxScreenError = 0.002 of the view's height (about 1.5 px at 720p) at the chunk's nearest point, and the chunk is at least kTerrainStrideDistance x stride = 32 m x stride away (stride 2 from 64 m, 4 from 128 m, 8 from 256 m), so near terrain keeps its vertex normals. The LOD bias scales both. No hysteresis.
  • Skirts hide the cracks between chunks (and tiles) at different strides: every chunk edge hangs a strip facing out of the chunk, as deep as 2 x the largest edge error through that sample plus 0.25 m. Skirt vertices copy the edge vertex's normal, UVs and lightmap UVs, so they shade like the edge. A skirt at the outer edge of the loaded tiles can be seen from outside them.
  • Lightmap UVs (TEXCOORD1) and the tiled / map UVs are unchanged; lightmapped tiles keep their lightmaps at every stride.
  • One draw per run of consecutive chunks at one stride and on the same side of the camera's frustum; the camera pass still culls by chunk, the shadow passes by run, with the camera's strides. Terrain is never instanced.
  • --no-lod, --force-lod N and reflection probe bakes use one stride everywhere (1; stride 1 << min(N, 3) forced), without skirts, one draw per tile: stride 1 is the exact pre-LOD mesh.

Hi-Z occlusion culling

In the camera pass, after frustum culling and before batching, a draw is skipped when a GPU test of its box against an earlier frame's depth found it hidden (engine/occlusion.h HizOcclusion). Each frame, per viewport:

  1. The depth the opaque meshes just wrote is copied, and the boxes of this frame's candidates (every draw that passed the frustum, skipped or not) are kept, grown by 2% of their largest extent (at least 5 cm) on every side.
  2. Next frame, a compute shader (cs_hiz_build.sc, 4 mips per pass) builds a depth pyramid from that copy: mip 0 is the largest power of 2 not over half the view (1280 x 720 gives 512 x 256), each texel the farthest depth under it; each mip below halves it, down to 1 x 1.
  3. Another compute shader (cs_hiz_test.sc) projects each kept box with that frame's view-projection, picks the mip where its screen rect covers at most 2 x 2 texels and marks it hidden if its nearest depth is beyond the farthest depth there. A box through the near plane or behind the eye is always visible.
  4. The visibility is blitted to a read-back texture and read back 3 frames later (Direct3D 11 waits for the GPU when a read-back is mapped, so asking at once stalls every frame).

Latency: a result is used 5 frames after the depth it was tested against was drawn (measured: Hi-Z latency 5 frames in --log-fps). With a still camera that changes nothing: the image with occlusion on matches --no-occlusion exactly. While the camera moves, a draw coming out from behind an occluder can appear up to about 5 frames late (a 1–5 frame pop at the occluder's edge); the box dilation hides most of it at walking speeds. A draw that moves out of the box it was tested with is drawn at once.

Never skipped

  • Animated (posed) models: their bounds are the bind pose's.
  • Draws with no result yet: new ones, ones that just came into the frustum.
  • Everything after a cut, teleport or big jump (results tested from an eye more than 2 m from the camera's are dropped) and after a viewport resize, until new results come back.
  • Everything without a render target to copy depth from, and on a GPU without compute, blit or read-back (bgfx::getCaps()); the log says Occlusion culling: this GPU lacks compute, blit or read-back; every draw in the frustum is drawn. --occlusion-unsupported forces this (a test hook).
  • Frames with fewer than 64 candidate draws test nothing (kOcclusionMinDraws): the pyramid and read-back cost a fixed few tens of microseconds. While the newest result hid less than 20% of its draws, a test runs only every 8th frame (its results stand meanwhile).
  • Shadow passes are not occlusion culled. At most 65536 draws are tested per frame; the rest draw.

Blended draws are tested like the rest, but never hide anything: only what writes depth is in the pyramid. Draws whose .kshader vertex() moves geometry outside their bounds can be culled wrongly, as with frustum culling.

Debug views

The Scene view's toolbar has a Debug menu (Editor controls):

  • LOD tint: every draw in an untextured colour by its level: LOD0 green, 1 yellow, 2 orange, 3 red, 4+ purple; terrain chunks by stride 1, 2, 4, 8 the same way (--lod-tint; --terrain-lod-tint is the same).
  • Occluded boxes: the boxes of the draws occlusion skipped, as orange lines drawn through what hides them (--show-occluded).
  • Hi-Z mip: a picture of one pyramid mip in the view's corner, brighter = nearer (--show-hiz N).

Stats

Renderer::stats() counts the last camera pass: triangles submitted, draw calls (an instanced batch is one), draws occluded and draws per level. The F3 overlay (Game view and built game) and the editor's --log-fps line (the Scene view's) print them:

FPS 1424.0, CPU 0.38 ms/frame, GPU 0.47 ms/frame, 33 draw calls; Scene view: Tris 580.6k  Draws 3  Occluded 72  LOD 3/0/0/504, Hi-Z latency 5 frames

Benchmark

tests/scenes/lod_occlusion.scene (far-field view) and tests/scenes/lod_occlusion_wall.scene (behind-wall view) are the same scene with a different Main Camera and editor camera: a 24 x 24 field of a 9216-triangle torus (tests/scenes/models/lod_torus.obj), an 80 x 15 m near wall and a 40 x 10 m middle wall. All three files are written by tests/scenes/gen_lod_occlusion.py. Run, for example:

kast_editor --scene tests/scenes/lod_occlusion.scene --log-fps --no-vsync
kast_editor --scene tests/scenes/lod_occlusion_wall.scene --log-fps --no-vsync --no-lod --no-occlusion

Measured on the development machine (Release, --no-vsync, 1280 x 720 window, Scene view 765 x 426), three interleaved rounds; the machine was also running another GPU-heavy program, so the FPS figures vary by about 10% between rounds. Triangles, draws and occluded are the Scene view's camera pass.

LOD cuts the far field's triangles by 87.5% (all tori at LOD3); behind the wall occlusion skips 95% of the draws. In this scene a torus is cheap once at LOD3, so with LOD on, occlusion saves little GPU time and its fixed cost (pyramid, test, read-back) shows: behind the wall all-on is up to 15% slower than --no-occlusion. Its gain is largest with LOD off (--no-lod 885–978 FPS vs 517–619 without either) and in scenes whose hidden draws are expensive.
