Instancing and culling

The renderer (engine/renderer.cpp, used by the editor's Scene and Game views and the built game; the Scene view also draws the edited zone with it) turns every MeshRenderer, every mesh of every ModelRenderer and every terrain tile into a draw each frame. Two automatic steps keep scenes with many repeated objects (a zone's grass, rocks and trees) cheap. Neither needs a component, flag or setting: the output is the same as drawing everything one by one.

Frustum culling

Each pass draws only the draws whose world-space bounds (an axis-aligned box) are at least partly inside that pass's view volume (engine/frustum.h: frustumFromViewProj, intersects):

  • Camera: the camera's frustum, near to far plane.
  • Directional light cascades: each cascade's orthographic volume. That volume already reaches back toward the light to the nearest shadow caster in the scene, so a caster outside the camera's view (a tree behind the camera, a cliff above it) still shadows what the camera sees.
  • Point light cube faces: each face's 90 degree frustum, after the light's range test, so a caster lands only in the faces it can shadow.

The test is conservative: a box near a corner of the frustum but outside it may still be drawn, never the reverse. Animated models are never culled: their bounds are the bind pose's, and a posed limb can reach past them.

GPU instancing

After culling, each pass groups its draws into batches. A batch of two or more is drawn with one bgfx instanced submit: the mesh and material are set once and each draw's world matrix goes in a per-instance buffer (64 bytes per instance, i_data0..3 in vs_mesh_instanced.sc and vs_shadow_instanced.sc; the normal matrix is derived from it in the shader). Draws are in the same batch when they share all of:

  • the vertex and index buffers (the same primitive, model mesh or terrain index buffer),
  • the material (the same .mat file, or the same model-embedded material),
  • castShadows and receiveShadows,
  • in the camera pass, the point lights that reach them (at most 8 per mesh, chosen per draw as before), so each instance is lit exactly as its own draw would be.

The 903 grass tufts of the starter MMO's meadow (3 meshes each), for example, become a few instanced submits per pass instead of thousands of draws.

Not instanced

  • Skinned meshes (a model mesh with joints): each has its own bone matrices.
  • Blended materials (alphaMode blend): still drawn one by one, far to near, after the opaque and mask ones. They are culled like the rest.
  • Per-entity materials (a MaterialInstance, e.g. one changed by a script): each is its own material, so its own batch.
  • Batches of one: drawn as before.
  • A batch that doesn't fit what is left of the frame's transient buffer (bgfx's limits.transientVbSize, also used by the editor's line overlays) is drawn one by one.

Turning them off

For comparing output and performance, Renderer::setInstancing(false) draws every draw with its own submit and Renderer::setCulling(false) sends every draw to every pass. The editor (Scene and Game views) and the built game take the same switches as flags:

FlagEffect
--no-instancingOne draw call per draw, as before instancing.
--no-cullingEvery draw in the camera pass, every cascade and every cube face of each shadowed point light in range.

With --log-fps the editor logs the draw call count once a second, which shows what batching saves:

kast_editor --scene samples/starter-mmo/scenes/meadow.scene --play --focus-panel Scene --log-fps --no-vsync
kast_editor --scene samples/starter-mmo/scenes/meadow.scene --play --focus-panel Scene --log-fps --no-vsync --no-instancing --no-culling

The single-draw shaders (vs_mesh, vs_shadow) transform exactly as the instanced ones do (model matrix, then u_viewProj), so a mesh covers the same pixels drawn either way: screenshots with and without the flags match.
