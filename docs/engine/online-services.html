Online Services

The built-in integration with the repo's services (services/auth, services/world), switched on per project by project.kast's online block. The whole flow in one project: samples/starter-mmo. While it is disabled none of it exists (kast.auth and kast.world are nil). If the CA file can't be loaded at editor Play start, the error is logged and that Play session runs without kast.auth and kast.world; a built game refuses to start.

kast.auth

Lua access to the auth service's player endpoints (services/auth/openapi.yaml), at online.authUrl, trusting online.caFile besides the Windows ROOT store. Built on kast.net's HTTP client (engine/auth_client.h, kast::AuthClient), so its requests show in the Network panel. Every call returns an id (a number) at once; its result arrives later as one event carrying that id: the call's success event or auth.error. There are no callbacks. Arguments that aren't strings raise at the calling line (kast.auth.login: email must be a string, got 1); everything else, including "not logged in", is an auth.error event.

The session (access + refresh token) lives in engine memory only: nothing is written to disk, Lua never sees the tokens, and nothing logs passwords, tokens or request bodies. One session per Play session: kept across kast.loadScene, cleared by editor Stop and at Play start; in a built game, one per process. The access token is refreshed automatically at 80% of its lifetime or 60 s before it expires, whichever is earlier (never before half of it), with at most one refresh in flight (the service revokes the whole session if a refresh token is used twice). me / realms called during a refresh wait for it and use the new token. A refresh that fails for any reason (the service says invalid_refresh_token or account_banned, or the request itself fails) clears the session and publishes auth.session.expired.

Function Request Success event
register(email, password) -> id POST /v1/auth/register auth.registered
resendVerification(email) -> id POST /v1/auth/resend-verification auth.verificationResent
verifyEmail(token) -> id POST /v1/auth/verify-email auth.emailVerified
login(email, password) -> id POST /v1/auth/login auth.login.ok
logout() -> id POST /v1/auth/logout auth.loggedOut
forgotPassword(email) -> id POST /v1/auth/forgot-password auth.passwordResetSent
resetPassword(token, password) -> id POST /v1/auth/reset-password auth.passwordReset
me() -> id GET /v1/me auth.me
realms() -> id GET /v1/realms auth.realms
isLoggedIn() -> bool none none
account() -> {accountId, email, role} \| nil none none
  • login while logged in, or while another login is in flight: auth.error already_logged_in (log out first; a second session would never be revoked).
  • logout, me, realms while logged out: auth.error not_logged_in.
  • logout clears the session at once (isLoggedIn() is false right after the call), then tells the service; auth.loggedOut follows its answer, or auth.error if it can't be reached (the game is logged out either way).
  • register, resendVerification and forgotPassword succeed for every email (the service never reveals whether an account exists). The tokens for verifyEmail / resetPassword come from the emails the service sends.

Events (on the session's event bus, publisher kast.auth):

Event Payload
auth.registered, auth.verificationResent, auth.emailVerified, auth.passwordResetSent, auth.passwordReset, auth.loggedOut {id}
auth.login.ok {id, accountId, email, role}: from the access token's claims (role is player, gm or admin)
auth.me {id, account = {id, email, role, emailVerified, createdAt}}
auth.realms {id, realms = {{id, name, host, port, region, status, sortOrder}, ...}}: ordered by sortOrder; status is online, offline or maintenance
auth.error {id, op, status, code, message, details?}: op is the function's name; for an error the service answered, status is the HTTP status and code / message / details are its {"error": ...} body's (e.g. invalid_credentials, email_not_verified, account_locked with details.lockedUntil, account_banned with details.reason / expiresAt, validation_error with details = {{path, message}, ...}, rate_limited, invalid_token, unauthorized). Client-side codes, all with status 0 unless noted: network_error (unreachable, TLS failure, timeout), not_logged_in, already_logged_in, http_error (an error response without a JSON error body; status set), bad_response (a success response that isn't what the API promises)
auth.session.expired {code, message}: the refresh failed (code as in auth.error); the session is already cleared
auth.session {accountId, email, role}: Play started with a session handed in from C++ (AuthClient::adopt, for the editor's own login) 
return {
    init = function()
        kast.subscribe("auth.login.ok", function(e)
            kast.log("hello " .. e.email)
            kast.auth.realms()
        end)
        kast.subscribe("auth.realms", function(e)
            for _, realm in ipairs(e.realms) do kast.log(realm.name .. " " .. realm.status) end
        end)
        kast.subscribe("auth.error", function(e) kast.warn(e.op .. ": " .. e.code .. " " .. e.message) end)
        kast.subscribe("auth.session.expired", function(e) kast.loadScene("login.scene") end)
        kast.auth.login("me@example.com", "my password")
    end,
    update = function(dt) end,
}

C++: LuaSystems::auth() is the session's kast::AuthClient (no Lua or bus): the same calls, loggedIn(), account(), accessToken() (for engine code that calls other services, e.g. the world server) and adopt(session). LuaSystems::start(..., authConfig(project, error)) turns it on; tick() hands it the Network results of its own requests (never published as net.http.*, since their bodies hold tokens) and publishes its events.

Sample: tests/project/online_auth.scene (scripts/online_auth_demo.lua) logs in as demo@example.com and logs the realms. It needs a copy of tests/project with online enabled; the tests build one pointing at kast_net_test_server, whose /v1/... routes are a fake auth service.

kast.world

Lua access to a realm's world server (services/world, wire format in the World Server protocol), with the current kast.auth session. The engine owns the connection (engine/world_client.h, kast::WorldClient): TLS over kast.net's TCP client, trusting online.caFile besides the Windows ROOT store; the Hello + Auth{access token} handshake; answering the server's Ping; and encoding / decoding every message with the world server's own codec (services/world/protocol, compiled into the engine unchanged). Scripts never see bytes, frames or the token. One connection at a time, kept across kast.loadScene, dropped by editor Stop and at Play start. It shows in the Network panel as kast.world.<n> (a new number per connection); its net.* results are never published.

Calls in the wrong state, and arguments of the wrong type, raise at the calling line (kast.world.say: needs state 'inWorld', the connection is 'lobby', kast.world.connect: realmId must be a whole number >= 0, got x). Everything the server or the network decides arrives as an event.

Function Needs state Sends Answered by
connect(realmId) disconnected Hello, Auth to the realm's host:port world.connected, or world.disconnected
disconnect() any closes the connection world.disconnected client_disconnect (nothing if already disconnected)
listCharacters() lobby CharListReq world.charList
createCharacter(name, options?) lobby CharCreate (3–16 ASCII letters, unique per realm). options: a table of string → string, the game's creation choices (for example {class = "mage"}); nil or absent sends none. The engine only carries it: the world server checks its size and characters, then its Lua decides (character creation). A non-table, or a non-string key or value, raises an error. world.charCreated or world.charError
deleteCharacter(charId) lobby CharDelete world.charDeleted or world.charError
enterWorld(charId) lobby EnterWorld world.entered or world.charError
say(text, kind?) inWorld Say{kind, text} (UTF-8, at most 256 bytes; the server drops invalid or rate-limited ones silently). kind: "say" (nil: the players in view), "yell" (everyone on the map within the server's CHAT_YELL_RADIUS) or "emote" (say range, shown as "Name text"); another kind raises world.chat, to the sender too; chat.error muted if the character is muted
send(name, data) inWorld ClientEvent: data (a table with string keys, or nil for {}) as JSON; the server's Lua gets it as client.<name> whatever the server's system sends back, as server.<name>
state() -> string any none disconnected, connecting, lobby or inWorld
  • connect needs a logged-in kast.auth session: without one it publishes world.disconnected not_logged_in and touches no network. It looks realmId up in the last auth.realms list (from any kast.auth.realms() call), and fetches the list itself when the id isn't in it.
  • The server takes one character request at a time (a second while one is in flight: world.charError rate_limited). Character ids are numbers.
  • The access token is checked only at the handshake; logging out of kast.auth doesn't close the world connection.
  • The engine never logs the token, and never logs chat text.
  • send is how a game asks the server to do something (attack, use, buy): the server's system decides and answers with its own events (World Server, Client events). It checks, in this order, and raises at the calling line:
    • kast.world.send: name must be a string, got nil
    • kast.world.send: name must be 1-32 characters of a-z, 0-9, '.' and '_', got 'Attack'
    • kast.world.send: data must be a table, got 5
    • kast.world.send: data must be a table with string keys, not a list
    • kast.world.send: data is 2000 bytes encoded, the limit is 1024
    • kast.world.send: needs state 'inWorld', the connection is 'disconnected'
  • The server re-checks the name, size and JSON (a bad one is disconnected as malformed) and passes 10 per second per character to its Lua; the rest are dropped silently (protocol).
  • Example, from the starter-mmo sample: kast.world.send("combat.power", {power = "firebolt", target = npcId}); the server answers with server.combat.power and server.combat.hit, or server.combat.rejected {reason}.

Events (on the session's event bus, publisher kast.world). Positions are {x, y, z} tables (x/z the ground plane, y up); heading is a number:

Event Payload From
world.connected {accountId, role}; role is player, gm or admin AuthOk; state lobby
world.charList {characters = {{id, name, position, options}, ...}}; options is the table the character was created with ({} for none) CharList
world.charCreated {character = {id, name, position, options}} CharCreated
world.charDeleted {charId} CharDeleted
world.charError {request, code}: request is the failed request's opcode name (CharListReq, CharCreate, CharDelete, EnterWorld); code is name_taken, name_invalid, options_invalid (creation options refused), char_limit, not_found, already_in_world, rate_limited or service_unavailable. The connection stays. CharError
world.entered {entityId, map, position, heading}: map is the id of the map the character is on (World Server, Maps) EnterWorldOk; state inWorld
world.mapChanged {map, position, heading}: the server moved the player (another map, or a teleport); every entity in view is gone, the new neighbours come as world.spawn MapChange
world.spawn {entityId, name, position, heading, kind, template}: a player (kind "player", template "") or a server NPC (kind "npc", template the client template it names) came into view Spawn
world.despawn {entityId}: left view or logged out Despawn
world.entityMove {entityId, position, heading} EntityMove
world.correction {position}: snap back to the last valid position Correction
world.chat {kind, from, text}: kind is say, yell or emote ChatMsg
world.chatServer {host, port}: where the realm's chat service is, right after world.entered; kast.chat connects there by itself ChatServer
chat.error {code = "muted", name, minutes}: a say, yell or emote dropped because the character is muted (the same event the chat service's errors use) ChatNotice
world.component {entityId, name, data}: a server Lua component's full value; data is its JSON object (scene-file encoding: vec3/quat as arrays, enums by name). The local player's own components come with its entityId from world.entered ComponentUpdate
world.componentRemoved {entityId, name} ComponentRemove
server.<name> the payload the server's Lua system sent (any plain data, nil if none): an event its kast.sendTo, kast.sendNearby or kast.broadcast sent this player (World Server, Lua components and systems). Subscribe with kast.subscribe("server.<name>", fn). A payload that isn't valid JSON is warned and ignored ServerEvent
world.disconnected {code, reason}; state disconnected see below

world.disconnected code:

  • The server's Disconnect reason, named as in the protocol's code table: protocol_mismatch, malformed, unknown_opcode, frame_too_large, rate_limited, handshake_timeout, idle_timeout, invalid_token, token_expired, service_unavailable, logged_in_elsewhere, server_shutdown, server_full, unexpected_message (and ok, or unknown for a value not in the table). reason is disconnected by the server (code <n>).
  • Client-side:
    • not_logged_in: connect without a session, or the session ended before the connection started.
    • unknown_realm: no realm with that id in the auth service's list.
    • realm_lookup_failed: the realm list request failed (reason has its auth.error code; that auth.error is published too).
    • connect_failed: DNS, TCP or TLS failed, it timed out (10 s), or the connection closed before AuthOk; reason says which.
    • connection_closed: the connection dropped without a Disconnect.
    • malformed / unknown_opcode: the server sent a frame that doesn't decode, or an opcode not in the protocol (reason names it); the client closes the connection.
    • unexpected_message: the server sent a message out of order, e.g. lobby or world messages before AuthOk, or a client-to-server message.
    • client_disconnect: kast.world.disconnect().
return {
    init = function()
        kast.subscribe("auth.login.ok", function() kast.world.connect(1) end)
        kast.subscribe("world.connected", function() kast.world.listCharacters() end)
        kast.subscribe("world.charList", function(e)
            if #e.characters > 0 then kast.world.enterWorld(e.characters[1].id)
            else kast.world.createCharacter("Hero") end
        end)
        kast.subscribe("world.charCreated", function(e) kast.world.enterWorld(e.character.id) end)
        kast.subscribe("world.entered", function() kast.world.say("hello") end)
        kast.subscribe("world.chat", function(e) kast.log(e.kind .. " " .. e.from .. ": " .. e.text) end)
        kast.subscribe("world.disconnected", function(e) kast.warn("world: " .. e.code .. " " .. e.reason) end)
        kast.auth.login("me@example.com", "my password")
    end,
    update = function(dt) end,
}

World address override (editor only): kast_editor --world-address host:port (or LuaSystems::world().setAddressOverride("host:port") from editor C++) makes every connect in editor Play use that address instead of the realm's, e.g. a world server on your own machine. It lasts across Play sessions; the shipped player has no such flag and never sets it.

C++: LuaSystems::world() is the session's kast::WorldClient (no Lua or bus): the same calls and state(). tick() hands it the Network results of its connections and the auth events (for realm lists), then publishes its events after the auth.* ones.

Sample: tests/project/online_world.scene (scripts/online_world_demo.lua) logs in, picks the realm named Testgrove, connects, reuses or creates the character Demo, enters the world and says hello world. The tests run it against kast_net_test_server, whose fake auth lists Testgrove at its fake world server (127.0.0.1:47707).

Against the real servers: start the stack (cd services/world && cp .env.example .env once, then docker compose up -d --build; world on 7777, auth on 3100), then run ctest -R world_live. world_live_setup copies the world's dev certificate out of the container (docker compose cp world:/app/certs/server.crt) and adds a realm Kast Live (127.0.0.1:7777) to auth's database; world_live drives two accounts through it. A world server started with a sample's compose override is switched to the default one for the test and switched back afterwards (world_live_teardown).

kast.chat

Lua access to the realm's chat service (whispers, the fixed channels, the zone channel, ignore, GM mutes; wire format in the chat service protocol). The engine owns the connection (engine/chat_client.h, kast::ChatClient), a second TLS connection next to the world's, trusting the same online.caFile. It follows the world connection on its own: when the world server announces the chat service (world.chatServer, after world.entered) it connects there with the current kast.auth access token; if the connection drops or is refused it reconnects with backoff (1 s, doubling to 30 s) while the world connection lasts, and once back it is in General again (the service's doing) and rejoins the other channels it was in; world.disconnected ends it. Proximity chat (kast.world.say) never depends on it. It shows in the Network panel as kast.chat.<n>; it never logs the token or chat text.

Requests need state connected, else they raise at the calling line (kast.chat.whisper: needs the chat service connected, it is 'disconnected'), as do arguments of the wrong type. What the service decides arrives as events.

FunctionSendsAnswered by
state() "disconnected", "connecting" or "connected"
channels() {{number = 1, name = "General"}, ...}: the channels it is in, by number (the service's CHAT_CHANNELS order)
whisper(name, text) ChatSend whisper chat.message whisper_sent, or chat.error not_online / bad_name
send(channel, text) ChatSend channel; channel is a name or the number of a channel it is in (another number raises) chat.message channel (to the sender too), or chat.error not_in_channel / no_channel
zone(text) ChatSend zone: everyone on the character's map chat.message zone (to the sender too)
join(channel) / leave(channel) ChatJoin / ChatLeave chat.channel, or chat.error no_channel / not_in_channel
ignore(name) / unignore(name) ChatIgnore chat.notice ignored / unignored
mute(name, minutes) / unmute(name) ChatMute (minutes a whole number >= 1). GM / admin accounts only: the service checks the token's role chat.notice mute_set / mute_cleared, or chat.error not_allowed

chat.message {kind, from, text}; kind whisper, channel (with channel and number) or zone; {kind = "whisper_sent", to, text} for your own whisper. Never logged ChatLine
chat.channel {channel, number, joined} ChatChannel
chat.error {code, name, minutes}: not_online, muted, not_allowed, no_channel, not_in_channel, rate_limited, rejected, bad_name (notices). muted also comes from the world server for a proximity message ChatNotice
chat.notice {code, name, minutes}: ignored, unignored, mute_set, mute_cleared, you_muted, you_unmuted ChatNotice

    if e.kind == "whisper" then kast.log(e.from .. " whispers: " .. e.text)
    elseif e.kind == "channel" then kast.log("[" .. e.channel .. "] " .. e.from .. ": " .. e.text) end
end)
kast.subscribe("chat.status", function(e) if e.connected then kast.chat.send(1, "hello General") end end)

C++: LuaSystems::chat() is the session's kast::ChatClient. tick() hands it the Network results of its connections and every world event before it is published (observe), then publishes its events after the world.* ones. The starter-mmo sample's scripts/chat.lua is a complete chat box: slash commands, coloured lines, Enter to send.

Replication

Networked players without sync code (engine/replication.h). Three built-in components, edited in the Inspector and saved in scenes like any other:

Component Fields What it does in Play
NetworkLocalPlayer sendRateHz (1–30, default 10) Marks the local player. world.entered sets its Transform position and yaw (from the server's heading). While inWorld, its Transform position and yaw go to the server as Move — only when they changed (by more than 0.1 mm / 0.0001 rad) and at most sendRateHz times a second on average, so an idle player sends nothing. world.correction snaps its position to the server's; world.mapChanged places it like world.entered and destroys every remote clone.
NetworkReplication templateEntity (an entity name), interpolationMs (0–1000, default 100), npcTemplates (an entity name, optional, default empty) One per scene (more: the first is used, with a warning). At Play start (and after each kast.loadScene) the named entity and its children are taken out of the scene, so the template is never rendered, simulated or seen by scripts; Stop restores it with the rest of the pre-Play scene. Each world.spawn adds a clone of it at the scene root, named after the character and placed at the spawn position and heading (snapped). Each world.entityMove moves the clone in a straight line from where it is shown to the new position over interpolationMs (0 snaps); heading snaps. world.despawn destroys that clone, world.disconnected all of them. NPCs (world.spawn with kind "npc") are cloned from the child of the npcTemplates entity whose name is the spawn's template; at Play start (and after each kast.loadScene) that entity and every template under it leave the scene too, and Stop restores them. A spawn whose template is empty or has no such child is a clone of templateEntity, with one Console warning per template name.
NetworkEntity entityId (the server's id) Added to each clone. Server ids are unsigned 32-bit; one past 2^31 reads negative.
  • Replicated Lua components: each world.component is applied to the same-named Lua component on the clone with that entityId, or on the NetworkLocalPlayer entity when it is the local player's id: added if absent, replaced otherwise. The server's value goes through the drift rules, so a definition that differs from the server's still loads (each fix a Console warning, once per component and fix). world.componentRemoved removes it. A name with no Lua definition in the project is a Console warning, once per name, and is ignored. The last values are kept per player, so a clone re-created after a scene switch (and the new scene's local player) gets them again. Scripts get the same events to react to (e.g. kast.subscribe("world.component", ...)).
  • Event: after each clone is made, world.entitySpawned {entityId, entity, name, kind, template} (publisher kast.replication; kind and template as in its world.spawn, so a scene loaded after the spawn still knows an NPC; delivered the frame after world.spawn), so scripts can decorate it: entity is the clone's id for kast.get / kast.set / kast.add. Scripts still get every world.* event; the clone exists before any world.spawn subscriber runs.
  • Positions are Transform positions, so keep the local player and the template at the scene root (x/z the ground plane, y up, as the protocol). Heading is radians, atan2(dx, dz): 0 faces +Z.
  • Rates: the world server accepts 60 messages a second per connection; sendRateHz is capped at 30 to leave room for chat and pings. Remote players send about 10 moves a second, so keep interpolationMs near their interval (100 ms): shorter makes clones stop between updates, longer adds lag.
  • Scene switches keep the connection and what replication knows: the map (the new scene's Terrain shows it), the local player's server id, position, heading and replicated components (the new scene's NetworkLocalPlayer is placed where the old one stood, with no Move sent for it) and the players and NPCs in view (the new scene's template is cloned for each, where it was last shown; an NPC from the new scene's NPC templates). That holds across a scene with no NetworkLocalPlayer or template too, such as a character select scene that enters the world and then loads a zone's scene. The new scene's scripts then get, before any other event, world.entered (the player's server id, map, position and heading now; publisher kast.replication), world.component for each replicated value and world.entitySpawned for each clone, as if they had just entered. A game's one-time server.* events (sent once on entering) are caught up with kast.subscribe(name, fn, {replay = true}) (Events), which calls fn at once with the connection's last event of that name. samples/starter-mmo loads one scene per zone this way (Zone Builder).
  • NPCs: the world server's NPCs (World Server, NPCs) arrive like players, with kind "npc" and a template. Put one entity per NPC type under an entity named in npcTemplates (e.g. NPC Templates > Guard, Merchant), named after the template the server's kast.create uses. Players are never cloned from them.
  • Not replicated: rotation other than yaw, animation, or anything the protocol doesn't carry; no client-side prediction beyond snapping on corrections.
  • Online Services disabled: the three components show "Online Services disabled for this project" in the Inspector and do nothing at run time (the template stays in the scene).
  • C++: LuaSystems::replication(); clone(entityId) gives a server id's clone. interpolate, MoveThrottle, yawRotation and headingOf are the pure parts.

Sample: tests/project/online_replication.scene (scripts/online_replication_demo.lua): a Player (gold box, NetworkLocalPlayer, walk with WASD at 5 m/s), a Remote Player template (red sphere) and a Replication manager. The script only logs in, enters the world and logs world.entitySpawned; the tests run it against kast_net_test_server, whose Other appears as a red sphere next to the player. tests/project/online_npcs.scene (scripts/online_npcs_demo.lua) adds an NPC Templates entity holding a Guard (a glowing cyan pillar with a gold helmet), set as npcTemplates; played against the services/world compose stack with the editor's test login (realm Kast Live, character Watcher), the sample Guard NPC patrols around the player as a clone of it.
