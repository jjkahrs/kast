Shader graphs

A shader graph (.kshadergraph) builds a mesh surface shader from connected nodes instead of code, like Unity's Shader Graph. Kast turns the graph into the text of a .kshader, and from there everything is the .kshader path: the compile cache, hot reload, the material Inspector's param widgets, Lua kast.getMaterialProperty / setMaterialProperty, Build and the player. A material uses one the same way: "shader": "shaders/my_surface.kshadergraph" in its .mat.

The graph model, its file format and the code generation are engine code (engine/shader_graph.h) and need no GPU or window.

The .kshadergraph file

Strict JSON, version 1. Every key is checked: an unknown key, a wrong type or an out-of-range value is an error naming its JSON path (nodes[2].inputs.b: must be a finite number or an array of 2 to 4 finite numbers), and a graph that fails to load renders its materials magenta, like a broken .kshader. Missing optional fields get their defaults. Kast writes the keys in a fixed order with every field present, so loading and saving a saved graph gives the same bytes.

{
  "version": 1,                     // required: 1
  "params": [                       // the .kshader's params, in order (one "param" line each)
    {"name": "tint", "type": "vec3", "default": [1.0, 0.6, 0.3]},
    {"name": "speed", "type": "float", "default": 0.5, "range": [0.0, 4.0]},
    {"name": "pattern", "type": "texture2D", "default": "white", "srgb": true}
  ],
  "nodes": [
    {"id": 1,                       // required: a whole number > 0, unique
     "type": "output_fragment",     // required: a node type id (below)
     "position": [760.0, 0.0],      // on the canvas; [0, 0]
     "settings": {},                // per node type, e.g. {"param": "tint"}, {"value": [1.0, 0.5, 0.0]}
     "inputs": {}}                  // constants for unlinked number inputs, e.g. {"b": 0.5} or {"b": [0.0, 1.0]}
  ],
  "links": [                        // an output into an input; at most one link per input
    {"from": [10, "out"], "to": [1, "ALBEDO"]}
  ],
  "comments": [                     // comment frames on the canvas: x, y, width, height
    {"title": "Scrolling UV", "rect": [-20.0, -40.0, 520.0, 300.0]}
  ]
}
  • params: name and type (float, vec2, vec3, vec4, color, texture2D) are required. default: a number (float), an array of N numbers (vecN; 3 or 4 for a color, alpha 1), or "white", "black" or "normal" (texture2D). range [min, max] is only for floats, srgb only for textures. Names and limits are the .kshader rules (at most 16 number params and 4 textures; not a built-in's name).
  • links must name existing nodes and pins (an output, then an input), and may not form a cycle (node 4: the links form a cycle).

The smallest graph, tests/project/shaders/empty.kshadergraph, is a Fragment Output with nothing linked. It renders exactly as the built-in material:

Types and links

  • Pins are float, vec2, vec3, vec4 or texture2D. Math node pins are dynamic: the node takes the widest type among those inputs (linked outputs' types, constants' sizes; unlinked: float), and its output is that type.
  • A float into a vector pin is splatted (vec3_splat(x)); a narrower vector into a wider one is padded with zeros; a wider vector into a narrower pin is truncated ((x).xyz) with a warning on the receiving node (logged: [warn] Shader '...': node 1: input 'ALBEDO': vec4 truncated to vec3).
  • canLink refuses a texture into a number pin, a number into a texture pin, missing pins and any link that would close a cycle; it allows a truncating link with that warning.

Code generation

generateKShader writes the params as param lines, then fragment(), then vertex() and light() only when their output node has a linked input. Each function holds the nodes upstream of its output node, in topological order (the lowest id first among the nodes that are ready), each after a // @node <id> <type> line, with one temp variable per output (n<id>_<pin>; a texture output is the param's name itself). An output node's linked inputs are assigned to the built-ins (ALBEDO = n10_out;), the Light Output's added (DIFFUSE_LIGHT += ...;, once per light: the template calls the graph's light() for the directional light and each point, spot and area light, as any .kshader's; for an area light the Light Direction and Attenuation inputs are the approximation light() describes). After the lights the template adds the ambient as for any .kshader: the flat ambient, or image-based lighting from the sky or a reflection probe. Helper functions a node needs (Noise's) are written once, before fragment(). A Custom Expression's code goes in a block of its own after its marker, its pins as locals (rules). Unlinked output pins are not written, so they keep what the built-in material computes. A node feeding two stages is emitted in each. The text depends only on the graph, not on the order of its nodes or links, which matters because the compile cache and game.pak key the bytecode by it. The demo graph generates:

param vec3 tint = vec3(1, 0.6, 0.3);
param float speed = 0.5 range(0, 4);
param texture2D pattern = white srgb;

void fragment()
{
    // @node 2 uv
    vec2 n2_out = UV;
    ...
    // @node 6 add
    vec2 n6_out = n2_out + vec2_splat(n5_out);
    // @node 7 param
    // @node 8 sample_texture
    vec4 n8_rgba = texture2D(pattern, n6_out);
    vec3 n8_rgb = n8_rgba.rgb;
    ...
    // @node 10 multiply
    vec3 n10_out = n8_rgb * n9_out;
    // @node 11 constant_float
    float n11_out = 0.3;
    // @node 1 output_fragment
    ALBEDO = n10_out;
    ROUGHNESS = n11_out;
}

Errors

Validation errors name the node they are on and stop code generation (the material renders magenta, or keeps its last good version):

[error] Shader 'shaders/x.kshadergraph': node 5: UV is not available in light() (only in vertex(), fragment()); rendering it magenta
[error] Shader 'shaders/x.kshadergraph': node 2: input 'texture' needs a link; rendering it magenta
[error] Shader 'shaders/x.kshadergraph': node 8: param 'ALBEDO' has the name of a built-in; rendering it magenta
[error] Shader 'shaders/x.kshadergraph': node 3: a second Fragment Output: a graph has at most one; rendering it magenta
[error] Shader 'shaders/x.kshadergraph': links[0].to: must be [node id, "pin"]; rendering it magenta

Each node type may only run in some stages (UV is not a light() input, Sample Texture is fragment-only); a node is checked against the stages of the outputs it reaches. A param error is put on the first Param node using that param (node 0 is the graph itself, e.g. a fifth texture param no node uses). shaderc's errors, which come back with .kshader line numbers, are mapped to the node whose // @node block holds the line: node 10: line 28: error X3004: undeclared identifier '...'.

Unsaved edits

The editor's live update hands the library the open graph's current JSON with ShaderLibrary::setOverride(path, text): until it is cleared, the library generates and compiles that instead of the file, on its worker thread, keeping the last good program meanwhile, and every material naming the path (Scene and Game views, the preview, Lua) uses it. setOverride(path, std::nullopt) goes back to the file. text(path) is the exact .kshader text of the last load, what View generated code shows.

Build and the player

Build compiles every shipped .kshadergraph, as it does every shipped .kshader, into game.pak bytecode entries keyed by the generated text (shaderPakPath), and fails on an error with the file and node (Build failed: shader 'shaders/x.kshadergraph': node 5: ...). The graph file ships in game.pak too. The player has no compiler: it reads the shipped graph, generates the same text with the same engine code (deterministic and GPU-free) and loads the bytecode stored under it (Loaded shader '...' (precompiled)). So Build stores nothing extra for graphs, and a graph changed after Build has no bytecode, exactly like a changed .kshader.
