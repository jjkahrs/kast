Skybox

Each scene can draw a sky behind all of its geometry: a procedural three-color gradient or a cubemap built from six project images. It is set per scene ("sky" in the scene file), edited in the Sky section of Window > Lighting (edits show live and mark the scene dirty) and can be changed at runtime from Lua. The Scene view, the Game view and the built game all draw it. A scene without "sky" (mode off) renders exactly as before skies: the view clears to its background color, or to the fog color while fog is on.

Modes

  • off [default]: no sky.
  • procedural: horizon at eye level, blended toward top looking up and toward bottom looking down by sqrt(|y|), where y is the view direction's height (-1 straight down .. 1 straight up). The square root keeps the horizon band narrow. Colors are linear RGB 0..1; defaults top [0.10, 0.30, 0.75], horizon [0.55, 0.70, 0.85], bottom [0.20, 0.20, 0.22].
  • cubemap: six square PNG or JPG images of the same size, read as sRGB (so the sky renders the colors the images show). If any face is missing, unreadable, not a PNG or JPG, not square or a different size from px, the engine logs one warning naming the face and why (Sky cubemap: face nx 'sky/nx.png': cannot read the file; using the procedural sky), draws the procedural gradient instead and the Lighting panel shows the reason in red. A scene with bad faces still loads. Faces load once per set of paths (and project); editing a face image on disk needs the path changed, or the scene reopened, to show. The six faces are compressed into one BC1 sRGB cube with mips (the sky ignores alpha) (RGBA8 if the size isn't a multiple of 4), cached like other textures (Loaded sky cube (cooked in 0.02 s), then (cache hit)); the editor draws the uncompressed cube until that is done. Build puts the compressed cube in game.pak instead of the face images (Build), and the player loads that one. A sky set only from Lua (kast.sky.set) with faces no shipped scene or prefab uses has no compressed cube in the built game: the player logs it and draws the procedural sky.
    Or one cube file ("cube", the Lighting panel's Cube file picker): a cubemap .ktx or .dds, used as stored (BCn or uncompressed, its own mips) instead of the six faces, which are then ignored (and hidden in the panel). A corrupt file, a 2D texture or a format the GPU lacks falls back to the procedural sky the same way: Sky cubemap: 'sky/storm.ktx': a 2D texture, not a cubemap; using the procedural sky. See Cube files for which side is which.

The sky is drawn after the opaque meshes at the far plane (only where no mesh is), before the blended ones, uses the camera's rotation but never its position (walking never gets closer to it) and is never fogged (fog still fades meshes toward the fog color, which may differ from the sky). Post-processing (tonemapping, bloom, grading) applies to it like the rest of the image.

The sky also lights the scene: with a sky on, meshes take their ambient light from it (diffuse from its colors all around, reflections of it on smooth surfaces), scaled and tinted by "lighting"'s ambientIntensity and ambientColor, instead of the flat ambient color; a cubemap that falls back lights with the gradient. With the sky off nothing changes from before. See Image-based lighting, which also covers reflection probes.

Scene file

"sky": {
  "mode": "cubemap",
  "top": [0.12, 0.32, 0.78],
  "horizon": [0.62, 0.74, 0.86],
  "bottom": [0.3, 0.32, 0.28],
  "faces": {"px": "sky/px.png", "nx": "sky/nx.png", "py": "sky/py.png",
            "ny": "sky/ny.png", "pz": "sky/pz.png", "nz": "sky/nz.png"},
  "cube": "sky/storm.ktx"
}

Every field is optional (missing = default), and the editor always saves all of them except cube, which is saved only when set (so scenes from before cube files load and save unchanged). mode is "off", "procedural" or "cubemap"; colors are arrays of 3 numbers between 0 and 1; faces is an object whose keys are among px nx py ny pz nz and whose values are project-relative paths (empty = none). An unknown field, mode or face name, a mistyped value or a color out of range fails the scene load with a message (sky: "mode" must be "off", "procedural" or "cubemap") and leaves the open scene as it was. Face paths are not checked at load.

Cube faces

Kast is right-handed, Y up, and a camera looks down its -Z (Coordinates and scenes). Each face is the view from the center of the cube along its axis, not mirrored:

FaceLooking alongImage top edge towardImage right edge toward
px+X+Y+Z
nx-X+Y-Z
py+Y (up)+Z+X
ny-Y (down)-Z+X
pz+Z+Y-X
nz-Z (a default camera's view)+Y+X

That is the usual unfolded cross with nz as the front: nx to its left, px to its right, pz behind, py above it and ny below. Internally the renderer samples a D3D (left-handed) cube with z flipped, so pz goes in the cube's -Z side and nz in its +Z side (engine/sky.cpp, fs_sky.sc). A set authored for D3D's left-handed convention (posz in front) works unchanged once its posz image is used as nz and its negz as pz.

Test faces live in tests/project/textures/sky_test/: 16x16, one color per face (px red, nx cyan, py green, ny magenta, pz blue, nz yellow), each with a white 4x4 marker in its top-left corner so a flip or rotation shows. player_sky_cube_probe and player_sky_cube_back_probe read every face's color and marker back from the built game.

Cube files

A cube .ktx / .dds is uploaded as stored, so its sides are D3D's +X, -X, +Y, -Y, +Z, -Z, and the z flip above applies: its +Z side shows looking along Kast's -Z. To make one from six Kast faces, put them in a horizontal strip in the order px nx py ny nz pz (note nz before pz) and run texturec -f strip.png -o sky.ktx --strip -t BC7 -m (or -t RGBA8). A cube authored for D3D's left-handed convention needs no change. tests/project/textures/sky_test/cube.ktx (RGBA8) and cube.dds (BC7) are the test faces made that way; the built games sky_cube_ktx / sky_cube_dds must pass the same probes as the six faces (player_sky_cube_ktx_probe, player_sky_cube_dds_probe).

The sky (times the ambient color and intensity) is also the light the lightmap bake sees escaping the scene: a cubemap sky bakes its faces' colors, and one that can't be read bakes the gradient, as it renders. Changing the sky marks a bake out of date.

Lua

kast.sky reads and changes the running scene's sky. Changes are runtime only: they are never saved, and editor Play's Stop restores the scene's own sky, like every other change a system makes to the scene.

FunctionReturnsNotes
kast.sky.get()tableA fresh copy, shaped like the scene file's block except colors: {mode = "procedural", top = {x =, y =, z =}, horizon = {...}, bottom = {...}, faces = {px = "", ...}} (plus cube when one is set; kast.sky.set({cube = "sky/storm.ktx"}) sets it, "" clears it). Colors are {x, y, z} tables, as kast.get returns color fields.
kast.sky.set(fields)—Partial: only the listed fields change, and only the listed faces (kast.sky.set({mode = "cubemap", faces = {nz = "sky/storm.png"}})). Colors as {x =, y =, z =} tables. All or nothing: anything the scene file would reject (unknown field, mode or face, a color outside 0..1, a non-string path, not a table) raises at the calling line and leaves the sky unchanged.
 
-- Dusk: warm horizon, darker top.
kast.sky.set({mode = "procedural", top = {x = 0.05, y = 0.08, z = 0.25}, horizon = {x = 0.9, y = 0.45, z = 0.2}})

Limits

  • No sun disc, clouds, stars or day/night cycle; no intensity, exposure or rotation controls; no sky-driven ambient or reflections.
  • PNG and JPG faces, or one KTX / DDS cube file (no equirectangular or HDR sources at runtime: convert them with texturec --equirect); no hot reload of face images or cube files.
  • One sky per scene, not per Camera. The editor's Scene and Game views each keep their own copy of a cubemap.
