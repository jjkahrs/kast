Game GUI

Game GUIs are HTML/CSS-like documents rendered by RmlUi (engine/gui*.h, engine/scene_gui.h): an .rml file for the elements and a sibling .rcss file for their style. RmlUi reads them through the engine's file access (disk in the editor, game.pak in the player), logs to the Console as RmlUi: ..., and draws with bgfx (engine/shaders/gui/).

Files: an .rml links its style sheet in its <head>; the builder edits the elements under <body>:

<rml>
    <head>
        <title>Main Menu</title>
        <link type="text/rcss" href="main_menu.rcss"/>
    </head>
    <body>
        <div id="menu" class="panel">
            <p id="title">Kast Quest</p>
            <button id="start_button" data-event="menu.start">Start</button>
        </div>
    </body>
</rml>

Elements: Panel = <div>, Text = <p>, Rich Text = <p class="rich"> (its text is BBCode markup), Button = <button>. A Button's data-event names the event its click publishes (see below). Any other element (hand-written <span>, <img>, ...) is Unknown to the builder: listed and movable/deletable there, never created or edited, and kept with its attributes and children on save. Attributes the builder doesn't edit (style, title, data-*, ...) and comments are kept too; saving only normalizes whitespace and indentation.

Style sheets are RCSS (CSS2-like; see the RmlUi docs). RmlUi has no built-in styles: elements are inline until a rule says otherwise, so sheets start with div, p { display: block; }. The bundled font is Roboto (font-family: Roboto;, set on body) with real regular, bold, italic and bold italic faces (font-weight: bold / font-style: italic pick them); a project adds its own in fonts/. Text without a font-family doesn't show (RmlUi warns). Images (<img src>, decorator: image(...)) are PNG or JPG files, paths relative to the document (or style sheet), read from disk or the built game's pak and drawn 1:1; a missing file is RmlUi's Could not load texture warning. A dragged element's clone (outside any document) finds them relative to the dragged element's document.

UIDocument (built-in component, UI Document in the Inspector): path (project-relative .rml; the Inspector offers a combo of the project's .rml files, an unknown path shows as (missing) <path> and is kept) and visible (default true). Saved with the scene like any component. In Play (and in the built game), every UIDocument in the scene loads at Play start and shows over the Game view while visible, stacked in entity creation order (later entities on top); they unload on Stop and on a kast.loadScene switch (the new scene's load instead). Adding, removing or editing a UIDocument during Play applies at once. A missing .rml, an .rml RmlUi can't parse or a linked .rcss with problems logs an error naming the file and that document shows nothing; Play goes on. While the Game panel has input (focused and playing) the GUIs get the mouse, wheel and keys too (the game's kast.* input still sees them).

Button events: clicking a <button> with a non-empty data-event publishes that event on the Play session's event bus, publisher UI, payload {"id": "<button id or empty>", "document": "<rml path>"} (the UIDocument's path). No or empty data-event: nothing is published. Lua subscribes as to any event:

kast.subscribe("menu.start", function(event)
    kast.log("Menu start clicked: " .. event.id .. " in " .. event.document)
end)

Drag and drop: an element is draggable when its style sheet gives it RmlUi's drag property (drag: clone draws a copy under the cursor while the original stays put; drag-drop and drag work too). Give it (or an ancestor) data-drag="name" and the drag publishes on the event bus, publisher UI:

  • name.start once the mouse has moved with the button down on it;
  • name.drop when the button is released, wherever that is.

Both carry {"id", "document", "target", "targetDocument", "shift", "ctrl", "alt"}: id is the dragged element's id (or its nearest ancestor's with one), document its .rml. On a drop, target is the id of the element under the cursor (or its nearest ancestor with one) and targetDocument that element's .rml; both are "" when released over no element or over a document's own <body> (the world). shift, ctrl and alt are the modifier keys held at that moment. The engine moves nothing: Lua decides what a drop means.

.slot { drag: clone; }

<div id="slot_3" class="slot" data-drag="bag.slot"><div id="icon_3" class="icon"></div></div>

kast.subscribe("bag.slot.drop", function(e)
    if e.target == "" then askToDestroy(e.id)                 -- dropped on the world
    elseif e.targetDocument == e.document then move(e.id, e.target, e.shift) end
end)

Stacked documents: a document's <body> is usually full-screen, and RmlUi gives the mouse to the topmost element under it, so a later document's empty body hides the panels of the ones below from clicks, drags and hover. Give body pointer-events: none and the panels pointer-events: auto (it is inherited); the starter-mmo sample's starter.rcss does.

A press that starts a drag is a press on the GUI, so kast.gui.mouseOver() was true when it went down. The editor's --sim-mouse frame,left[+shift],dx,dy,0 performs one drag for tests (ctest -R ui_drag, tests/project/ui_drag.scene).

kast.gui (Lua, in Play and the built game; nil where no game GUI runs): reads and writes elements of the scene's loaded documents by id, topmost document first (engine/gui_access.h).

Function Returns Notes
kast.gui.value(id) string, number, boolean or nil The current text of the <input> / <textarea> with that id, a form widget's typed value, or a list's selected row's value (nil if none is selected); nil if no loaded document has one.
kast.gui.setValue(id, value) — Sets a form widget's value (snapped and clamped like input) or a text field's text, or selects a list's row (nil: none); publishes no change event.
kast.gui.scrollTo(id, index), kast.gui.scrollToEnd(id) — Scrolls a list's 0-based row index into view, or to its end. Not kept.
kast.gui.setText(id, text) — A text field's value; any other element's content as plain text (escaped, "\n" is a line break): markup shows as typed.
kast.gui.setRichText(id, text) — The element's content as rich text: text is BBCode, turned into safe RML (a text field takes it as typed). Kept like setText; the later of the two on an id wins.
kast.gui.setVisible(id, visible) — false hides the element (display: none), true gives it back its style sheet's display.
kast.gui.setAttribute(id, name, value) — Sets an attribute (all strings): an <img>'s src (relative to the document, like in the .rml), the class list ("slot uncommon") for styling, a style such as decorator: image(../icons/wing.png), ...
kast.gui.focus(id) boolean Gives the element keyboard focus, as a click would (a text field: typed text goes there, e.g. Enter to chat). false if no visible document has that id. Not kept.
kast.gui.focusedField() string or nil The id of the text field (<input type="text">, "password", <textarea>) with keyboard focus, e.g. to ignore movement keys while the player types.
kast.gui.mouseOver() boolean The mouse is over a GUI element (RmlUi's hover element is something other than a document's own <body>, so a full-screen body doesn't count), or over an element of an interactive WorldUI panel. Checked when a button goes down, it tells a press on the chat box from a press on the world.
kast.gui.hovered() string or nil The id of the element under the mouse, or of its nearest ancestor with one (an icon inside a slot reports the slot); nil over no element or only a <body>. Poll it each update for tooltips.
kast.gui.set(model, key, value) — Replaces the top-level variable key of the data model model: a string, number, boolean, nil (unset), an array or a table of string keys, nested. The views bound to it update.
kast.gui.get(model, key) the value or nil The variable as it is now, edits through two-way bound fields included; a fresh Lua copy. nil if unset.
kast.gui.clone(templateId, parentId, newId) boolean Deep-copies templateId (from parentId's document) under parentId as newId, shown. See runtime elements.
kast.gui.create(parentId, tag, newId[, attrs]) boolean Appends a new <tag id="newId"> to parentId, with attrs (a table of string attributes, e.g. {class = "row"}).
kast.gui.instantiate(prefabPath, parentId, newId) boolean Appends a new instance of a GUI prefab to parentId as newId (ids inside prefixed newId_, its .rcss added). See GUI prefabs: Lua.
kast.gui.remove(id) boolean Removes the element (and its children) from the topmost document holding it.

Writes (setText, setVisible, setAttribute, setValue) are kept and applied again to every document that loads later, so a system's init (which runs before the scene's documents load) and hot reloads see them; they are forgotten when the scene switches (kast.loadScene) and at each Play start. A write to an id no document has does nothing. Arguments that aren't strings (or, for setVisible, a boolean) raise at the calling line. Values and texts are never logged: a field may hold a password, so clear it after reading (kast.gui.setText("password", "")). Typed text reaches the fields because SDL text input is on while one has focus (editor: while the Game view has input).

kast.subscribe("login.submit", function()
    local email, password = kast.gui.value("email"), kast.gui.value("password")
    kast.gui.setText("password", "")
    kast.gui.setText("status", "Logging in...")
    kast.auth.login(email, password)
end)

Hot reload (Play): when a loaded .rml or a .rcss it links changes on disk (the editor's 0.5 s file poll), that document reloads; fix a broken file and it shows again. Not in the built game.

Sample: tests/project/ui.scene has a Main Menu entity with a UIDocument for ui/main_menu.rml (+ main_menu.rcss: a panel with a title, a subtitle holding an unknown <span>, and Start / Quit buttons publishing menu.start / menu.quit); scripts/ui_menu.lua logs both events.

Rich text

Rich text is BBCode markup turned into RML by the engine (engine/gui_richtext.h, guiRichTextRml): bold, italic, underline, strikethrough, colour, size, font, clickable links and inline images, from three places that share one converter:

  • Authored: a <p class="rich"> (the GUI Builder's Rich Text, its toolbar) holds the markup verbatim in the .rml; it is converted when the document loads (Play, the built game, the builder's preview). Its surrounding whitespace (the .rml's own line breaks) is trimmed. Only a <p class="rich"> holding text alone is converted, once at load: one inside a data-for row isn't (use data-rich there).
  • Lua: kast.gui.setRichText(id, text) on any element (kast.gui.setText stays plain).
  • Data binding: data-rich="expression" shows the bound value as rich text and follows the model like {{...}} does (inside a data-model; an unset variable shows nothing).
<p id="quest_text" class="rich">Bring [b]3 bat wings[/b] to [color=#ffcc00]Mara[/color]. [link=quest_42]Details[/link]</p>
<div data-model="chat"><p class="line" data-for="line : lines" data-rich="line.text"></p></div>

kast.gui.setRichText("status", "[i]Saved[/i] [img=../icons/ok.png]")
kast.gui.set("chat", "lines", {{text = "[color=#40c0ff]Mara:[/color] hello"}})
kast.subscribe("gui.link", function(e) openQuest(e.target) end) -- e.id, e.document too

Tags (names in any case; no spaces around =):

Tag Result
[b]...[/b], [i]...[/i]Bold, italic (Roboto's real bold / italic faces; any font family's faces when it has them).
[u]...[/u], [s]...[/s]Underline, strikethrough. RmlUi draws one decoration: inside each other the inner one wins.
[color=X]...[/color]#rgb, #rgba, #rrggbb, #rrggbbaa or a colour name RmlUi knows: black, silver, gray, grey, white, maroon, red, orange, purple, fuchsia, green, lime, olive, yellow, navy, blue, teal, aqua, transparent.
[size=N]...[/size]Font size in pixels: a positive number, clamped to 4..200 (a clamp is a warning).
[font=Family]...[/font]A loaded font family: Roboto or a project font. Letters, digits, spaces, _ and - only; a family that isn't loaded is a bad value.
[link=target]...[/link]A clickable <span class="link" data-link="target">; target is any printable text (escaped). Clicking it publishes gui.link; it opens nothing by itself.
[img=path], [img=path w=N h=N]An inline <img>, no closing tag. path is relative to the .rml (no spaces, quotes or < >); without w / h it is one line high (1em), with one of them the other follows the image's aspect; whole pixels 1..4096.

Text and escaping: everything else is text, escaped as setText escapes it (& < > "), and { / } too, so no {{...}} binding runs from it; a line break ("\n", or one typed in the builder) is a line break. [[ is a literal [ ([[b] shows [b]); a ] needs no escape. No input can produce an element or attribute other than the tags above: values are checked (colours, sizes, font names, image paths) or escaped (link targets). Spaces alone between two tags are kept (RmlUi drops text that is only spaces): the converter moves them next to text, or writes &nbsp; between two images.

Malformed markup never fails and never crashes; each case is a warning (the builder lists them under the field):

  • an unknown tag ([blink]), a bad value ([color=nope], [size=-3], [b=1]), a [ with no ], and a closing tag with nothing open to close (stray[/b], [/img]) show as the literal text they are;
  • tags still open at the end are closed there ([b]open is bold to the end);
  • mis-nesting: a closing tag that skips inner open tags closes them with it and opens them again right after it, so [b]a[i]b[/b]c[/i] is <b>a<i>b</i></b><i>c</i>: bold a, bold italic b, italic c.

Links: clicking a link publishes gui.link on the event bus, publisher UI, payload {"id": "<id>", "document": "<rml path>", "target": "<link target>"}; id is the id of the link's nearest element that has one: the rich text element's ("" if it and its ancestors have none). The engine's default style colours links #ffaa00, #ffcc00 hovered and #ff9900 pressed; a document rule for .link overrides it.

Fonts: every .ttf / .otf under the project's fonts/ folder loads when Play starts (and in the built game, from game.pak) and when the GUI Builder previews a GUI. Its family is the name inside the file (e.g. LatoLatin for LatoLatin-Regular.ttf; the Console logs RmlUi: Loaded font face 'LatoLatin' [regular]), its bold and italic files (same family) are picked by font-weight / font-style and by [b] / [i]. Use it with [font=LatoLatin] or font-family: LatoLatin;. A file that isn't a font logs Font 'fonts/x.ttf' could not be loaded and the others still load; documents aren't rejected for it. A font loads once per session (replacing the file needs a restart).

Sample: tests/project/ui_richtext.scene (ui/richtext.rml, scripts/ui_richtext.lua) shows every tag, the project font fonts/LatoLatin-Regular.ttf, malformed markup, setRichText / setText, a data-rich binding and a link whose gui.link the script logs (ctest -R richtext; kast_self_check --richtext runs the converter and headless checks).

Data binding

RmlUi's data bindings work without any C++: an element with data-model="name" opens a model, and inside it {{expression}} in text, data-for, data-if, data-visible, data-value, data-checked, data-attr-*, data-class-*, data-style-*, data-rml, data-alias-* and data-event-* read its variables, and kast's data-rich shows one as rich text. Lua fills them with kast.gui.set:

<div id="quests" data-model="quest_log">
    <p>{{title}} ({{count}}) <span data-if="full">full</span></p>
    <button class="row" data-for="row : rows" data-attr-id="'row_' + it_index"
            data-class-selected="row.selected" data-event="quest.pick">
        {{row.title}} <span data-for="goal : row.goals">{{goal}}</span>
    </button>
    <input type="text" id="filter" data-value="filter"/>
</div>

kast.gui.set("quest_log", "title", "Quests")
kast.gui.set("quest_log", "rows", {{title = "Bat Trouble", goals = {"Bats 2/3"}, selected = true}, ...}) -- as many as there are
kast.subscribe("quest.pick", function(e) kast.log(e.id) end)                                 -- "row_0", "row_1", ...
local filter = kast.gui.get("quest_log", "filter")                                           -- what the player typed
  • Models are made for you (engine/gui_models.h). Before a document loads, the engine reads its .rml for data-model names and the top-level variables its bindings read (rows in row.title / data-for="row : rows"; not data-for / data-alias names, members, | transforms, callbacks(), literals or RmlUi's reserved it, it_index, ev, size, ...). It creates each model on the scene's GUI context and binds each variable, so the document loads with no RmlUi warning (one would reject it). An unset variable reads as empty ("", false, no rows). Models belong to the context, not a document: two documents naming one model share it.
  • Values are plain data (GuiValue, JSON in C++): strings, numbers, booleans, arrays (a Lua sequence {a, b}; data-for repeats over it, rows.size is its length) and tables of string keys (row.title), nested up to 32 deep. An empty Lua table is an empty table (no rows). set replaces one top-level key whole; send the whole list again after a change. Numbers show without trailing zeros (3, 2.5).
  • Two-way: data-value on a text <input>, a range or a <select>, and data-checked on a checkbox, write the player's edits into the model; kast.gui.get reads them. A checkbox gives a boolean; text a string, kept a number when the variable held one and the text is a number (a range).
  • Persistence: values are kept until the scene switches (kast.loadScene) or Play starts again, like the other writes. A document that loads later, or hot reloads, shows the current values. A name stays bound for the session: a hot reload that turns a bound variable name into a data-for / data-alias name gets RmlUi's "shadowed" warning until Play restarts.
  • Events: data-event buttons and data-drag elements inside data-for rows publish as usual; give each row an id with data-attr-id (e.g. 'row_' + it_index, 0-based) to tell them apart. RmlUi's own data-event-click="..." runs model expressions; kast's data-event="name" (no suffix) is unaffected.
  • Errors: a model or key that isn't a string, a key that isn't a variable name (a letter, then letters, digits and _; not reserved) and a value that isn't plain data (a function, a cycle, mixed keys) raise at the calling line. Values are never logged.
  • The GUI Builder's preview creates the same models, empty: data-for rows and {{...}} show no data there.

Runtime elements: clone, create, remove

For elements outside a model (or when a list is easier by hand), kast.gui.clone copies a template, typically hidden in the .rml with style="display: none"; the copy gets newId, loses its inline display (shown), and its descendants' ids that start with "<templateId>_" are renamed to start with "<newId>_", so the copy's parts can be written:

<div id="list">
    <div id="tpl" class="row" style="display: none"><p id="tpl_name"></p><button id="tpl_pick" data-event="row.pick">Pick</button></div>
</div>

if kast.gui.clone("tpl", "list", "row_7") then kast.gui.setText("row_7_name", "Seventh") end -- row.pick: id "row_7_pick"
kast.gui.create("list", "p", "note_1", {class = "note"})
kast.gui.remove("row_7")
  • Live only: created and cloned elements (and removals) are not kept. They are gone when their document reloads (hot reload, Play start, a scene switch); model values are not. Do it again after a reload if needed.
  • false, not an error: a missing template, parent or id, an empty tag or newId, or a newId already in that document returns false and logs a warning saying which (kast.gui.clone('tpl', 'list', 'row_7'): the new id is taken in that GUI). remove also refuses (false, logged) a row a data-for made, or anything inside one: RmlUi owns those, change the model instead (the check is by position: an element just before a data-for one of the same tag counts too). Arguments of the wrong type raise like the other functions.
  • Clicks and drags work on them as on authored elements.

Sample and tests: tests/project/ui_bind.scene shows ui/bind.rml (two models: a bound list with nested tags and Pick buttons, two-way inputs echoed below; a clone template), driven by scripts/ui_bind.lua; ctest -R ui_bind, player_bind_click and self_check's checkGuiDataModels. The starter-mmo chat and quest log are bound lists.

GUI prefabs

A GUI prefab is a reusable element subtree that GUIs place as linked instances (authoring: GUI Builder: GUI prefabs). The engine expands the instances of a document before RmlUi parses it, the same way in the GUI Builder preview, editor Play and the built player (engine/gui_prefabs.h, .cpp).

File format

  • <stem>.guiprefab: XML holding exactly one element (any element, children allowed; comments around it are kept). Its own id, if any, is ignored: an instance's id is the reference's. The root can't itself be an instance of another prefab; elements inside it can (nested prefabs).
  • An optional sibling <stem>.rcss: the prefab's styles. It is linked into every document holding an instance of the prefab, once per document, before the document's own sheets (a <link type="text/rcss"> put first in its <head>), so the document's rules win at equal specificity.
  • Both ship in game.pak like every project file; images a .guiprefab names count as used by the GUI when Build decides which images keep their source file.

Instance markup and overrides

<div id="hp" data-prefab="ui/hp_bar.guiprefab">
    <override target="title" text="Health"/>                     <!-- the text of the prefab element with id "title" -->
    <override target="title" attribute="class" value="big"/>     <!-- one of its attributes -->
    <override target="bar" attribute="style"/>                   <!-- no value: the attribute is removed -->
    <override target="" attribute="class" value="hp wide"/>     <!-- "": the prefab's root -->
    <override target="1/0" text="..."/>                          <!-- an element without an id: child indices -->
</div>
  • The reference is any element with data-prefab="<project path>" and a required id; the GUI Builder writes a <div>. Other attributes of the reference are ignored.
  • Each <override> child changes one field of one prefab element: target is the element's id inside the prefab (as written in the .guiprefab, without the instance prefix), "" for the root, or its element child indices from the root ("1/0": the root's second child's first child) when it has no id of its own. With text it replaces the element's text (its element children stay); with attribute it sets that attribute to value, or removes it when value is absent. A target that is no element of the prefab is ignored with a warning. The instance root's id can't be overridden (it is the reference's).
  • Overrides are values, not edits: the GUI Builder writes one per field that differs from the prefab, so a value set back to the prefab's disappears from the file. There are no structural overrides (adding, removing or reordering children) and a composite widget's insides (a Dropdown's options, ...) are edited in the prefab.
  • Left unexpanded the reference holds only empty <override> elements: nothing of it renders as text.

Expansion and ids

  1. The reference is replaced by a copy of the prefab's element; data-prefab="<path>" stays on it.
  2. References inside the prefab are expanded first (recursively), with their own overrides from the prefab file.
  3. Every id inside the copy becomes <instance id>_<id>, the root's id is the reference's: the convention of kast.gui.clone. Two instances a and b of a prefab holding title give a_title and b_title; a nested instance inner of another prefab inside instance n gives n_inner_title.
  4. The reference's overrides are applied (targets found first, then applied).
  5. The prefab's .rcss, if it exists, is linked into the document (once).

Lua and data bindings address the expanded ids (kast.gui.setText("a_title", ...); a button's click payload carries a_button).

Missing prefabs and cycles

A reference that can't be expanded is logged with log::warn naming the document, the path and why, and stays as an empty placeholder element (its overrides dropped from what RmlUi sees); the rest of the document loads:

GUI 'ui/hud.rml': prefab 'ui/gone.guiprefab' (#m): not found; left as an empty placeholder
GUI 'ui/hud.rml': prefab 'ui/a.guiprefab' (#a): a cycle (ui/a.guiprefab -> ui/b.guiprefab -> ui/a.guiprefab); left as an empty placeholder

The reasons: no id, the file not found, not well-formed XML, not exactly one element, and a cycle (a prefab holding itself, directly or through nesting): the reference that would close the cycle is skipped. The GUI Builder keeps such a reference and its overrides as written and saves them unchanged.

Lua: kast.gui.instantiate

if kast.gui.instantiate("ui/prefab_button.guiprefab", "spawn", "s") then
    kast.gui.setText("s_title", "Spawned card") -- its button publishes its data-event with id "s_button"
end
  • kast.gui.instantiate(prefabPath, parentId, newId) expands the prefab (nested prefabs included, ids prefixed with newId_, the prefab's own overrides of its nested instances applied) and appends it under the element parentId of the topmost loaded document holding one. The prefab's .rcss is added to that document if it doesn't have it yet (after its own sheets). In editor Play and built games.
  • Returns true, or false with a warning: a missing or broken prefab, an unknown parent, an empty newId, or any of the new ids already in that document (kast.gui.instantiate('ui/prefab_button.guiprefab', 'spawn', 's'): the id 's' is taken in that GUI). Arguments that aren't strings raise.
  • Live only, as clone: gone when the document reloads. kast.gui.remove(newId) removes it.

Hot reload: in Play, saving a .guiprefab (or its .rcss) reloads the documents holding instances of it, without re-saving them.

Sample and tests: tests/project/ui_prefab.scene shows ui/prefab_host.rml (two instances of prefab_button.guiprefab, one overriding its title, one of prefab_nested.guiprefab, a missing one) driven by scripts/ui_prefab.lua; ctest -R "ui_prefab|guiprefab" and kast_self_check --guiprefabs.

Form widgets

Five widgets are plain RML markup (the GUI Builder adds and edits them, see GUI Builder). Each renders with the engine's default widget style (Kast palette) with no project RCSS, in Play, the GUI Builder preview and the built player (engine/gui_widgets.h, .cpp):

Widget Markup Value
Toggle <input type="checkbox" class="toggle"/>; with a label: <label><input type="checkbox" class="toggle"/>Sound</label> (clicking the text toggles it too). checked="" starts it on. boolean
Slider <input type="range" min="0" max="100" step="1" value="50"/> (horizontal) number
Dropdown <select><option value="low">Low</option><option value="high" selected="">High</option></select> string (the selected option's value)
Spinbox <div class="spinbox" data-min="0" data-max="10" data-step="1"><button>-</button><input type="text" value="0"/><button>+</button></div>: exactly a button, a text input and a button number
Progress <progress value="0.5" max="1"/> (fills left to right) number in 0..max
  • Default style and overriding it: the default sheet (kGuiWidgetStyle, compiled into the engine like the Roboto font, so a built game needs no file) is put under every game GUI document's own sheets. Your RCSS overrides it by the normal cascade: a rule at least as specific as the default's wins. The default selectors are input.toggle (:hover, :checked), input[type="range"] with slidertrack, sliderprogress and sliderbar, select with selectvalue, selectarrow, selectbox and option, .spinbox with .spinbox button and .spinbox input, and progress with progress fill. For example progress fill { background-color: #3060ff; } recolours every bar, and the default sizes (160 px wide controls) stay unless you set them. Nothing else is styled: text fields, buttons and checkboxes without class="toggle" look as before. A range input or <select> your sheet already styles keeps your properties and gains the default's others (the track's height, the arrow box).
  • Spinbox (driven by the engine, no script needed): the - and + buttons step by data-step; Up / Down step while its input has focus; typed text is checked on Enter and when the input loses focus: a number is snapped to data-min + k * data-step and clamped to [data-min, data-max] (a max off that grid clamps to the last step under it), anything else reverts to the last valid value. A fractional step shows its decimals (data-step="0.25": "1.50"). Missing data-min / data-max are unbounded; a missing or bad data-step is 1. Put the id, data-event and data-min / data-max / data-step on the div, the starting value and any data-value binding on its <input>.
  • Change events: give a toggle, slider, dropdown or spinbox data-event="name" (on the <input> / <select>; on a spinbox's div) and every change the player makes publishes name on the event bus, publisher UI, with {"id", "document", "value"}: the widget's id ("" if none), its .rml, and the new value typed as above. A slider publishes at every step while it is dragged, as well as on clicks and arrow keys; a spinbox once per step or accepted entry (its - / + buttons publish no button event of their own); a progress bar never. Changes the game makes (kast.gui.setValue, a data model update moving a bound widget) publish nothing, so a handler that writes a value back can't loop. 
    kast.subscribe("settings.volume", function(e) kast.log("volume " .. e.value) end)          -- e.value is a number
kast.subscribe("settings.sound", function(e) kast.log(e.id .. " is " .. tostring(e.value)) end)   -- a boolean
  • Lua: kast.gui.value(id) returns the typed value (a spinbox's id is its div's; a plain checkbox also reads as a boolean). kast.gui.setValue(id, value) sets it as the player could: a slider's and spinbox's number snapped and clamped, a progress bar's clamped to 0..max, a toggle takes a boolean, a dropdown the value of one of its options, a text field a string. A value of the wrong type, an option no dropdown has, or an id that is no widget logs a warning (never the value) and changes nothing. A value is kept like setText (Play start, hot reload), unless no loaded widget took it. A value that isn't a boolean, number, string or nil raises (nil, which clears a list's selection, is the wrong type for a widget: logged). 
    kast.gui.setValue("loading", done / total) -- drives a progress bar
if kast.gui.value("sound") then ... end
  • Data binding: data-checked on a toggle, data-value on a slider, a dropdown and a spinbox's <input> are two-way (a spinbox writes its model when it accepts a value; a number variable stays a number), and data-value or data-attr-value on a progress bar sets it. Widgets inside data-for rows, and ones made by kast.gui.clone or kast.gui.create (a spinbox needs its three children), are styled and publish like authored ones.

Sample and tests: tests/project/ui_widgets.scene shows ui/widgets.rml (all five, unstyled by its widgets.rcss; a fractional spinbox; the same widgets bound to model wbind with toggles made by data-for), driven by scripts/ui_widgets.lua, which logs every change event and drives the progress bar with setValue; ctest -R "ui_widgets|player_widgets|gui_builder_widget" and self_check's checkGuiWidgets.

Effects: glow, filters and gradients

RmlUi's CSS effects draw in Play (the Game view), the GUI Builder preview and the built player alike (engine/gui_render.cpp, engine/gui_effects.cpp, shaders engine/shaders/gui/fs_gui_matrix.sc, fs_gui_blur.sc, fs_gui_gradient.sc):

Property Supported
box-shadow Offset, blur, spread and colour; several shadows, comma separated. The way to make an element glow.
filter blur(), drop-shadow() and the colour filters opacity(), brightness(), contrast(), grayscale(), sepia(), hue-rotate(), saturate(), invert(); several, space separated, apply in order.
backdrop-filter The same filters on what is behind the element, e.g. blur() for frosted glass under a translucent background.
decorator linear-gradient, radial-gradient, conic-gradient and their repeating- forms, up to 16 colour stops (more are dropped).

A glow is a box-shadow with no offset. The Starter MMO's buttons (samples/starter-mmo/ui/starter.rcss):

button:hover { background-color: #ffcc00; box-shadow: 0 0 8px 6px #ffcc00; }   /* hover glow */
button.power { box-shadow: 0 0 6px 3px #ffaa00; }                               /* a ready power */
button.power.cooling { box-shadow: none; }

Fainter than a browser: like RmlUi's own reference renderer, the engine keeps the shadow off the element before blurring it, so only the ring the spread adds outside the element is blurred. Near the element a glow is therefore dimmer than a browser draws it: 0 0 12px 4px #ffaa00 gives about 26% of the colour 2.5 px out, where a browser gives about 60%. For a bright glow use a larger spread and a shorter blur (0 0 8px 6px), a brighter colour, or stack two shadows (box-shadow: 0 0 6px 4px #ffcc00, 0 0 16px 6px #ffaa00).

Performance: effects cost only where they are used. A document without shadows, filters or gradients draws exactly as before, in one bgfx view, with no offscreen targets (ctest -R ui_play checks main_menu.rml creates none). The first effect creates the GUI's layers: RGBA8 render targets the size of the GUI (logged as GUI layer framebuffer N created) and one depth-stencil buffer, kept for later frames and recreated when the GUI resizes. Every change of render target uses another bgfx view, out of gui::kViews (65) per GUI each frame:

  • a blurred box-shadow about 9 views, but only on the frame it is drawn into its texture; it is cached after that until the element's size or shadow changes (a hover glow bakes each time the mouse arrives; animating a shadow re-bakes it every frame);
  • a blur() filter 3 to 5 views every frame, more for a large radius; a drop-shadow() 2 more than its blur;
  • a colour filter or opacity() about 2 views every frame;
  • a gradient decorator none: it draws in the element's own pass.

Past the budget the engine logs GUI effects need more than 65 bgfx views in a frame; some are not drawn once, and the draws that needed more views are skipped that frame. backdrop-filter must read what is already drawn: in the built player, which draws to the window's backbuffer, the first frame that needs it draws without the effect, and from then on the player draws scene and GUI into a readable target and copies it to the window (one full-screen copy per frame).

Failures never stop the document: the element draws without the effect.

  • An unknown filter or gradient name, or one RmlUi can't parse, is RmlUi's own warning (RmlUi: ...) about the style sheet, and never reaches the renderer.
  • Invalid parameters (filter: blur(-4px)) log GUI filter 'blur' has invalid parameters: elements using it draw without it once per filter, plus RmlUi's Could not compile filter on element: ....

Tests: ctest -R "effects|ui_layer|bad_filter|starter_mmo_(login_hover|hud_glow)" plays tests/project/ui/effects.rml (one element per effect) in the Game view, the GUI Builder and the built player and checks each effect's pixels.

Masking: mask-image and shape clipping

Two standard RmlUi CSS routes mask an element, in Play, the GUI Builder preview and the built player alike (engine/gui_render.cpp, engine/gui_effects.cpp; no extra shader):

CSS Effect
mask-image The mask's alpha multiplies the element (its content, background and children). Sources: image(file.png) (a path relative to the style sheet), linear-gradient, radial-gradient, conic-gradient and their repeating- forms. Several, comma separated, add up. Combines with filter (the mask applies last), border-radius and clip masks.
overflow: hidden on a rounded (border-radius) or transformed element Children are clipped to the element's real shape (a circle, a rotated box) instead of its bounding rectangle. The clipped children must be in normal flow: RmlUi doesn't clip absolutely positioned children.

RmlUi 6 takes no percentage border-radius (50% is a syntax warning): for a circle give half the box's size in px. The Starter MMO (samples/starter-mmo/ui/starter.rcss) uses all three typical cases:

#target_portrait { width: 52px; height: 52px; border: 2px #ffaa00; border-radius: 28px; overflow: hidden; } /* round portrait */
#chat_log { mask-image: linear-gradient(to bottom, #00000000 0px, #000000ff 60px); }   /* oldest lines fade out at the top */
/* cooldown wipe: scripts/powers.lua sets the angle each frame from the fraction of the cooldown left */
#power_1_wipe { background-color: #000000b0; mask-image: conic-gradient(#00000000 0deg, #00000000 94deg, #000000ff 94deg); }

Shape clipping on the base layer: clip masks use a stencil, which the window's backbuffer (or a host's target) doesn't give the GUI. The first frame a document asks for one on its base layer draws that element clipped to its rectangle; from the next frame on the GUI draws its base layer into an offscreen layer with the GUI's stencil (logged once as GUI base layer redirected for clip masks (WxH)) and copies it onto the target at the end. Shapes are therefore exact from the second frame. The redirect stays on until 60 renders pass without a request (about a second), so an element that hides for a moment keeps its shape when it returns. Inside effect layers clip masks work at once. Note that form widgets with a rounded, scrolling style (overflow-y: auto) ask for one too.

Performance: masking costs only where it is used; a document without mask-image or shape clipping draws exactly as before (ctest -R "ui_play|ui_layer|ui_effects" forbid the redirect line). In views (out of gui::kViews, as for the effects):

  • a mask-image element about 4 views every frame: its own layer, the mask's layer, the masking pass and the return to the layer below; and one more GUI layer in the pool while a mask is held;
  • shape clipping on the base layer 2 views every frame while redirected, whatever the number of clipped elements, plus 2 per backdrop-filter (it reads what the redirect has drawn so far), and one GUI-sized layer; each clip itself draws its shape into the stencil in the current view;
  • shape clipping inside an effect layer nothing extra.

Failures never stop the document:

  • A mask with no layer to save it in logs GUI mask-image has no layer to save its mask in: elements using it draw unmasked once, and the element draws unmasked.
  • Out of views, the effects' GUI effects need more than 65 bgfx views in a frame; some are not drawn warning fires once and the masked element is not drawn that frame (its final composite needs a view too).
  • A source RmlUi can't parse is RmlUi's own warning (RmlUi: ...) about the style sheet.

Tests: ctest -R masks plays tests/project/ui/masks.rml (one element per masking case) in the Game view, the GUI Builder and the built player, and the Starter MMO HUD (round portrait, chat fade, cooldown wipes), and checks their pixels; kast_self_check covers the no-layer failure.

Resolution and DPI scaling

A GUI designed at one resolution should look right on a 4K monitor, at Windows' 150% display scale, and when the player asks for bigger text. One number does that: the dp ratio, how many window pixels one RmlUi dp unit is.

dpRatio = refFit × (useOsDpi ? osScale : 1) × uiScale
refFit  = exp2(lerp(log2(width / refWidth), log2(height / refHeight), match))   (1 without a reference resolution)
  • refFit is Unity's CanvasScaler "Scale With Screen Size / Match Width Or Height": the window's size against the project's reference resolution, blended in log space. match 0 fits the width, 1 the height, 0.5 both equally. Reference 1920x1080 in a 3840x2160 window is 2 at any match; in a 1920x2160 window it is 1 at match 0, 2 at match 1 and √2 at 0.5.
  • osScale is the OS display scale of the monitor the window is on (1 = 100%), SDL_GetWindowDisplayScale.
  • uiScale is the player's multiplier, 0.5 to 3 (kast.gui.setScale).

The ratio is recomputed when the window is resized, moves to another monitor, the Windows scale changes (SDL_EVENT_WINDOW_DISPLAY_SCALE_CHANGED) and when any setting changes; a minimized (zero-size) window keeps the last one. Each change logs GUI dp ratio 2 (1280x720 pixels, display scale 1, UI scale 1).

dp and all documents

Each UI Document chooses what follows the ratio, with its Scaling field (Inspector; "scaling" in the scene file, left out while it is dp, so older scenes load and save unchanged):

ScalingWhat scalesUse it for
dp (default)Only dp units: width: 160dp is 320 pixels at ratio 2. px stay physical pixels. Text in dp is rasterized at its real size, so it stays sharp.New GUIs: write sizes and fonts in dp, keep px for hairlines that must stay one pixel.
allEverything, px too: the document lays out at the window's size ÷ dpRatio and is drawn scaled up by dpRatio; mouse positions are mapped back, so clicks land on the scaled elements. Text is drawn at its layout size and magnified, so it is softer than dp text at ratios above 1.Existing px GUIs that should simply grow with the screen.

Both kinds work together in one scene. They live in two RmlUi contexts (RmlUi's dp ratio and layout size are per context) that act as one GUI: all documents draw above every dp document, whatever their entity order; the mouse goes to an all document while it is over one of its elements, otherwise to the dp documents; a click or kast.gui.focus in one takes the keyboard there and blurs the other's focused field; kast.gui.click, focus, mouseOver, hovered, data models and every other kast.gui call span both. Without a reference resolution and at 100% display scale the ratio is 1, so existing px documents look exactly as before. Effect filters in an all document run on the window's pixels, so a blur() radius is not scaled with the document.

project.kast "gui"

The project's defaults, set in Build > Display & GUI Scaling... (the block is left out of project.kast while everything is default; without it the ratio is just the display scale):

"gui": {
  "referenceResolution": [1920, 1080],  // optional; [width, height], 1..16384
  "match": 0.5,                         // 0..1, default 0.5
  "useOsDpi": true,                     // default true
  "uiScale": 1.0,                       // 0.5..3, default 1
  "mode": "windowed",                   // the player's window: "windowed" | "borderless" | "exclusive"
  "width": 1280, "height": 720,         // its size (exclusive: the display mode's), default 1280x720
  "refresh": 144                        // optional; exclusive: Hz, unset = the highest that size has
}

A wrong type or value fails the project's load naming the field, e.g. Invalid project '...': "gui": match must be a number from 0 to 1.

Player window modes

The built player opens windowed at any size, borderless fullscreen on the desktop of its monitor, or exclusive fullscreen in one of that monitor's display modes (WxH@Hz, from SDL_GetFullscreenDisplayModes). At startup the project's window applies, the user settings file over it, and the --size WxH flag over both (a window of that size). Lua switches at run time with kast.display.setMode.

User settings file

What the player chooses through kast.display.setMode and kast.gui.setScale is kept per Windows user in %APPDATA%\Kast\<project name>\settings.json (SDL_GetPrefPath("Kast", name); characters other than letters, digits, space, -, _ and . in the name become _). The player logs its path at startup (User settings: ...); --user-settings <file> uses another file (tests). Every key is optional:

{ "mode": "windowed", "width": 800, "height": 600, "refresh": 60, "uiScale": 1.5 }

A missing file means the project's defaults. A corrupt or invalid one logs User settings '...' are invalid (...): using the project's defaults and the project's defaults apply. Runtime changes are never written back to project.kast. The editor never reads or writes this file.
