Game GUI

Game GUIs are HTML/CSS-like documents rendered by RmlUi (engine/gui*.h, engine/scene_gui.h): an .rml file for the elements and a sibling .rcss file for their style. RmlUi reads them through the engine's file access (disk in the editor, game.pak in the player), logs to the Console as RmlUi: ..., and draws with bgfx (engine/shaders/gui/).

Files: an .rml links its style sheet in its <head>; the builder edits the elements under <body>:

<rml>
    <head>
        <title>Main Menu</title>
        <link type="text/rcss" href="main_menu.rcss"/>
    </head>
    <body>
        <div id="menu" class="panel">
            <p id="title">Kast Quest</p>
            <button id="start_button" data-event="menu.start">Start</button>
        </div>
    </body>
</rml>

Elements: Panel = <div>, Text = <p>, Button = <button>. A Button's data-event names the event its click publishes (see below). Any other element (hand-written <span>, <img>, ...) is Unknown to the builder: listed and movable/deletable there, never created or edited, and kept with its attributes and children on save. Attributes the builder doesn't edit (style, title, data-*, ...) and comments are kept too; saving only normalizes whitespace and indentation.

Style sheets are RCSS (CSS2-like; see the RmlUi docs). RmlUi has no built-in styles: elements are inline until a rule says otherwise, so sheets start with div, p { display: block; }. The only font is the bundled Roboto (font-family: Roboto;, set on body); text without a font-family doesn't show (RmlUi warns). Images (<img src>, decorator: image(...)) are PNG or JPG files, paths relative to the document (or style sheet), read from disk or the built game's pak and drawn 1:1; a missing file is RmlUi's Could not load texture warning. A dragged element's clone (outside any document) finds them relative to the dragged element's document.

UIDocument (built-in component, UI Document in the Inspector): path (project-relative .rml; the Inspector offers a combo of the project's .rml files, an unknown path shows as (missing) <path> and is kept) and visible (default true). Saved with the scene like any component. In Play (and in the built game), every UIDocument in the scene loads at Play start and shows over the Game view while visible, stacked in entity creation order (later entities on top); they unload on Stop and on a kast.loadScene switch (the new scene's load instead). Adding, removing or editing a UIDocument during Play applies at once. A missing .rml, an .rml RmlUi can't parse or a linked .rcss with problems logs an error naming the file and that document shows nothing; Play goes on. While the Game panel has input (focused and playing) the GUIs get the mouse, wheel and keys too (the game's kast.* input still sees them).

Button events: clicking a <button> with a non-empty data-event publishes that event on the Play session's event bus, publisher UI, payload {"id": "<button id or empty>", "document": "<rml path>"} (the UIDocument's path). No or empty data-event: nothing is published. Lua subscribes as to any event:

kast.subscribe("menu.start", function(event)
    kast.log("Menu start clicked: " .. event.id .. " in " .. event.document)
end)

Drag and drop: an element is draggable when its style sheet gives it RmlUi's drag property (drag: clone draws a copy under the cursor while the original stays put; drag-drop and drag work too). Give it (or an ancestor) data-drag="name" and the drag publishes on the event bus, publisher UI:

  • name.start once the mouse has moved with the button down on it;
  • name.drop when the button is released, wherever that is.

Both carry {"id", "document", "target", "targetDocument", "shift", "ctrl", "alt"}: id is the dragged element's id (or its nearest ancestor's with one), document its .rml. On a drop, target is the id of the element under the cursor (or its nearest ancestor with one) and targetDocument that element's .rml; both are "" when released over no element or over a document's own <body> (the world). shift, ctrl and alt are the modifier keys held at that moment. The engine moves nothing: Lua decides what a drop means.

.slot { drag: clone; }

<div id="slot_3" class="slot" data-drag="bag.slot"><div id="icon_3" class="icon"></div></div>

kast.subscribe("bag.slot.drop", function(e)
    if e.target == "" then askToDestroy(e.id)                 -- dropped on the world
    elseif e.targetDocument == e.document then move(e.id, e.target, e.shift) end
end)

Stacked documents: a document's <body> is usually full-screen, and RmlUi gives the mouse to the topmost element under it, so a later document's empty body hides the panels of the ones below from clicks, drags and hover. Give body pointer-events: none and the panels pointer-events: auto (it is inherited); the starter-mmo sample's starter.rcss does.

A press that starts a drag is a press on the GUI, so kast.gui.mouseOver() was true when it went down. The editor's --sim-mouse frame,left[+shift],dx,dy,0 performs one drag for tests (ctest -R ui_drag, tests/project/ui_drag.scene).

kast.gui (Lua, in Play and the built game; nil where no game GUI runs): reads and writes elements of the scene's loaded documents by id, topmost document first (engine/gui_access.h).

Function Returns Notes
kast.gui.value(id) string or nil The current text of the <input> / <textarea> with that id; nil if no loaded document has one.
kast.gui.setText(id, text) — A text field's value; any other element's content as plain text (escaped, "\n" is a line break).
kast.gui.setVisible(id, visible) — false hides the element (display: none), true gives it back its style sheet's display.
kast.gui.setAttribute(id, name, value) — Sets an attribute (all strings): an <img>'s src (relative to the document, like in the .rml), the class list ("slot uncommon") for styling, a style such as decorator: image(../icons/wing.png), ...
kast.gui.focus(id) boolean Gives the element keyboard focus, as a click would (a text field: typed text goes there, e.g. Enter to chat). false if no visible document has that id. Not kept.
kast.gui.focusedField() string or nil The id of the text field (<input type="text">, "password", <textarea>) with keyboard focus, e.g. to ignore movement keys while the player types.
kast.gui.mouseOver() boolean The mouse is over a GUI element (RmlUi's hover element is something other than a document's own <body>, so a full-screen body doesn't count). Checked when a button goes down, it tells a press on the chat box from a press on the world.
kast.gui.hovered() string or nil The id of the element under the mouse, or of its nearest ancestor with one (an icon inside a slot reports the slot); nil over no element or only a <body>. Poll it each update for tooltips.
kast.gui.set(model, key, value) — Replaces the top-level variable key of the data model model: a string, number, boolean, nil (unset), an array or a table of string keys, nested. The views bound to it update.
kast.gui.get(model, key) the value or nil The variable as it is now, edits through two-way bound fields included; a fresh Lua copy. nil if unset.
kast.gui.clone(templateId, parentId, newId) boolean Deep-copies templateId (from parentId's document) under parentId as newId, shown. See runtime elements.
kast.gui.create(parentId, tag, newId[, attrs]) boolean Appends a new <tag id="newId"> to parentId, with attrs (a table of string attributes, e.g. {class = "row"}).
kast.gui.remove(id) boolean Removes the element (and its children) from the topmost document holding it.

Writes (setText, setVisible, setAttribute) are kept and applied again to every document that loads later, so a system's init (which runs before the scene's documents load) and hot reloads see them; they are forgotten when the scene switches (kast.loadScene) and at each Play start. A write to an id no document has does nothing. Arguments that aren't strings (or, for setVisible, a boolean) raise at the calling line. Values and texts are never logged: a field may hold a password, so clear it after reading (kast.gui.setText("password", "")). Typed text reaches the fields because SDL text input is on while one has focus (editor: while the Game view has input).

kast.subscribe("login.submit", function()
    local email, password = kast.gui.value("email"), kast.gui.value("password")
    kast.gui.setText("password", "")
    kast.gui.setText("status", "Logging in...")
    kast.auth.login(email, password)
end)

Hot reload (Play): when a loaded .rml or a .rcss it links changes on disk (the editor's 0.5 s file poll), that document reloads; fix a broken file and it shows again. Not in the built game.

Sample: tests/project/ui.scene has a Main Menu entity with a UIDocument for ui/main_menu.rml (+ main_menu.rcss: a panel with a title, a subtitle holding an unknown <span>, and Start / Quit buttons publishing menu.start / menu.quit); scripts/ui_menu.lua logs both events.

Data binding

RmlUi's data bindings work without any C++: an element with data-model="name" opens a model, and inside it {{expression}} in text, data-for, data-if, data-visible, data-value, data-checked, data-attr-*, data-class-*, data-style-*, data-rml, data-alias-* and data-event-* read its variables. Lua fills them with kast.gui.set:

<div id="quests" data-model="quest_log">
    <p>{{title}} ({{count}}) <span data-if="full">full</span></p>
    <button class="row" data-for="row : rows" data-attr-id="'row_' + it_index"
            data-class-selected="row.selected" data-event="quest.pick">
        {{row.title}} <span data-for="goal : row.goals">{{goal}}</span>
    </button>
    <input type="text" id="filter" data-value="filter"/>
</div>

kast.gui.set("quest_log", "title", "Quests")
kast.gui.set("quest_log", "rows", {{title = "Bat Trouble", goals = {"Bats 2/3"}, selected = true}, ...}) -- as many as there are
kast.subscribe("quest.pick", function(e) kast.log(e.id) end)                                 -- "row_0", "row_1", ...
local filter = kast.gui.get("quest_log", "filter")                                           -- what the player typed
  • Models are made for you (engine/gui_models.h). Before a document loads, the engine reads its .rml for data-model names and the top-level variables its bindings read (rows in row.title / data-for="row : rows"; not data-for / data-alias names, members, | transforms, callbacks(), literals or RmlUi's reserved it, it_index, ev, size, ...). It creates each model on the scene's GUI context and binds each variable, so the document loads with no RmlUi warning (one would reject it). An unset variable reads as empty ("", false, no rows). Models belong to the context, not a document: two documents naming one model share it.
  • Values are plain data (GuiValue, JSON in C++): strings, numbers, booleans, arrays (a Lua sequence {a, b}; data-for repeats over it, rows.size is its length) and tables of string keys (row.title), nested up to 32 deep. An empty Lua table is an empty table (no rows). set replaces one top-level key whole; send the whole list again after a change. Numbers show without trailing zeros (3, 2.5).
  • Two-way: data-value on a text <input>, a range or a <select>, and data-checked on a checkbox, write the player's edits into the model; kast.gui.get reads them. A checkbox gives a boolean; text a string, kept a number when the variable held one and the text is a number (a range).
  • Persistence: values are kept until the scene switches (kast.loadScene) or Play starts again, like the other writes. A document that loads later, or hot reloads, shows the current values. A name stays bound for the session: a hot reload that turns a bound variable name into a data-for / data-alias name gets RmlUi's "shadowed" warning until Play restarts.
  • Events: data-event buttons and data-drag elements inside data-for rows publish as usual; give each row an id with data-attr-id (e.g. 'row_' + it_index, 0-based) to tell them apart. RmlUi's own data-event-click="..." runs model expressions; kast's data-event="name" (no suffix) is unaffected.
  • Errors: a model or key that isn't a string, a key that isn't a variable name (a letter, then letters, digits and _; not reserved) and a value that isn't plain data (a function, a cycle, mixed keys) raise at the calling line. Values are never logged.
  • The GUI Builder's preview creates the same models, empty: data-for rows and {{...}} show no data there.

Runtime elements: clone, create, remove

For elements outside a model (or when a list is easier by hand), kast.gui.clone copies a template, typically hidden in the .rml with style="display: none"; the copy gets newId, loses its inline display (shown), and its descendants' ids that start with "<templateId>_" are renamed to start with "<newId>_", so the copy's parts can be written:

<div id="list">
    <div id="tpl" class="row" style="display: none"><p id="tpl_name"></p><button id="tpl_pick" data-event="row.pick">Pick</button></div>
</div>

if kast.gui.clone("tpl", "list", "row_7") then kast.gui.setText("row_7_name", "Seventh") end -- row.pick: id "row_7_pick"
kast.gui.create("list", "p", "note_1", {class = "note"})
kast.gui.remove("row_7")
  • Live only: created and cloned elements (and removals) are not kept. They are gone when their document reloads (hot reload, Play start, a scene switch); model values are not. Do it again after a reload if needed.
  • false, not an error: a missing template, parent or id, an empty tag or newId, or a newId already in that document returns false and logs a warning saying which (kast.gui.clone('tpl', 'list', 'row_7'): the new id is taken in that GUI). remove also refuses (false, logged) a row a data-for made, or anything inside one: RmlUi owns those, change the model instead (the check is by position: an element just before a data-for one of the same tag counts too). Arguments of the wrong type raise like the other functions.
  • Clicks and drags work on them as on authored elements.

Sample and tests: tests/project/ui_bind.scene shows ui/bind.rml (two models: a bound list with nested tags and Pick buttons, two-way inputs echoed below; a clone template), driven by scripts/ui_bind.lua; ctest -R ui_bind, player_bind_click and self_check's checkGuiDataModels. The starter-mmo chat and quest log are bound lists.

Effects: glow, filters and gradients

RmlUi's CSS effects draw in Play (the Game view), the GUI Builder preview and the built player alike (engine/gui_render.cpp, engine/gui_effects.cpp, shaders engine/shaders/gui/fs_gui_matrix.sc, fs_gui_blur.sc, fs_gui_gradient.sc):

Property Supported
box-shadow Offset, blur, spread and colour; several shadows, comma separated. The way to make an element glow.
filter blur(), drop-shadow() and the colour filters opacity(), brightness(), contrast(), grayscale(), sepia(), hue-rotate(), saturate(), invert(); several, space separated, apply in order.
backdrop-filter The same filters on what is behind the element, e.g. blur() for frosted glass under a translucent background.
decorator linear-gradient, radial-gradient, conic-gradient and their repeating- forms, up to 16 colour stops (more are dropped).

A glow is a box-shadow with no offset. The Starter MMO's buttons (samples/starter-mmo/ui/starter.rcss):

button:hover { background-color: #ffcc00; box-shadow: 0 0 8px 6px #ffcc00; }   /* hover glow */
button.power { box-shadow: 0 0 6px 3px #ffaa00; }                               /* a ready power */
button.power.cooling { box-shadow: none; }

Fainter than a browser: like RmlUi's own reference renderer, the engine keeps the shadow off the element before blurring it, so only the ring the spread adds outside the element is blurred. Near the element a glow is therefore dimmer than a browser draws it: 0 0 12px 4px #ffaa00 gives about 26% of the colour 2.5 px out, where a browser gives about 60%. For a bright glow use a larger spread and a shorter blur (0 0 8px 6px), a brighter colour, or stack two shadows (box-shadow: 0 0 6px 4px #ffcc00, 0 0 16px 6px #ffaa00).

Performance: effects cost only where they are used. A document without shadows, filters or gradients draws exactly as before, in one bgfx view, with no offscreen targets (ctest -R ui_play checks main_menu.rml creates none). The first effect creates the GUI's layers: RGBA8 render targets the size of the GUI (logged as GUI layer framebuffer N created) and one depth-stencil buffer, kept for later frames and recreated when the GUI resizes. Every change of render target uses another bgfx view, out of gui::kViews (80) per GUI each frame:

  • a blurred box-shadow about 9 views, but only on the frame it is drawn into its texture; it is cached after that until the element's size or shadow changes (a hover glow bakes each time the mouse arrives; animating a shadow re-bakes it every frame);
  • a blur() filter 3 to 5 views every frame, more for a large radius; a drop-shadow() 2 more than its blur;
  • a colour filter or opacity() about 2 views every frame;
  • a gradient decorator none: it draws in the element's own pass.

Past the budget the engine logs GUI effects need more than 80 bgfx views in a frame; some are not drawn once, and the draws that needed more views are skipped that frame. backdrop-filter must read what is already drawn: in the built player, which draws to the window's backbuffer, the first frame that needs it draws without the effect, and from then on the player draws scene and GUI into a readable target and copies it to the window (one full-screen copy per frame).

Failures never stop the document: the element draws without the effect.

  • An unknown filter or gradient name, or one RmlUi can't parse, is RmlUi's own warning (RmlUi: ...) about the style sheet, and never reaches the renderer.
  • Invalid parameters (filter: blur(-4px)) log GUI filter 'blur' has invalid parameters: elements using it draw without it once per filter, plus RmlUi's Could not compile filter on element: ....

Not supported: mask-image (the renderer has no SaveLayerAsMaskImage), and clip masks in general. Clip masks work inside effect layers only, where box-shadow needs them; on the document's base layer they do nothing, so overflow: hidden on a transformed or rounded element clips to its plain rectangle (scissor) instead of its shape.

Tests: ctest -R "effects|ui_layer|bad_filter|starter_mmo_(login_hover|hud_glow)" plays tests/project/ui/effects.rml (one element per effect) in the Game view, the GUI Builder and the built player and checks each effect's pixels.
