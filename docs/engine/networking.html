Networking

Client TCP (plain or TLS), WebSocket (ws://, wss://) and HTTP/HTTPS from Lua (kast.net), on Boost.Asio + Beast with OpenSSL (engine/network.h). Editor Play and kast_player both run it. Lua may reach any host and port.

Lifetime: connections belong to the Play session, not the scene. A kast.loadScene switch keeps every connection open (same socket) and every request in flight; the new scene's systems re-acquire connections with kast.net.get(name) and subscribe to the events again. Connections close, and requests are cancelled, only on editor Stop, game exit, an explicit close, the peer or an error; Play always starts with none. There is no auto-reconnect: reopen on net.closed.

kast.net (errors raise at the calling line as kast.net.<fn>: ..., like kast.*):

Function Does
open{name, type, ...} -> handle starts connecting (asynchronously); options below. A name that is connecting or open raises; a closed one is replaced
get(name) -> handle \| nil the connection of that name (open, connecting or closed by the peer), nil if none
close(name) closes it after its queued sends (net.closed "closed by script" follows) and forgets the name; unknown names are ignored
request{url, method, headers, body, encoding, caFile, timeout} -> id a one-shot HTTP/HTTPS request; id (a number) is in its net.http.response / net.http.error
base64Encode(bytes) -> text, base64Decode(text) -> bytes standard padded base64 (decode raises on anything else)

A handle is a read-only table: h.name, h:send(data), h:close(), h:state() ("connecting", "open" or "closed"). Handles act by name, so one from an earlier scene still works. send before the connection opens queues the data; send on a closed or unknown connection raises.

open options:

Option Meaning [default]
name string, unique among open connections (required)
type "tcp" or "ws" (required)
host, port tcp: the server (required)
tls tcp: TLS over the stream [false]
url ws: ws://host[:port][/path] or wss://... (required)
framing tcp: "raw", "u16le" or "line" [raw]
encoding "text", "base64" or "json" [text]
caFile project-relative PEM file of extra trusted certificates (read from game.pak in a built game)
timeout seconds for DNS + connect + TLS/WebSocket handshakes [10]

request options: url (http:// or https://, required), method ["GET"], headers (a string-to-string table), body (sent as encoding says), encoding (of both bodies) [text], caFile, timeout (the whole request, seconds) [10]. No redirects are followed.

Events (on the session's event bus, publisher kast.net; conn is the connection's name):

Event Payload
net.open {conn}
net.message {conn, data}: one message (see framing) as the encoding says
net.closed {conn, reason}: "closed by script", "closed by peer" or the error's message; once per connection
net.error {conn, message}: a failure (followed by net.closed), or a message that didn't fit the encoding (dropped; the connection stays open)
net.http.response {id, status, headers, body}: headers by name (repeats joined with ", "), body as the encoding says
net.http.error {id, message}

Encodings (per connection or request; sends mirror receives):

  • text: data is a UTF-8 string. Received bytes that aren't valid UTF-8 give a net.error; sending invalid UTF-8 raises. WebSocket messages go as text frames.
  • base64: received bytes arrive as base64 text (kast.net.base64Decode gives the raw bytes); send takes base64 and sends the decoded bytes. WebSocket messages go as binary frames. Use this for binary protocols.
  • json: received data is parsed into a Lua table (or number, string, boolean; invalid JSON gives a net.error); send takes plain data (as kast.publish payloads) and sends it as compact JSON.

TCP framing: raw delivers each read as it arrives (message boundaries are whatever TCP gives; a UTF-8 character split across reads fails text, so prefer the others for text); u16le splits on a 2-byte little-endian length prefix counting the bytes after it, and send prepends it (at most 65535 bytes); line splits on \n (removed), and send appends one (data containing \n raises). Split and coalesced reads are reassembled. WebSocket messages are whole messages already. Note: the world server's frames (u16 length | u16 opcode | payload, see World Server protocol) have a length that excludes the opcode, so u16le doesn't split them; use raw with base64 and reassemble frames in Lua.

TLS (tls = true, wss://, https://): the server's certificate must verify against the Windows ROOT certificate store or caFile, and match the host name (or IP) connected to; SNI is sent for names. There is no way to turn verification off. For a self-signed development server (e.g. the world server's) put its certificate in the project and pass it as caFile.

Limits: one message, frame, line or HTTP body is at most 16 MiB: a larger one received gives a net.error and closes the connection (fails the request); a larger send raises. Connect and request timeouts default to 10 s. DNS failure, refused connection, TLS failure, timeout and peer close all end in events, never a Lua error.

Threading: one background thread runs every socket; Lua and the event bus are only touched on the main thread. Results queue in the network layer (not the bus queue, which a scene switch drops) and are published at the start of the next LuaSystems tick, before the systems' updates; after a kast.loadScene that is after the new scene's inits, so nothing received around the switch is lost. While the editor is paused nothing is published (results wait).

-- Scene A: log in over HTTPS, then open the game connection.
return {
    init = function()
        kast.subscribe("net.http.response", function(e)
            kast.net.open{name = "world", type = "tcp", host = "localhost", port = 7777, tls = true,
                          caFile = "certs/world_dev.pem", encoding = "base64"}
        end)
        kast.net.request{method = "POST", url = "https://localhost:8443/login", encoding = "json",
                         body = {user = "me", password = "secret"}}
        kast.subscribe("net.open", function(e) if e.conn == "world" then kast.loadScene("town.scene") end end)
    end,
    update = function(dt) end,
}
-- Scene B (town.scene): the same connection, still open.
return {
    init = function()
        local world = kast.net.get("world")
        kast.subscribe("net.message", function(e)
            if e.conn == "world" then local bytes = kast.net.base64Decode(e.data) --[[ parse frames ]] end
        end)
        kast.subscribe("net.closed", function(e) kast.warn("lost " .. e.conn .. ": " .. e.reason) end)
    end,
    update = function(dt) end,
}

Editor: Window > Network (read-only) lists, during Play, a card per connection (name, state, type, host:port or url, bytes in/out, last error) and the HTTP requests in flight; otherwise an empty-state line.

C++: kast::Network (from LuaSystems::network(); no Lua or ImGui): open, send, close, request, poll (the queued events) and status() (what the panel shows). Every call must come from the thread that made it (asserted in debug builds).

World round-trip time: while kast::WorldClient is connected to a world server (lobby or in the world) it sends its own Ping{nonce} every 1 s (steady clock) and times the matching Pong; it still answers the server's Pings with Pong. WorldClient::rttMs() is the newest answered Ping's round trip in whole ms, read by the F3 stats overlay. It is empty (the overlay shows Ping -- ms) when not connected (offline play, Online Services disabled, before the first Pong) and while a Ping is unanswered for more than 5 s. Pings unanswered after 5 s are forgotten, so a late Pong for one is ignored and at most six are outstanding. The bookkeeping is kast::PingTracker (engine/world_client.h), which takes the time as an argument for tests.

Built game: Build ships OpenSSL's libssl-3-x64.dll and libcrypto-3-x64.dll next to the exe.

Sample: tests/project/net_a.scene (scripts/net_a.lua) opens TCP, TLS, ws and wss connections to kast_net_test_server (tests/net_test_server.cpp, ports 47701-47706) and, in the frame all four open, starts a 100-line stream and two slow requests and switches to net_b.scene; scripts/net_b.lua re-acquires the connections, checks they are the same sockets and that every tick and both responses arrive, and logs PASS or FAIL.
