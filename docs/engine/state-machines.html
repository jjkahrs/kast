State machines

Game logic can be organised as finite state machines defined in Lua (engine/state_machines.h): named states, at most one current, with rules on which state each may be entered from and optional enter/exit callbacks. There are two kinds, built from the same definition files:

  • Game state machines: project-wide, one instance per Play session, listed by name in project.kast "stateMachines" (the State Machines panel's Global checkbox). They keep their state across kast.loadScene.
  • Entity state machines: one instance per entity with the built-in StateMachine component (machine, initialState).

Files: every .lua file under <project>/fsms/, scanned recursively, is one definition. Each returns exactly one table:

-- fsms/door.lua
return {
    name = "door",              -- required, unique: kast.fsm.* game target and StateMachine "machine"
    initial = "closed",         -- required: one of the states
    states = {                  -- required, non-empty: name -> state
        closed = { allowedFrom = {"open"}, enter = function(ctx) end, exit = function(ctx) end },
        open   = { allowedFrom = {"closed", "locked"} },
        locked = { },                      -- no allowedFrom: enterable from any state
        broken = { allowedFrom = {"*"} },  -- "*": from any state
    },
}
  • name is a non-empty string; state names are non-empty strings other than "*". allowedFrom is a list of state names of this machine, or "*". enter and exit are optional functions. There is no per-state update: drive machines from Lua systems.
  • A file that isn't valid Lua, raises, doesn't return exactly one table, has a missing or non-string name, an initial that isn't one of its states, an allowedFrom entry naming an unknown state, a wrong type or an unknown key is rejected. The message starts with the project-relative path (and the line for Lua errors), is logged as State machine rejected: ... and shown in the State Machines panel. If two files declare the same name, both are rejected, each naming the other.
  • Callbacks run sandboxed like Lua systems: each definition file has its own environment with the full read-only kast API. kast.log and events published from a callback are prefixed / attributed with the definition's path (fsms/door.lua).

Callbacks get one argument, ctx:

Field Value
ctx.machine The definition's name.
ctx.entity The entity id for an entity machine; nil for a game machine.
ctx.from The state being left; nil when the machine enters its first state (Play start, runtime add, hot reload reset).
ctx.to The state being entered.

exit and enter of one transition get the same ctx.

Transition rules (kast.fsm.change / StateMachines::change):

  • A state may be entered from the current one if its allowedFrom is omitted, contains "*", or lists the current state. That includes a self-transition (target == current): it is allowed only by the same rule (omitted or "*" count as listing itself), and then runs exit and enter and publishes an event like any other.
  • Denied (not allowed, or an unknown target state): returns false with a Console warning (State machine "door" (entity 3): "open" can't be entered from "open" (allowedFrom); staying in "open"). Nothing else happens: same state, no callbacks, no event.
  • Allowed: applied immediately, in this order: exit of the old state, the switch, enter of the new state, then fsm.changed is published on the event bus with {machine, entity, from, to} (entity is null for a game machine; the publisher is the definition's path). Returns true.
  • A change requested from inside enter or exit (of any machine) is queued and returns true; queued changes are applied after the current transition finishes, in request order (no recursion). One that turns out denied when applied logs the usual warning.
  • An error in enter or exit is logged with file:line and a traceback (State machine fsms/door.lua: enter "open" failed: fsms/door.lua:5: ...). The transition still commits and returns true; the machine stays usable.

Lifecycle:

  • Play start: definitions load into the session's Lua state, then every scene system's init runs, then each listed game machine enters its initial state, then every StateMachine entity (depth-first) enters its initialState. An empty or unknown initialState falls back to the definition's initial, with a warning. Entering a first state calls enter with from = nil and publishes no event. A machine touched by kast.fsm.* before that (from an init) enters right then, once.
  • A listed game machine without a valid definition is logged as an error (once per Play) and unavailable: kast.fsm.* on it raises.
  • An entity that gains StateMachine during Play (kast.add then kast.set of machine, an Inspector edit, a Duplicate) enters its initial state: at once from kast.add/kast.set, otherwise at the start of the next frame. Changing machine enters the new machine's initial state (no exit of the old one); changing only initialState does nothing until the next Play. kast.add alone leaves machine empty: no machine yet, and kast.fsm.* on it raises. A machine with no valid definition is logged once. A destroyed entity's machine, or one whose StateMachine is removed, just goes away: no exit.
  • kast.loadScene: game machines keep their current state name, with no callbacks; their definitions (and callbacks) reload into the new scene's Lua state. The new scene's entity machines enter after its systems' inits.
  • Stop resets everything; the next Play starts every machine from its initial state again. The current state is never saved: Stop restores the scene (and its StateMachine data) as it was.

Lua API (kast.fsm, read-only). target is a game machine's name (string) or an entity id (number):

Function Returns Notes
kast.fsm.state(target) string The current state.
kast.fsm.change(target, state) boolean The transition rules above.
kast.fsm.canChange(target, state) boolean The same check against the current state, with no side effects and no log.
kast.fsm.states(target) table The machine's state names, sorted.

A bad argument raises a Lua error at the calling line: an unknown or unavailable game machine, an invalid entity id, an entity without StateMachine (or with no valid machine), a target that is neither a string nor a number, a non-string state. An unknown state name passed to change is a denial (false and a warning), not an error.

local door
return {
    init = function()
        for e in kast.query("StateMachine") do door = e end
    end,
    update = function(dt)
        if kast.input.keyDown("E") and kast.fsm.canChange(door, "open") then
            kast.fsm.change(door, "open")
        end
        if kast.fsm.state("game_flow") == "paused" then return end
    end,
}

C++ API (kast::StateMachines, from LuaSystems::fsm(); no Lua or ImGui dependency), same rules, events and logging; a bad target throws std::invalid_argument (which kast.fsm turns into the Lua error):

kast::StateMachines& fsm = lua.fsm();
std::string state = fsm.state("game_flow");           // a game machine by name
bool opened = fsm.change(kast::EntityId{7}, "open");  // an entity machine by persistent id
bool can = fsm.canChange("game_flow", "paused");
std::vector<std::string> names = fsm.states(kast::EntityId{7});
std::optional<std::string> shown = fsm.peek("game_flow"); // editor display: never enters or throws

Hot reload: while playing, the fsms/ folder is checked every frame; on any added, removed or modified file every definition reloads (each in a fresh environment). A running machine keeps its current state if the new definition still has it; otherwise it resets to its initial state with a warning and enter runs with from = nil. New callbacks are used from then on. A definition that becomes invalid (or whose file is deleted) logs the error, and its machines keep their last valid definition until it is fixed.

Editor: the Inspector shows StateMachine as a Machine combo (valid definitions; a name with no valid definition is shown as (missing) <name> with a red "No valid definition" note, and kept as-is until another machine is chosen) and an Initial combo ((initial: <state>) for empty, then the machine's states; an unknown one shown as (missing) <state>), plus the live Current state while playing. See the State Machines panel under Editor controls.

Built games: fsms/ is packed into game.pak like every project file, and kast_player runs the project's game machines and entity machines exactly as Play does (definitions are read from the pak; hot reload doesn't apply).

Sample: tests/project/fsm.scene has two entities with StateMachine (traffic_light, from fsms/entities/traffic_light.lua, whose enter recolors the entity's material) and the project lists the game machine game_flow (fsms/game_flow.lua). scripts/fsm_driver.lua moves game_flow from boot to playing, then steps each light once (red → green, green → yellow) and tries to switch both to red: the yellow one may, the green one is denied with a warning.

The dock layout is saved to imgui.ini in the working directory; delete it to get the default layout back.
