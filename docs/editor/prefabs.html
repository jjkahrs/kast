Prefabs

A prefab is a reusable entity subtree saved as a .prefab file in the project. Instances of it in scenes stay linked: when the prefab changes, every instance follows, except for what the instance changed itself (its overrides). Prefabs need a project, and none of the actions below run during Play. The file format is in Coordinates and scenes.

Game GUIs have their own prefabs, reusable element subtrees in .guiprefab files with the same linked instances, overrides, Revert / Apply / Unpack and missing-prefab placeholders: see GUI Builder: GUI prefabs and Game GUI: GUI prefabs.

Creating a prefab

  • Drag an entity from the Hierarchy onto the Assets panel's background (the project root) or onto a folder: <entity name>.prefab is written there (Orc_2.prefab, ... if the name is taken).
  • Or right-click it in the Hierarchy > Create Prefab: the same, in the Assets panel's current folder (the selected folder, else the selected file's folder, else the root).
  • The entity becomes an instance of the new prefab. Its subtree may hold other prefab instances: they are nested in the new prefab and stay linked. An entity that is already part of an instance can't become a new prefab (unpack it first), nor can a subtree holding a missing-prefab placeholder.

Placing instances

  • Drag a .prefab from Assets onto the Hierarchy: on its empty space it becomes a root, on an entity a child of it.
  • Drag it onto the Scene view: a root instance where the cursor ray first hits a mesh or model, else where the ray crosses the y = 0 plane, else 10 m in front of the camera.
  • The new instance is selected; it starts at the prefab root's transform (the Scene view drop moves it).
  • From Lua: kast.instantiate(path, parent?, position?), in editor Play and in built games.

In the Hierarchy an instance root has a small cube icon after its name. Ctrl+D duplicates an instance as another linked instance; a duplicated prefab child becomes an added child. Prefab children can't be dragged to another parent: unpack the instance first.

Overrides

Overrides are per field: change a field of an instance entity (in the Inspector, the gizmo, ...) and only that field stops following the prefab. The instance root's name and Transform always belong to the instance. Structural changes are overrides too: adding or removing a component, adding a child entity (it is saved in the scene, not the prefab) and deleting a prefab child. Everything is worked out by comparing the entities with the prefab, so a field changed back to the prefab's value is no longer an override.

The Inspector, on any entity of an instance:

  • A Prefab card at the top names the prefab (and the prefabs nested inside it that this entity belongs to). On a prefab child, Select Root selects the instance root.
  • Overridden fields, the headers of components with overridden fields, added components and an overridden name are marked with a #ffcc00 bar at the Inspector's left edge.
  • Removed components are listed on the card (Removed component: X); on the instance root also its deleted children (Deleted child: X) and added children.

Revert, Apply and Unpack

  • Right-click a marked field, component header or the Name: Revert (back to the prefab's value; for a component header the whole component, removing an added one) or Apply to X.prefab (write this value into the prefab). Removed components and deleted children have their own Revert / Apply buttons on the card.
  • On the instance root: Revert All drops every override (fields, components, added children; deleted children come back); Apply All writes the whole instance into the prefab: overrides, added children (they become prefab children), deleted children (removed from the prefab). The root's own name and transform are never applied.
  • Unpack breaks the link: the instance becomes plain entities with their current values. Prefab instances nested inside stay linked (with what the outer prefab changed on them as their own overrides).
  • Apply writes the .prefab file immediately and refreshes every instance in the open scene. Other scenes pick the change up when they load.

Nesting

A prefab may contain instances of other prefabs, e.g. Tower.prefab holding a Crate.prefab. Changing Crate.prefab reaches the crate inside every Tower instance (under whatever Tower overrides on it). For an entity that belongs to several prefabs the Apply item is a submenu, outermost first: Apply to Tower.prefab (outermost) keeps the change as Tower's override of the crate; Apply to Crate.prefab writes it into the crate prefab itself (and clears the matching override in Tower). A prefab can never contain itself, directly or through nesting: creating, applying, saving or dropping something that would, is refused with an error saying which instance holds which prefab.

Prefab edit mode

  • Double-click a .prefab in Assets. The Hierarchy, Inspector and Scene view then show only the prefab, under the breadcrumb <scene name> > Crate.prefab at the top of the Hierarchy, with a Back button. The window title shows the prefab.
  • Edit it like a scene. Play is disabled. File > Save (Ctrl+S) writes the .prefab (Save As saves to the same file).
  • Back, opening another prefab, or opening / creating a scene, building or quitting with unsaved prefab changes asks Save / Don't Save / Cancel. The scene comes back as you left it (unsaved changes included), with every instance of the edited prefab, and of prefabs nesting it, refreshed and their overrides kept.

Renaming, moving and deleting prefabs

  • Renaming or moving a .prefab (or a folder holding prefabs) in Assets updates the references in the open scene and in every .scene and .prefab file of the project on disk.
  • Deleting a prefab that scenes or prefabs use lists those files in the Delete Asset confirmation first. If you delete it anyway, its instances load as missing-prefab placeholders.

Missing prefabs

A scene (or prefab) whose instance names a prefab that doesn't load (deleted, moved outside the editor, broken JSON, a cycle) still loads. The instance becomes a placeholder entity named after the prefab file, drawn red in the Hierarchy (its tooltip and the Inspector card name the path), and the Console has a warning naming the entity and the path. Saving keeps the reference and all its overrides unchanged, so once the prefab is back the instance is too.

Testing hooks

Every action above can run headless from the command line (--create-prefab, --drop-prefab, --drop-prefab-view, --set-field, --prefab-revert, --prefab-apply, --prefab-unpack, --edit-prefab, --prefab-save, --prefab-back), followed by --save-scene; the prefab_* tests in ctest use them on tests/project/prefabs.scene.
